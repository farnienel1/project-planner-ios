# iPhone 1.31 + 1.32: step by step

Work top to bottom and tick each box. The row numbers (A1, B4…) match `docs/test-sessions/1.31-1.32.md`.

Order: **1** (web rules) and **2–3** (screens, decisions) can run in parallel. **4** needs 1 done. **5–6** come last.

---

## 1. Publish web's 1.32.1 Firestore rules

**Who:** whoever deploys web. **Time:** about 10 min. **Warning:** `project-planner-f986c` is the live project, so publishing applies to every real user.

### 1.1 Check web 1.32.1 is live first
- [ ] Open the live web app in a browser and sign in.
- [ ] Go to **Settings**.
- [ ] Look for the line **Rules 1.32.1**. If it shows an older number, or no line at all, **stop**: web must be deployed first.

### 1.2 Get the rules file
- [ ] On your computer, open Terminal.
- [ ] `cd` into your `project-planner-web` folder.
- [ ] Run `git checkout main`
- [ ] Run `git pull`
- [ ] Run `head -3 docs/RULEBOOK.md` and check it shows **Version: 1.32.1**.

### 1.3a Publish from the console
- [ ] Go to https://console.firebase.google.com and pick **project-planner-f986c**.
- [ ] Left menu: **Build → Firestore Database**.
- [ ] Open the **Rules** tab.
- [ ] Open `firestore.rules` from the web folder in a text editor and select all and copy (⌘A, ⌘C).
- [ ] In the console editor, select all, paste over it (⌘A, ⌘V).
- [ ] Click **Publish**.
- [ ] Wait for "Rules published". If it says "unknown error", go to 1.4.

### 1.3b Or publish from the command line
- [ ] In the web folder run `firebase login` (only if not already signed in).
- [ ] Run `firebase deploy --only firestore:rules --project project-planner-f986c`
- [ ] It should end with **Deploy complete!** If it fails with 503 or "unknown error", go to 1.4.

### 1.4 If Google refuses the rules
- [ ] Don't retry repeatedly. Copy the error text.
- [ ] Give it to the web agent. The rulebook "Deploy notes" name a fallback file (`docs/rules-cost/`).

### 1.5 Confirm
- [ ] Console → Firestore → Rules → **History**: the newest entry is today.

## 2. Screen checks, Part A (seeded data, no Firebase)

**Who:** someone with a Mac and Xcode 26.2. **Time:** 30–45 min.

### 2.1 Get the code
- [ ] Open Terminal, `cd` into `project-planner-ios`.
- [ ] Run `git fetch origin`
- [ ] Run `git checkout rulebook-1.32.1-sync`
- [ ] Run `git pull`
- [ ] Run `git log --oneline -1`. It should be `a1e580c` or newer.

### 2.2 Get the right simulator
- [ ] Open Xcode → **Settings → Components**. Check **iOS 26.2** is installed; if not, click **Get**.
- [ ] Menu **Window → Devices and Simulators → Simulators**. If there's no **iPhone 16e** on iOS 26.2, click **+**, choose iPhone 16e and iOS 26.2, then **Create**.

### 2.3 Open and set up the project
- [ ] Double-click `Project Planner.xcodeproj`.
- [ ] At the top of the window, set the scheme to **Project Planner** and the device to **iPhone 16e (26.2)**.
- [ ] Menu **Product → Scheme → Edit Scheme…** → **Run** (left) → **Arguments** tab.
- [ ] Under **Arguments Passed On Launch**, click **+** four times and enter one per line:
  - `-uiTesting`
  - `-autoLoginRole`
  - `admin`
  - `-seedDemoData`
- [ ] Click **Close**.

### 2.4 Run as admin
- [ ] Press **⌘R**. Wait for the build (first time can take several minutes).
- [ ] The app opens already signed in as the test admin, with `TEST-` data.

Do these rows. After each one, write **pass** or **fail** and take a screenshot of each fail (**⌘S** in the simulator).

- [ ] **A1:** Bottom bar → **Settings** → scroll to the bottom. Under the app version, **Rules 1.32.1** is shown.
- [ ] **A3:** Still in Settings, find **Company-wide**. An amber **PAYE payday** banner is shown (the seeded org has no payday). Tap it: it opens **Payment runs & timesheets**.
- [ ] **A4:** On that screen, find **Set PAYE payday** and pick **Day 25**. Don't press Save. A **"Press Save to apply it…"** line appears, and the screen counts it as an unsaved change (Save becomes active). Go back without saving.
- [ ] **A5:** Go to **Timesheets** (Home → Timesheets) → **Overtime, Expenses & Price Work**. The payday banner is at the top.
- [ ] **A6:** Go to **Home** → quick actions. A **Weekly report** tile is there.
- [ ] **A9:** Go to **Daily Overview** → **Book labour** → pick an **operative** → **Other**. **Office / WFH / Site survey** are offered.
- [ ] **A12:** In Book labour, choose **Custom hours**. The overtime **rate** is shown, pre-filled with the organisation's rate (e.g. ×1.5).
- [ ] **A13:** Open a project → **Scheduling** → a person → **Hours**. The same pre-filled rate is shown.
- [ ] **A15:** Repeat a couple of these in dark mode (Simulator menu **Features → Toggle Appearance**). Look for cut-off text or overlapping parts.

### 2.5 Run as manager
- [ ] Stop the app (**⌘.**).
- [ ] **Product → Scheme → Edit Scheme… → Run → Arguments**: change `admin` to `manager`. **Close**.
- [ ] **⌘R**.
- [ ] **A7:** Home quick actions: **no** Weekly report tile.
- [ ] **A8:** **Manage Users** → pick someone → **Change user type → Manager**. There's **no** "Weekly Report" toggle.
- [ ] **A10:** **Book labour** → pick **someone else** → **Other**. Office / WFH / Site survey are **not** offered.
- [ ] **A11:** **My Schedule** → **Add booking** for **yourself**. Office / WFH / Site survey **are** offered.
- [ ] **A14:** **Daily Overview** → find a manager site booking that has its own rate. Its hours label shows **that** rate, not the organisation's.

### 2.6 Run as operative
- [ ] Stop, change `manager` to `operative`, **⌘R**.
- [ ] **A2:** **Settings** → bottom: **Rules 1.32.1** is shown for operatives too.

### 2.7 When finished
- [ ] **Edit Scheme → Arguments**: **untick** all four lines (needed for section 4).

## 4. Save checks, Part B (real Firebase, TEST organisation)

**Who:** you plus the Mac from section 2. **Time:** 1.5–2 hours. **Needs:** section 1 done.

### 4.1 Set up the TEST accounts (on web or iOS, signed in as the TEST org's admin)
Use real email addresses you can open (e.g. `you+test-lm@…`). Every name starts with `TEST-`.
- [ ] **TEST-Admin:** you, or a second admin.
- [ ] **TEST-LineManager:** Manage Users → **Add User** → type **Manager**, no admin. Send the invite and accept it **on web** from that email.
- [ ] **TEST-PAYE-Report:** Add User → type **Operative** → employment type **PAYE** → line manager **TEST-LineManager**. Accept the invite on web.
- [ ] **TEST-PAYE-NoLM:** Add User → **Operative**, **PAYE**, no line manager. If the form insists on a line manager, tell me: that's a finding.
- [ ] **TEST-OpsManager:** Add User → **Manager** with the **Operatives** toggle on.
- [ ] **TEST-OldRow:** **Operatives** → **Create Operative** (no app account). Book them on 2 PAYE days with overtime.
- [ ] Set up overtime for **TEST-PAYE-Report**: book them on 5 days in the current payrun with custom hours past the normal day.

### 4.2 Run the app against real Firebase
- [ ] Check the four launch arguments are **unticked** (2.7).
- [ ] **⌘R**, then sign in with the account each block says.
- [ ] Sign out between accounts (Settings → Sign out).

### 4.3 Overtime (B1–B10)
- [ ] **B1** as TEST-PAYE-Report: Timesheets → Overtime hub → **My…** → **Current payrun** → a **future** day → change overtime → save. It says it was **sent as a request**.
- [ ] **B2** same account: try a day in the **next** payrun. It's **locked**.
- [ ] **B3** as TEST-PAYE-NoLM: change overtime on a current-payrun day. It **saves directly**, with no request.
- [ ] **B4** as TEST-LineManager: Overtime hub → **Users'…** → TEST-PAYE-Report → the waiting request. Tick ✓ on **2** of the 5 lines and leave 3 → tap **Approve**. There's **one** Approve button, the message reads like **"Approved 2 of 5…"**, and the request stays **waiting**.
- [ ] **B6** as TEST-PAYE-Report: a notification **"Part of your overtime request was approved…"** arrived.
- [ ] **B5** as TEST-LineManager: decide the other 3 → **Approve**. The request is **complete**.
- [ ] **B7:** make a new request; as admin, **change one** of its bookings; as TEST-LineManager, approve everything. Only the changed line stays **waiting**.
- [ ] **B8:** a request with a TEST-OldRow line. That line shows **Needs an admin**. As admin, it can be approved.
- [ ] **B9:** open a request and decide **nothing**. **Approve** is greyed out.
- [ ] **B10** as admin: open a person who has records under an older id. All of them show.

### 4.4 Price work and expenses (B11–B15)
- [ ] **B11** as TEST-PAYE-Report: add one **expense** and one **price work** item (price work needs a **job number**).
- [ ] **B12** as TEST-LineManager: Users'… → TEST-PAYE-Report → **Expenses** → the range. ✓ and ✕ appear on each item, and a pick shows **"(not saved)"**.
- [ ] **B13:** ✓ one, ✕ the other → **Approve**. The message reads **"Approved 1 of 2…"** and each item shows its state.
- [ ] **B14** as TEST-PAYE-Report: own list shows the states, with **no** ✓/✕ buttons.
- [ ] **B15:** as TEST-PAYE-Report, look for any way to review your own items. There must be **none**.

### 4.5 Pay visibility (B16–B19)
- [ ] **B16** as TEST-LineManager: **Manage Users** → TEST-PAYE-Report. **No pay** is shown.
- [ ] **B17** same account: open **TEST-PAYE-Report's timesheet review**. Pay **is** shown.
- [ ] **B18** as admin: Home → **Weekly report** → export **PDF**, **XLSX** and **CSV**. Overtime rows read like **"2h at ×1.5 = 3h"**, and rows with their own rate are marked.
- [ ] **B19** as admin: the Pay Summary in the export has no gaps for people the admin can see.

### 4.6 PAYE payday (B20–B21)
- [ ] **B20** as admin: Settings → Payment runs & timesheets → payday **Day 25** → press the main **Save**. The banners on Settings and the Overtime hub **disappear**.
- [ ] **B21:** change it to **Day 28** → **Save**. A line says it changes **from the next payrun**.

### 4.7 Booking rate (B22–B24)
- [ ] **B22** as admin: Book labour → Custom hours → leave the rate as filled in → book. Then, in the Firebase console, open that booking: there's **no** `otMultiplierOverride` field.
- [ ] **B23:** book again and **change** the rate. The booking **has** `otMultiplierOverride`.
- [ ] **B24:** Daily Overview → move or edit the B23 booking → save. The rate is **still there**.

### 4.8 Invitations and legal pack (B25–B29)
- [ ] **B25** as admin: Add User → invite `you+test-inv@…` → then **Resend**. Both emails arrive, and only the **newest** link works.
- [ ] **B26** as TEST-OpsManager: invite an operative → Resend. It works. You only see invitations **you** sent.
- [ ] **B27** as admin: delete a person who has a pending invite. **No error**, and the invite is gone.
- [ ] **B28:** open an invite link **on web** and finish sign-up. The account is created; iOS has no accept screen of its own.
- [ ] **B29:** first launch as a new user → accept the legal pack → close and reopen the app. It **isn't** asked again.
