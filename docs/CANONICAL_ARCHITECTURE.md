# Canonical architecture

The executable business rules live in the web repository at `lib/canonical/engine.ts`. This app does not keep a second copy of those rules.

Falling back to `users/{uid}.organizationId` leaves `persistOrganizationId` null so that id is not copied into `cached_organizationId`. The payment-run 1–31 strip is visible only when `paymentRunShowsMonthCoverage` is true, which is `date_ranges`; a leftover `recurring_date` on that mode becomes `specific_dates`, and an invoicing save merges unknown keys on the existing `invoicing` map.

Rebuild the script from the web repo with `npm run build:canonical` and commit `canonical-business.js`. Do not edit the script by hand.

Manager catalogue visibility is not in the script. In Swift, a manager sees every project and every small works job, including jobs they are not assigned to. `permissions.projects` and `permissions.smallWorks` hide create and edit only. Super admin ignores those two toggles. Staff warning rows are the same canonical list for admins and managers. One email is one person: Swift sends the finished account with the smaller id first, unless that id is on `excludedUserIdsFromUnbookedWarnings`, and repeats that person row under every alias id. The scan passes those stored ids only. The script skips a row when the account it kept is in that list, so an excluded alias does not hide the other account on the email. Since script `315d73c4…` (web branch `cursor/warning-coverage-rulebook-530e`), `unbookedLabourRows` builds an email to user-id map from those rows and looks up manager bookings and approved holidays on every id that shares the email, so an alias that holds the hours or the leave covers the day. Swift keeps every row that function returns. Paid hours outside the standard day do not hide a row the script still calls missing. Weekend unbooked people on Daily Overview come from `unbookedLabourRowsOnDay`. Excluded users are omitted on Warnings and on Daily Overview. Do not hand-edit the script. A notification for a job still goes to the line manager or the assigned project manager, not to every manager. The web bundle must catch up if it still hides those lists or warning rows by assignment.

The material cut-off message and the clash row text still live in `Core/WarningsComputation.swift`; which bookings clash is the script's `overlappingIntervalGroups` over `slotInterval`, so groups and their resolution-key numbering match web. Those dates use `CanonicalBusinessEngine.businessCalendar`, not `Calendar.current`. Paid hours are the script's `payrollHoursResult` (see Paid hours below); `PayrollHoursEngine` only maps the Swift booking and policy in and the result out. Named `FULL DAY`, `AM`, and `PM` hours are defined in the canonical script (`paidHoursForNamedSlot`): a half day pays half the standard paid hours whatever its clock window.

## Standard day, AM and PM

The standard day and its two halves come from the script. `CanonicalBusinessEngine.halfDayWindows(CanonicalStandardDayInput)` returns the day, `am`, `pm`, the `pivot` (`break` or `midpoint`), and the break. The organisation policy fields go through unchanged; the script applies the 07:30–16:00 and 12:00–12:30 fallbacks. With the default policy AM is 07:30–12:00 and PM is 12:30–16:00. A company whose break is not usable (outside the day, or under an hour from either end) is split at the wall-clock midpoint. There is no Swift copy of that split; `PayrollTimePolicyCatalog.weekdayHalfDayWindows` is gone. The day input is always `CanonicalStandardDayInput(policy:)`, the weekday standard day and break, on Saturday and Sunday too, the same input the web app feeds in. Weekend custom windows and all-hours-at-multiplier stay in `timelinePolicy` for pay and drawing; they do not change the shared split.

The other wrappers in that file are `slotInterval` (the interval a booking occupies), `namedSlotKind`, `standardDayWindow`, `standardBreakWindow`, `mergeMinuteIntervals`, and `subtractMinuteIntervals`. `halfDayWindows` and `slotInterval` memoise script results per distinct input because clash and sort loops call them; the cache holds answers, not a rule.

Clash, sort, and calendar export (`OperativeBookingInterval.clashInterval`, `ManagerScheduleInterval.clashInterval`, `Booking` and `ManagerSiteBooking` `minutesSortKey` and `calendarBlock`, `HomeUpNextSupport.sortDate`) call `slotInterval` with the stored slot and the stored clock times and use the result as-is. Clock times win; the named slot applies only when the script rejects the clock pair (missing, unparsable, or end not after start). Swift has no "AM means the half even when clocks differ" branch and no local clock parsing on that path. Overnight clash extension is not implemented in Swift: an end before the start falls through to the named slot, as in the script. `payrollHoursResult`, `PayrollPolicyBookingRecalibrator`, the Book Labour quick AM/PM draft, the project week Quick Add slot picker, and the My Schedule default times take the halves from `halfDayWindows` or `slotInterval` with the same weekday input. Pay counts 22:00–02:00 as four hours inside `payrollHoursResult`; `Booking.totalBookedHours` (via `clockSpanMinutes`) shows the same wall length.

## Stored bookings

`FirebaseBackend.bookingsFromFirestoreDocuments` reads every `organizations/{orgId}/bookings` document through `CanonicalBusinessEngine.parseBookingDocuments`, which calls the script's `parseBookingDocument` once per document in one script call. That is the reader the web app uses, so both apps keep and refuse the same documents: legacy status spellings (`confirmed`, `pending`, `canceled`), a missing slot (FULL DAY), a missing `bookedBy`, a millisecond or ISO `date`, and clock times stored as instants all read. A refused document is logged as `BOOKING_REFUSED` with its id and the script's errors; nothing is dropped silently. There is no Swift booking parser.

A stored id that is not a UUID is kept (see the booking identity section from #131/#132: `Booking.internalOperativeId(for:)`, `operativeKey`, `storedOperativeId`). A booking document id that `uuidString` would not spell the same way is kept on `Booking.documentId`, and `saveBooking`, `deleteBooking`, and the offline outbox write under `documentKey`. Before this, iOS required a UUID `operativeId` and dropped those documents, so a person web showed as booked was unbooked on Daily Overview and Warnings and missing from the weekly report. `FirebaseBackend.lastBookingDecodeReport` counts the documents the reader kept or refused; refused ids are logged as `BOOKING_UNREADABLE_ON_IOS`.

A server snapshot of the bookings listener replaces the list (`BookingStore.applyRemoteBookings`), so a booking deleted or moved on the web leaves this device. Only cache snapshots are merged. Manager schedule documents with a missing or unknown `locationType` read as `project`, as web's `parseManagerSiteBooking` does.

A failed bookings or manager-schedule read, or a script that did not run, skips the warning scan (`WarningsDataCompleteness.blockingReason`). The Warnings screen shows that reason and no all-clear. Missing data is never treated as unbooked.

Daily Overview turns the picked day into London midnight and matches bookings with `businessCalendar`, the same day the unbooked rows use. A day before the launch query window is loaded on demand (`noteScheduleNeedsDate`).

## Paid hours

`CanonicalBusinessEngine.payrollHoursResult` (web `lib/canonical/payrollHours.ts`) is the one hours calculation for Daily Overview pills, the weekly report, timesheets, and invoicing on both apps. Input: the booking's slot, clock times, break-removed flag, and `otMultiplierOverride`; its London `dayKey`; and the organisation policy mapped field for field by `PayrollHoursEngine.canonicalPolicy`. Output: `standardHours` (paid at the normal rate), `outsideHours` (before the multiplier), `outsideMultiplier`, `totalPaidHours` (weighted), and the segments. Weekday rule: hours inside the standard day less the unpaid break when the booking spans the break window (not for AM/PM, not when the break is paid or removed); hours before or after at the weekday multiplier or the booking override. AM, PM, and custom hours within 20 minutes of a half pay half the standard paid hours. Saturday and Sunday use that day's rule (all hours at the multiplier, or a defined window that counts as `countsAsStandardHours`, pro rata, with outside hours at that day's multiplier). Sunday uses Saturday's rule when `sundaySameAsSaturday`. `effectiveWeekdayOtMultiplier` is `outsideMultiplier`. The weekday is the London day, never the device day. Weekly-report day units are `reportDayValue` (weighted paid hours over the standard day, capped at 1.5) and `subcontractorDayValue` (full day 1, otherwise 0.5). Timesheet normal hours equal `paid − outside × multiplier`, which is `standardHours`; web now uses the same figure.

## Booking identity

`users/{uid}.formerUserIds` is read with `parseFormerUserIds` onto `AppUser.formerUserIds` and passed as `formerIds` in every unbooked-labour person row, so a booking made while the person was a pending invitee still covers them after sign-up. iOS does not write it: `users/{authUid}` is created by the invitation's set-password step on the web (`completeInviteSetup`), which also records the 16-or-over confirmation the rules require. If an invitee signs in on iOS before that step, `mergePlaceholderUserDocOntoAuthUidIfNeeded` writes nothing and tells them to finish setup from the invitation email. Which statuses put a person on a job is `BookingStatus.occupiesDay` (`bookingOccupiesDay`: Confirmed, Tentative, Completed). Which bookings are still open on a job is `BookingStatus.isOpen` (`isOpenBookingStatus`: Confirmed, Tentative); the project people list uses it for subcontractor bookings, as web's active users list does.

## Past days

The launch listener only loads bookings from the earlier of the warning-window start and this Monday. Daily Overview calls `FirebaseBackend.noteScheduleNeedsDate` for the viewed day (on appear, on a day change, and for a historic date) and reloads bookings and manager schedules when that moves the window earlier. Without it, a past day such as 21 October showed no bookings on iOS while web listed them.

## Weekend defaults

`OrgPayrollTimePolicy.fromFirestore` uses `.defaultSaturday` (07:30–13:00 counts as 8h, 2× outside) and `.defaultSunday` (every hour at 2×) when the company never saved that day, the same as the rulebook's `DEFAULT_SATURDAY_PAYROLL` and `DEFAULT_SUNDAY_PAYROLL`.

## Weekly report pay

`reportPayCell`, `reportPersonPayCell`, and `reportPayTotal` (web `lib/canonical/reportPay.ts`) decide each pay cell, each person's total row, and the grand total. A PAYE line (`employmentTypeOnDay` is `paye` on that day) keeps its bookings, days, and hours, and its pay cell shows `PAYE` (`PAYE_PAY_CELL_LABEL`), not £0. It adds nothing to a pay total. A person who is PAYE on every line shows `PAYE` on the total row. Someone who changes type inside the period totals only the self-employed lines. A line with no rate shows no figure and is not labelled PAYE. The iOS PDF and XLSX export (`buildExportSections`) and the CSV builder use these cells. Approved timesheet lines for a PAYE day keep their hours with no pay.

The weekly report's hours still come from `PayrollHoursEngine` on iOS and `lib/timesheets/timesheetHours.ts` on web. Those are two calculators; see the open items in the web repository's architecture document.

## Annual leave against bookings

`CanonicalBusinessEngine.leaveCoverageRows(CanonicalLeaveCoverageInput)` returns the script's `leave_clash` rows (a booking inside approved leave) and `leave_cover` rows (half-day leave whose other half is not fully booked, with the clock ranges still open and their hours). `WarningsComputation` builds one person per account. `personKey` is that user id, the same key the web scan uses, with each alias id as its own person and every operative id on the email attached. A roster operative with no account uses the operative id. The payload also includes the coverage day keys, the weekday payroll fields, `includeWeekendsForUnbookedLabour`, the exclusion list, approved and pending holiday records (slot and day keys), and operative and manager bookings with their slot and clock times. The warnings screen shows `leave_clash` as high ("Booked during annual leave") and `leave_cover` as medium ("Half-day leave not covered"), with the script's message, missing ranges, and missing hours, under an Annual leave filter. The scan dates use `Europe/London`.

## User profile document

Every account is `users/{uid}`: operative, manager, admin, and super admin. `normalizeEmploymentType`, `employmentTypeOnDay`, `applyEmploymentTypeChange`, `employmentEffectiveLabel`, `accountKindFromFlags`, and `isBillableSelfEmployedDay` come from the packed script. Employment type is `paye` or `self_employed`. The camelCase `selfEmployed` spelling is accepted on read only. A future effective date stores the new type on `employmentType`, the previous type on `employmentTypeTransitionFrom`, and that day on `employmentTypeEffectiveAt`. Today or an immediate change clears the transition. Timesheets, the weekly report, and payroll ask `employmentTypeOnDay`. There is no Swift copy of that day comparison.

People lists (Manage Users, Managers, Operatives, and the project View filter) call `CanonicalBusinessEngine.listedRosterUsers` with the `organizations/{orgId}/userEmails` document ids (`organizationUserEmailClaims`; nil when that read failed). The tab then keeps rows whose `rosterSegment` is that tab. The profile passed in is `users/{uid}` `email`, `firstName`, `surname`, `name`, `displayName`, `passwordSet`, `isActive`, and `mobileNumber`. An anonymised deleted profile is Inactive: `isAnonymisedDeletedProfile` is true when the email is empty and `name`, `displayName`, or the first-and-surname name is `Deleted user`. `passwordSet` and `isActive` on that document do not put it on Active or Pending. `parseAppUserDocument` keeps that empty email. Re-invite of that email calls `resolveInviteEmailClaim` and `inviteEmailHasLiveClaim` from Add User and from `createUserInvitation`. The users lookup is only `inviteEmailOrgLookupConstraints` (this organisation and this email). The placeholder flags are `invitePlaceholderUserWriteFields`. `userCreateRequiresAgeConfirmation` is false for that placeholder, so `ageConfirmed`, `ageConfirmedAt`, and `ageConfirmedYears` are not written. `inviteWritesOperativeProfile` is false, so iOS does not write `organizations/{orgId}/operativeProfiles/{newUserId}` at invite. A typed day rate stays on `users/{uid}` as `payBasis` `day` and `dayRate`, and may also stay on `invitations/{id}`. Add User does not invent `hourlyRate`. Only a live `userEmails` claim, a finished account that still has the email, or a pending invite whose claim read failed blocks it. An allow with no `reuseUserId` writes a new `users/{uuid}` and points `userEmails/{email}` at that id. The tombstone uid is not rewritten, and the invite does not recreate `orgMemberships` or `operativeProfiles` on it. Schedule select-operative calls `listedCurrentLabourPeople` before the existing email list, on both the picker and the operatives a new booking can select. A `users/{uid}` row on the Operatives list is included when no operative shares that email, including when `passwordSet` is false. The booking id is that user id when it is a UUID. That path does not write `operativeProfiles`. The anonymised deleted profile stays off the list. People lists still show the profile on Inactive. A pending `users` document that still has a real name, email, or phone is dropped by `listedRosterUsers` once that email claim is gone, so the name, email, and phone are not shown under Pending. A pending invite whose email is still claimed stays Pending. A failed `userEmails` read does not drop those invites. `UserRosterSegment` is only the tab. There is no Swift Active/Inactive/Pending calculator on that path. Account delete, including the Auth email stored on `adminJobs/{uid}.email` before anonymise, stays on the web.

Edit User is the same screen from Manage Users, Manage Operatives, Managers, and the qualification warning “Open operative” button, for a person who has a login. A catalogue row with no `users/{uid}` stays on the operative editor. Managers see every staff warning. The button is hidden unless `permissions.operatives` is on, because they cannot open Edit User without it. Admins and super admins who can manage users still see it when Operatives is off. Operatives do not see the staff warning list. A save writes the nested `permissions` map and does not delete `hourlyRate`, trade fields, `status`, `payBasis`, or `lastSeenAt` just because this screen did not edit them. Employment type is not stored on `organizations/{org}/operatives/{id}`.

`canViewStaffWarnings` is the script’s staff rule. Permission row titles on Edit User match `userProfile.ts` (`Gives Manage Users.` and the organisational qualifications sentence). The packed script does not export `OPERATIVE_PERMISSION_TOGGLES` or `MANAGER_PERMISSION_TOGGLES`, so the row chrome stays in SwiftUI.

Qualification library search is `tokenizeQualificationSearch`, `qualificationSearchScore`, `rankQualificationRecords`, `qualificationLibraryFilterChips`, `qualificationMatchesSection`, `qualificationSearchRecordFromItem`, and `qualificationSectionChipLabel`. Records are name, code, awarding body, section, subsection, and notes. An empty query keeps the original order and still applies the section chip. Chip keys are the full section strings from `QUALIFICATION_LIBRARY_SECTIONS`; All is every row; Other is a row with no section. Organisation Qualifications, My Qualifications add, and Edit User use that one browser. A new organisation, and each Organisation Qualifications load, merges any missing starter codes from `missingStarterQualificationCodes` into `organizations/{orgId}/qualifications` (document id is the code). A guided-setup or custom row does not block the 272. The material catalogue still uses `starterCollectionShouldSeed` and writes only when that collection is empty. A template write always keeps `name`, `hasEndDate`, `createdAt`, and `updatedAt`, and adds `code`, `section`, `subsection`, `awardingBody`, `level`, `renewYears`, `renewalType`, `status`, and `notes` when the row has them. It does not delete the collection and rewrite it. Assignments stay on the operative: `qualifications[]` (`id`, `name`, `hasEndDate`, `createdAt`, `updatedAt`, optional `endDate`), `qualificationExpiryDates`, and `qualificationCertificateURLs`, keyed by that same document id. `assignedQualificationWriteFields` and `mergeOperativeQualificationWrite` build that write. The editor saves the assignment before any certificate upload, so a failed file still leaves the qualification. Certificate URLs merge through `mergeQualificationCertificateUrls`; a URL is removed only when this save cleared it. The storage path comes from `qualificationCertificateStoragePath`: `organizations/{orgId}/operatives/{operativeId}/qualifications/{qualificationId}/certificates/{uid}_{ts}_{name}`. The qualification save merges those three fields and does not rewrite the rest of the operative. Missing library codes are merged before names are restored from assignments.

Material search is `tokenizeMaterialSearch`, `materialSearchScore`, `rankMaterialRecords`, `materialRecordMatches`, `normalizeMaterialSearchText`, and `catalogueRecordFromItem`. Catalogue, project and small-works add, variation suggestions, and wholesaler history pass `{ name, brand, productCode, category, size, length }` and use the returned indexes. An empty query browses in the original order. Add-material suggestions ask for 80 hits. The record list stays in the script between keystrokes; Swift does not tokenise or score. Catalogue categories start collapsed so a few thousand rows are not built at once.

UTR and VAT number live in `users/{uid}/private/taxIds` (`sensitiveProfileDocPath`), not on `users/{uid}` or `invitations/{id}`. The document holds exactly `utrNumber`, `vatNumber`, `updatedByUserId`, and a server `updatedAt`, built by `sensitiveProfileWriteFields` (trimmed, at most `SENSITIVE_VALUE_MAX` characters, blank clears). After that write iOS deletes the legacy `utrNumber` and `vatNumber` from `users/{uid}`. Every read goes through `resolveSensitiveProfile`: the private document wins once it exists, even when a field in it is blank; otherwise the legacy fields are used until migration. `canViewSensitiveProfile` decides who sees them: the person, and admins or super admins not in operative mode. Everyone else sees `SENSITIVE_HELD_BY_ADMIN_COPY`, and iOS does not read the document for them. Values show as `maskSensitiveValue` with Show / Hide. Editing starts empty with a "Saved: … — type to replace" hint, plus Remove. Add User shows the fields only to admins and writes the placeholder's `private/taxIds`. Invite completion is the web set-password step, which moves that document to the new account (`moveTaxIds`); iOS does not create the account profile. Invoices and the signed-timesheet export leave UTR and VAT out unless the `SENSITIVE_EXPORT_OPTION_LABEL` toggle is on and `exportIncludesSensitiveFields` agrees. The toggle starts off every time and is shown only to viewers who may see the values. The blank-UTR warning appears only when the toggle is on. `AppUser.vatNumber` and `utrNumber` hold only the legacy copy, for that fallback. They are not encoded or written. Account delete removes the private document on the web (`/api/account/delete`).

`annualLeaveEnabled` means this person has a paid allowance. Holiday and booking stay when it is off. `hasAnnualLeaveAllowance`, `leaveYearBounds`, `annualLeaveBalance`, `applyRemainingOverride`, and `snapLeaveDays` are the remaining, taken, pending, and leave-year results. Add User and Edit User use `ANNUAL_LEAVE_ALLOWANCE_COPY`. A typed remaining is stored as `annualLeaveYearAllowance` plus `annualLeaveYearAllowanceKey` from `applyRemainingOverride` (the pot is remaining + taken + pending for that `yearKey` only). Turning the allowance off does not delete that pot. A save that does not change remaining does not write those two fields.

## Warnings list order

Warnings lists reorder with `sortWarningsByDate` by each row’s coverage day (`dayKey`). The Oldest / Newest choice defaults to oldest and is stored per signed-in user on this device in UserDefaults (`warningsSortDirection:{userId}`), not in Firestore.

My notifications visibility and copy come from `visibleNotificationPreferenceKeys`, `notificationPreferenceIsVisible`, and `notificationPreferenceCopy`. The audience is the staff role plus `catalogue.projects` / `catalogue.smallWorks`, and optional `canManagePeople`, `canManageClients`, and `canManageMaterials`. The screen lists only the keys those functions return, with that copy. Stored values still come from `parseUserNotificationPreferences`. A toggle writes one dotted `notificationPreferences.{key}` through `userNotificationPreferenceFieldPatch` and does not replace the map. A key the account cannot see is not written. Inbox destinations stay `notificationDestination`, delivery stays `notificationPreferenceAllowsDelivery`, and a toggle does not widen who receives a job, booking, or warning (`receivesJobNotification` stays the fan-out).

Device pushes are only `notificationDeliversDevicePush`, the in-app bell is `unreadNotificationBadgeCount` on the rows the centre already lists, and `NOTIFICATION_ICON_BADGE_CLEARS_ON_FOREGROUND` clears the home-screen icon when the app becomes active without clearing that in-app number. A timesheet submission reminder is one inbox row plus the FCM alert, with no second local banner for that id. The centre queries `organizations/{orgId}/notifications` where `userId` is the signed-in user, keeps a row only when `inboxNotificationVisibleToUser` says so, and orders that list with `compareInboxNotificationsByCreatedAt`.

## Material order delivery

Order required delivery and quote omission come from `defaultMaterialDeliveryRequiredAt`, `defaultMaterialDeliveryDayKey`, `materialDeliveryInstant`, `materialOrderIncludesDeliveryRequired`, and `formatMaterialDeliveryRequired`: Send opens on tomorrow 08:00 Europe/London, or next Monday 08:00 on Saturday or Sunday, the user can change the day and time, orders write `deliveryRequiredAt` and include that instant on the email, and quotes write neither a day nor a time (`materialsDate` stays the list day). A successful wholesaler email is shown as Order placed or Quote sent even when the send-record write fails.

A new material line writes inbox type `material_order_placed`, which `notificationDeliversDevicePush` pushes and `notificationPreferenceKeyForType` maps to `materialOrderPlaced`. The older iOS `material_added` rows still parse, but the script has no push, toggle, or destination for them. The inbox writes run after the sheet closes; the line itself is saved first.

Recipients come from `materialOrderRecipients`: the active, non-operative accounts that are the managers assigned to that project or small works (`managerIds`, matched to accounts by id or by the managers row's email), never the person who added the line. Admins are not added unless they are one of the job's managers. Until the packed script exports that function, iOS keeps its previous recipients (every admin plus the job's managers).

Quote and order history is part of every job's Materials for admins and managers on both apps, with no Wholesalers toggle, and is never shown in operative mode. Both apps decide that with `canViewMaterialOrderHistory`. Both apps write the same `materialSendRecords` document (`id`, `projectId`, `requestType` `Order`/`Quote`, `sentAt`, `sentBy`, `recipients`, `lines`, `materialsDate`, `deliveryRequiredAt` on orders), and both list every record for the job, newest first. Firestore `canReadMaterialSendHistory` (web repo) allows every admin and manager outside operative mode, with no Wholesalers toggle.

The WhatsApp order message, the wa.me number, and the landline refusal come from `materialWhatsAppRows` (one row per recipient: `recipientId`, `message`, `ok`, `digits`, `reason`, `url`), called through `CanonicalBusinessEngine.objectRows` by `MaterialWhatsAppRulebook`. Swift builds no message text. Send via WhatsApp stays hidden until the packed script exports that function. A wholesaler contact's mobile is `contacts[].phone` (string or null), read and written on every save so an iOS edit keeps a number saved on web.

## User Timesheets scope

`canReviewUserTimesheets` and `seesEveryUserTimesheet` decide the role. Whose timesheets a viewer sees comes from `userTimesheetSubjects` (viewer id, `formerUserIds`, same-email ids, and role; each member's `email`, `isActive`, role, `assignedManagerUserIds`, `assignedManagerUserId`, `hasNoLineManager`), called through `CanonicalBusinessEngine.objectRows` by `UserTimesheetAccessRulebook`. `UserStore.userTimesheetSubjectUsers` is the one list the hub, User Timesheets, and its counts use. A manager keeps the screen while the profile or this organisation's roster is still loading. Until the packed script exports `userTimesheetSubjects`, the previous Swift filters stay, including the operative-mode requirement on a manager's reports.

## Dismissed warnings

`CanonicalBusinessEngine.qualificationDismissKey(operativeId:qualificationId:expiryDayKey:)` is the id both apps store a dismissed qualification warning under (`qual|operative|qualification|expiryDay`), and `withoutDismissedQualificationRows` drops only expired rows whose key is dismissed. `qualificationExpiryRows` already returns `dismissKey` on each row. The warnings screen shows Dismiss only when `daysUntilExpiry` is negative. That write is `organizations/{orgId}/dismissedWarnings/{dismissKey}` (`kind`, `dismissKey`, `operativeId`, `qualificationId`, `expiryDayKey`, `dismissedAt`, `dismissedByUserId`). The next warning read loads that collection and passes the ids into `withoutDismissedQualificationRows`. Upcoming expiry rows have no Dismiss button.

## Agent windows

A window that only has this repo may change SwiftUI and data loading. Shared results come from `CanonicalBusinessEngine`. Do not edit `canonical-business.js` by hand, and do not add a second calculator for a rule the script already has. A new shared rule is added in `project-planner-web/lib/canonical`, the script is rebuilt, and both copies are committed.

A window that only has the web repo may change `lib/canonical`. `npm run build:canonical` writes this app's script only when this checkout is at `../project-planner-ios`. If it is not, the file to commit here is the generated `lib/canonical/dist/canonical-business.js` from that web change.

A workspace with both repositories changes the TypeScript, rebuilds, and commits both generated scripts in the same phase.

The full description of what is shared and how a switch works is `docs/CANONICAL_ARCHITECTURE.md` in `project-planner-web`.
