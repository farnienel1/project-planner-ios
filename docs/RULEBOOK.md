# Project Planner Rulebook

Version: 1.18.0
Updated: 2026-11-03

This is the one rulebook for every Project Planner platform: web, iOS and (later) Android. It is written platform-neutral. Each rule names the shared function in `lib/canonical` that implements it; platforms call that function (web `@/lib/canonical`, iOS `CanonicalBusinessEngine`, Android the same packed script) and never keep a second copy.

**Where it lives.** The canonical copy is `docs/RULEBOOK.md` in `project-planner-web`. iOS keeps a byte-identical mirror at `docs/RULEBOOK.md`; the packed script carries this file's version and sha256 (`rulebookStamp()`), so a platform can prove at test time that its mirror matches the rules it runs. Never edit a mirror by hand. See "How the rulebook changes" at the end.

---

## 1. Data, sync and source of truth

- **Firebase is the single source of truth** for shared data. No shared data is kept only on a device or in a browser. Device storage is a cache or a per-device preference only.
- **Identical field names, types, defaults and enums** on every platform. Where platforms differed, the web schema wins. Shapes are listed in `ORGANIZATION_DOCUMENT_FIELDS`, `USER_DOCUMENT_FIELDS` and `OPERATIONAL_COLLECTION_PATHS`, all three in the packed script.
- **Live screens use real-time listeners.** A screen showing shared data holds a Firestore snapshot listener for it while it is open, so a save on one platform appears on the other without a refresh, a restart or a pull-to-refresh. The list is `LIVE_COLLECTIONS` (`liveCollection(id)`, `screenMustListen(id)`; an id not listed is live). Listeners are scoped to the open organisation, removed when the organisation changes or the user signs out, and never publish another company's rows. A cache may give the first paint; it is never the only read, and a time-to-live cache never stands in for a listener. The roster is `users` where `organizationId` is the open organisation; a member linked only through a membership, `userEmails` or a staff link is not in that listener and refreshes on the next full load (accepted). **Anchored people** (1.11.0, `rosterMembersForOrganization`): every key of `organizations/{orgId}.members`, the creator, and the signed-in user when listed are always on the roster, read by id when their users document names another company (the security rules let a co-member read them, `anchoredInCallerCompany`); their level in this organisation is `organizationLevelFor` — their users flags only when that document's `organizationId` is this organisation, else their membership here, else the `members` role, and the creator is always the super admin. An anchored person leaves the roster only when their users document is confirmed missing or they are removed from `members`; a denied read or a listener snapshot never removes them, and no device permanently hides anyone because a read was denied.

- **Never re-save what you didn't change.** A write happens only because the user changed that record in that action, or because the device replays such a queued action (`syncWriteAllowed(trigger)`: `userAction` and `offlineReplay` only, from `SYNC_WRITE_TRIGGERS`). Launch, return to the foreground, reconnect, a background sync, a pull-to-refresh and a listener snapshot never write records; the only exceptions are writes of a field the device itself owns (the signed-in user's `lastSeenAt`, this device's push token), seeding a starter library that is missing (`starterCollectionShouldSeed`, `missingStarterQualificationCodes`: creates only documents that do not exist) and, from 1.10.0, the idempotent key migrations in `IDEMPOTENT_MIGRATION_WRITES` (`syncWriteAllowed(trigger, migration)`): `warningResolutionMigrationWrites` writes a resolution stored under an older warning key to its shared key only when the shared key is not resolved yet, changes no data and gives the same result however often or wherever it runs, so it may run from a warnings scan or listener. Names recovered for display (job types from live jobs, `mergeJobTypeCatalogues`) are shown, never written — on load or by a later save: a job type save is the stored list plus the user's explicit adds and removes only (`jobTypesChangeWriteFields(stored, { add, remove })`, 1.10.0); a recovered name is saved only when the user adds it. A save writes only the records the user changed (`recordsToSave(records, changedIds)`) — saving one project never saves the others — and each as a partial update of its changed fields. An edit of a document that no longer exists is refused, never re-created (`editOfMissingDocumentIsRefused({ isCreate, exists, code })`): edits use an update that fails on a missing document, never a set or merge-set, and the app drops its local row and shows `EDIT_OF_MISSING_DOCUMENT_MESSAGE` ("This was deleted on another device."). A refused offline replay is final under `replayRefusedIsFinal` (`bookingReplayRefusedIsFinal` is the booking form, §2).
- **Bounded downloads.** Booking listeners start at `bookingLoadStart`: the earlier of this week's Monday and the warning window start, filtered on the booking `date`. A screen showing an older day moves the start earlier (never later); history screens ask for the full archive. The notification inbox loads the newest 150 rows for the signed-in user (`createdAt` descending).
- **Document readers.** A stored document is read into the shared rules only through its rulebook reader, never an app-level parser: bookings `parseBookingDocument`, manager site bookings `parseManagerSiteBookingDocument`, annual leave `parseHolidayDocument` / `parseHolidayDocuments` (§9), job documents `parseJobDocument` (`parseProjectDocument` for `projects`, `parseSmallWorkDocument` for `smallWorks`) and the job list `workDocuments`, subcontractor bookings `parseSubcontractorBookingDocument`, timesheet price work and expense entries `parseTimesheetEntries` (§8), deadline programmes `parseDeadlineDocument` / `parseDeadlineItem` and `settings/deadlineAssignments` `parseDeadlineAssignments` / `deadlineAssignedProjectIds`, the operations collections (job material lines `parseMaterialLineDocument` / `parseMaterialListDocuments`, `materialCatalogue` `parseMaterialCatalogueDocument`, `materialSendRecords` `parseMaterialSendRecordDocument`, `wholesalers` `parseWholesalerDocument`, `siteAudits` `parseSiteAuditDocument`, `tasks` `parseTaskDocument`, `settings/jobTypes` `parseJobTypesDocument` / `coerceJobTypeList` / `canonicalJobTypeName`, `settings/tradeTypeInventory` `parseTradeTypeInventory`, the `operativeProfiles` pay mirror `parseOperativeProfileDocument`, the private pay profile `payProfiles` `parsePayProfileDocument` (1.13.0, §8)), the record collections (health & safety `parseHealthSafetyDocument`, variations `parseVariationDocument` and `variationTrackers` `parseVariationTrackerDocument`, inbox rows `parseNotificationDocument` (§13), `warningResolutions` `parseWarningResolutionDocument` / `warningResolutionRecords` (§5)), the roster fold `rosterPeople`, the people collections (`parseUserDocument` for `users/{uid}`, `parseOperativeDocument` for `operatives`, `parseManagerDocument` for `managers`, `parsePayRateHistoryDocument` / `parsePayRateHistoryDocuments` for `operativeDayRateHistory`, `parseClientDocument`, `parseSubcontractorDocument`, `parseSkillDocument`), and organisation memberships `parseOrgMembershipDocument` (§14, 1.10.0), and the organisation settings parsers (`parseCompanyDetails`, `parseOrganizationName`, `resolveOrganizationCurrency`, `parseWarningDetection`, `parseMaterialCutOff`, `parseUserNotificationPreferences`, `parseAnnualLeaveDefaults`). A reader turns stored dates into organisation-zone day keys (and epoch milliseconds), keeps ids in their stored case and uses the document id as the record id — a stored `id` field never replaces it and an id that is not a UUID is kept. Readers accept a Firestore Timestamp, `{seconds, nanoseconds}`, a Date, epoch ms or an ISO string for an instant, true/false/1/0/"yes"/"no" for a flag, and a numeric string for a number (`documentInstantMs`, `documentBool`, `documentNumber`). An array row stored without an id (a subcontractor or wholesaler contact, a task item, a site-audit item, a variation line, a timesheet entry) gets a derived id — `derivedRowId` of the parent document id, the array, the position and the row's content (`subcontractorContactId`, `wholesalerContactId`, `variationLineId`, `timesheetEntryId`) — the same on every platform and read, never random; the next save writes it. A job naming a client with no client id gets `jobClientId(jobDocId, clientName)`. A stored organisation reference may be an id, a path (`organizations/{id}`) or a DocumentReference; readers return the id (`documentOrganizationId`). `users/{uid}.organizationId` is written on create only (`userProfileWriteFields`); switching organisation never rewrites it (§14). `parseUserDocument` without the organisation's `annualLeaveDefaults` marks `annualLeaveDefaultsPending`: the app re-parses the user when the organisation document arrives and never saves those figures. Status words are one vocabulary per collection: materials `normalizeMaterialWorkflowStatus` (`draft`, `sentForQuote`, `ordered`), tasks `normalizeProjectTaskStatus` (`To Do`, `In Progress`, `Completed`), toolbox issues `normalizeHSIssueStatus` (`awaiting`, `scheduled`, `complete`, stored `completed`), signatures `normalizeHSSignatureStatus`, variations `normalizeVariationStatus`; an unknown word reads as the first value and never drops the row. **Known gaps:** none — every shared collection has a rulebook reader.
- **Cross-platform contract** (1.10.0). `lib/canonical/cross-platform-contract.json` holds, for every shared collection in `LIVE_COLLECTIONS` that has a reader, a document as web writes it, a document as iOS writes it, and what the reader returns for each (`readCrossPlatformSample(reader, docId, data, { timeZone })`; collections without a reader are `CONTRACT_NO_READER` in `crossPlatformContract.samples.ts`). It is packed and mirrored like the parity fixture (iOS `ProjectPlannerTests/CrossPlatformContract.json`; its sha256 is `crossPlatformContractSha256` in the manifest). Web `crossPlatformContract.test.ts` and iOS `CrossPlatformContractTests` read every sample through the packed readers and compare with `expected`, and each checks its own writers still produce its samples. A change to what an app writes changes the contract in the same change.
- **Writes carry metadata.** Every write to a shared document includes `updatedAt` (server timestamp), `updatedBy` (signed-in user id) and `updatedFrom` (`web` | `ios` | `android`) — `writeMetadataFields(uid, platform)`; each app adds its SDK server timestamp. Security rules never reject a write only because these are missing (older app builds). **Exception:** a booking tombstone (§2) carries only its own fields (`BOOKING_TOMBSTONE_FIELDS`) and no write metadata.
- **Partial writes only.** A save writes the fields it changed (dotted partial update) — `documentWriteFields(before, next)` → `{ set, remove }`, and for the people collections `userProfileWriteFields`, `operativeRowWriteFields`, `managerRowWriteFields`, `clientWriteFields` and `subcontractorWriteFields`: a `null` removes a field only when the stored copy has one, line manager ids and `hasNoLineManager`, pay basis and both rates, and employment type and its transition are each written together, and `id` / `createdAt` / `organizationId` are never rewritten. For the work collections: jobs `jobWriteFields` (manager ids, the address lines and the map pin each written together), edits of an existing booking `bookingUpdateWriteFields` of a manager site booking `managerSiteBookingUpdateWriteFields` (1.9.0; the slot with its clock times and break, and the location kind with its id or custom name, each written together) and of a subcontractor booking `subcontractorBookingWriteFields` (the slot with its clock times, and the firm contacts with their names, written together; `bookedBy` is never rewritten; an edit of a booking whose document is gone writes nothing and is refused, never turned into a create), a new subcontractor booking `subcontractorBookingCreateFields` (document id = its `id` field, status Confirmed when not given, `isBreakRemoved`, `bookedContactIds` and `bookedOperativeNames` always written), and one job's deadline assignees `deadlineAssignmentWriteFields` (a field-path partial update of `projects.{KEY}`, the document created only when missing, `deadlineProjectKey` = the job id upper-cased as both apps have always stored it, `deadlinesDocumentId`). For the operations and record collections (1.8.0): material lines `materialLineFields` + `materialLineWriteFields` (`date` is organisation-zone midnight of the materials day and `dayKey` is stored with it; owner fields `addedBy` / `addedByUserId` / `addedAt` are create-only; a send moves status with `materialSendStatusWriteFields`, never ordered → sent for quote), catalogue items `materialCatalogueItemWriteFields`, wholesalers `wholesalerWriteFields` (contacts with the primary contact), site audits `siteAuditWriteFields` (`createdAt` and author never rewritten; items laid over their stored rows with `mergeStoredRows`), tasks `taskFields` + `taskWriteFields` (never a whole-task `setData`), variations `variationWriteFields` and renumbering `variationRenumberWriteFields` (only the sequence and, when the number changes, the number with one appended history entry), the `operativeProfiles` mirror `operativeProfileWriteFields`, `settings/jobTypes` `jobTypesWriteFields` (the `jobTypes` field only; empty only when the user removed every stored name, `options.removed`), `settings/tradeTypeInventory` `tradeTypeInventoryWriteFields` (adds, never removes), send records `materialSendRecordCreateFields` (written once), inbox rows `notificationReadWriteFields` (`isRead` only). 1.9.0: `variationTrackers/{parentId}` `variationTrackerWriteFields(stored, action)` (enable, disable, lock, unlock, mode, renumbered — only that action's fields; enabling an existing tracker keeps its mode, prefix, padding and version), `settings/variationTrades` `parseVariationTrades` / `variationTradesWriteFields` (only the trades added or removed in that action), a variation settings log `settings/variations_{parentId}` `variationLogItems` / `parseVariationLogDocument` / `variationLogWriteFields` (an entry stored without an id gets `variationLogItemId`, a `derivedRowId`, and the next save writes it; one entry is laid over its stored entry, others are never touched). While `annualLeaveDefaultsPending`, a `users/{uid}` save leaves out `annualLeavePendingOmitFields(user, edited)`. Health & safety: whole-list saves go through `healthSafetyDocumentWriteFields` (rows laid over their stored rows by id; 1.16.1: a blank or missing `fileURL` / `fileName` (`HEALTH_SAFETY_FILE_FIELDS`) never overwrites a stored non-blank one, and two copies of the same rows — the job's nested copy and the settings document — are read as one list by `mergeHealthSafetyRowCopies`, keeping the copy that has a `fileURL`; an upload stores a download URL only, never a `gs://` address, an empty list replaces a stored one only when the user removed every stored row in that save, `options.removedIds`; `signatureRecords` never touched); removing a recipient or an issue removes those signatures with `healthSafetySignatureRemovalWrites` (field-path deletes of the matching `signatureRecords` entries and the `signatures` array without them, in the same update); a signature is `healthSafetySignatureWriteFields` — a field-path update of `signatureRecords.{issueId}__{userId}` (`healthSafetySignatureKey`) plus an `arrayUnion` of the row onto `signatures` for older builds — so two people signing at once never lose a signature, and readers fold both sources (`foldHealthSafetySignatures`, a signed copy always wins). The skills catalogue is saved with `skillsCatalogueWrites` and the material catalogue with `materialCatalogueWrites`: never delete-all and rewrite, only changed items are written, and an empty or failed load never deletes an item. **Create shapes** (1.9.0) for the documents written whole once: `invitations/{id}` `invitationCreateFields` (never UTR or VAT; marking used is `invitationUsedWriteFields`), `organizations/{orgId}` `organizationCreateFields` (billing and subscription at create only), `users/{uid}/private/taxIds` `taxIdsDocumentFields` (its only fields, written whole), inbox rows `notificationCreateFields` (created once; a row that already exists — a dedupe hit — is never rewritten, so its read state is never reset). It never rewrites a whole document from a possibly stale copy, and never deletes a field just because the local copy lacks it. A dotted key (`settings.currencyCode`) is only used with a partial update, never with a merge-set, where it would become a literal field name. Edits to an existing document — annual leave (`holidayBookings`) and timesheet drafts included — are partial updates.
- **Document ids keep their stored case.** Ids are written exactly as created (iOS `UUID.uuidString` is upper case; web ids may be lower case) and stored keys are never rewritten. Comparisons ignore case: `normalizeDocumentId` (trimmed, lower case) is used for warning resolution keys, accepted clash pairs and timesheet entry-review lookups (`resolvedWarningKeys`, `approvedWarningKeys`, `isWarningActive`, `isClashApproved`, `isClashAccepted`, `timesheetEntryDecision`).
- **Job keys.** A record that belongs to a job (material lines, send records, site audits, tasks, variations, subcontractor bookings, bookings, offline caches) stores the job's document id exactly as stored in its `projectId` / `parentId` field — never re-formatted through a UUID type, so a non-UUID or lower-case job id works on every platform. Settings documents keyed by a job use the job id upper-cased (`deadlineProjectKey`: `deadlinesDocumentId`, `healthSafetyDocumentId` → `settings/healthSafety_{projects|smallWorks}_{KEY}`; `healthSafetyDocumentIds` also lists the stored-case id older web builds wrote, read and merged). A key read back from a store, a map or a cache is mapped to the job with `storedJobIdForKey(key, jobIds)` (without case); `deadlineAssignedProjectIds(data, personIds, jobIds)` returns stored job ids.
- **Shared calculations run on each device from one packed script.** Warnings, overtime, timesheet figures, Daily Overview and pay are calculated on each device by the same packed rulebook script, not re-implemented per platform. Moving a calculation to the server (Cloud Functions) is a separate decision; until then the function named here is the exact specification (inputs, edge cases, rounding) and is locked by tests in `lib/canonical/canonical.test.ts` and `lib/canonical/parity-fixture.json`.
- **One business time zone per organisation**, from `organizations/{orgId}.countryCode` (`organizationTimeZone`): GB → Europe/London; missing or unknown → Europe/London. Every day key, warning window, payment run, timesheet day, cut-off clock and effective date uses this zone, with BST/GMT handled by the zone rules. Never the phone or browser zone. A day key's instant is the first instant of that calendar day in the zone (`dateFromDayKeyInZone`, `midnightInZone`, `addDaysInZone`), worked out from the zone offset at that local midnight — never from UTC noon, which in a zone at UTC+12 or later (Pacific/Auckland, Pacific/Chatham, Pacific/Kiritimati) is already the next local day (1.12.0: every New Zealand day key was one day out, so a Friday paid at Saturday rules, Mon–Fri leave counted 2 days and rate changes started a day late).
- **The week starts on Monday** and runs Monday–Sunday for every organisation. Monday–Friday are working days; Saturday and Sunday count only where a setting says so (for example "Include weekends in unbooked labour"). This is fixed, not an organisation setting.
- **Security rules enforce permissions on the server.** Firestore rules enforce role permissions, approvals and who may change organisation settings. Hiding a control in an app is never the only guard.

## 2. Offline rules

- **Web:** online only. No offline editing.
- **iOS and Android:** offline mode with restrictions. The logic is kept separate from screens so Android can reuse the same rules.

The table below is `OFFLINE_ACTIONS` (stable action ids, e.g. `booking.create`, `users.pay_rate`, `view.warnings`), read with `offlineAvailability(actionId)` → `allowedOffline` | `onlineOnly` | `readOnlyOffline`; an unknown id is online only. The messages are `OFFLINE_PENDING_SYNC_LABEL`, `OFFLINE_ONLINE_ONLY_MESSAGE` and `offlineLastUpdatedLabel(instant, timeZone)`.

**Allowed offline** (queued on the device, pushed automatically when the connection returns; each queued item shows **"Pending sync"** until the server confirms it):
- Create, edit and cancel bookings (projects and small works). Deleting a booking is online only.
- Annual leave requests.
- The user's own personal profile fields.
- The user's own notification toggles.

**Online only** (controls disabled offline with the message **"Connect to the internet to change this"**):
- All organisation settings: company details, currency, working hours and overtime (including scheduled changes), warning settings (including excluded users), payment runs, material order cut-off and schedule options (including custom items).
- All Manage Users changes: role, line manager, employment status, day/hourly rate and effective dates, exclusions, inactive flag, invites.
- Approvals: annual leave approval, timesheet signing, clash approvals.
- Account actions: sign-in, password changes, switching organisation.
- Deleting a booking (the delete and its tombstone are never queued).

**Read-only offline.** Daily Overview, warnings, weekly reports and My Schedule show the last synced data, labelled "Last updated [date/time]" in the organisation zone (`offlineLastUpdatedLabel`, e.g. "Last updated 24 Oct 2026, 14:05"), and are never recalculated from unsynced local changes.

**Conflicts.**
- Last write wins, by server timestamp.
- A booking cancelled or deleted on another device cannot be brought back by an offline edit. Deleting a booking (`bookings`, `managerSiteBookings` or, from 1.10.0, `subcontractorBookings`) writes a tombstone at `organizations/{orgId}/deletedBookings/{bookingId}` in the same batch (`bookingTombstonePath`, `bookingTombstoneWriteFields`; the app adds the server `deletedAt`). A tombstone carries only `bookingId`, `collection`, `deletedAt`, `deletedBy` and `deletedFrom` — no write metadata. Security rules refuse any later create or update of that booking id. Who may create, edit, cancel or delete a booking — labour, manager site or subcontractor — is `canWriteBooking` / `canDeleteBooking` (1.10.0, owner decision; §16): admins every booking; managers the bookings on a project or small works they manage (and their own office / working-from-home / site-survey bookings); operatives never. Apps show Delete to exactly those people. Only they can move a booking off `Cancelled`. **Deleting a person or a job** removes only their bookings dated today or later in the organisation zone (`bookingsToRemoveOnOperativeDelete` — every id of the person, never a name — and for a job `jobDeleteBookingRemovals` (1.10.0): its labour bookings, its subcontractor bookings and the manager site bookings at the job), each with its tombstone in the same batch; past bookings stay as history with their stored names (a job's show `ORPHAN_BOOKING_LABEL`); deactivating or archiving a person removes nothing. No platform deletes all of a person's bookings or deletes one without its tombstone. A refused replay is final (`bookingReplayRefusedIsFinal({ code, isCreate })`): permission-denied always, and not-found when the queued item edits or cancels a booking (`isCreate` false), so an edit of a booking deleted elsewhere is never turned into a create (the general rule for every collection is `replayRefusedIsFinal` / `editOfMissingDocumentIsRefused`, §1). The device removes the queued item, drops the local row and shows `BOOKING_REPLAY_REFUSED_MESSAGE` ("This booking was cancelled or deleted on another device").
- Double bookings created offline are not blocked; warnings pick them up after sync.
- Queued writes to online-only areas are refused by the security rules when they replay.

## 3. The data flow (in order)

1. **Scheduling** (projects and small works) books people onto days.
2. **Daily Overview** is a snapshot of each day: who is booked (and on what), who is unbooked, who is on annual leave. It is driven by bookings, annual leave and organisation settings.
3. **Warnings** consume the same day data plus warning settings and organisation settings.
4. **Weekly Report** is an extraction of Daily Overview and warnings for a chosen date range.
5. **Timesheets** are fed by bookings, annual leave, working hours/overtime rules, payment runs and each person's effective-dated employment profile.
6. **My Schedule** is each person's own view of their bookings and annual leave.

A change upstream flows to everything downstream on every platform.

## 4. Organisation settings

All organisation settings live on `organizations/{orgId}` and are identical on every platform. They are online-only edits, saved only when the user presses **Save**, and a save on one platform appears on the other through the live listener. Settings screens keep an unsaved draft and only refresh it from the server while the draft is unchanged. A value that looks like the factory default on the server is still the server value — no platform re-saves its own cached copy over it.

### 4.1 Company details
Flat fields on the organisation document: `name`, `officeAddressLine1`, `officeAddressLine2`, `officeCity`, `officeCounty`, `officePostcode`, `countryCode` (two letters, GB when missing), `documentAbbreviation` (1–3 characters), `companyLogoURL`, `defaultLatitude`, `defaultLongitude`, `bankHolidayRegionId` (`parseCompanyDetails`, `companyDetailsWriteFields` → `{ set, remove }`, `companyDetailsValidationError`). A legacy nested `officeAddress` map is read only as a fallback and every save deletes it. Blank optional fields are deleted, never saved as empty text; with no office, all address fields are deleted. A missing map pin leaves the saved pin alone. A blank name is never saved (`organizationNameWriteFields`). The country sets the business time zone and the default currency.

**Country change asks for the bank-holiday region.** Regions are one shared list, `BANK_HOLIDAY_REGIONS` (`{ id, title, countryCode, subdivisionCodes? }`; ids are stored and never renamed: `GB-ENG-WLS`, `GB-SCT`, `GB-NIR`, `GB`, `IE`, `US`, …; the older web id `GB-ENG` reads as `GB-ENG-WLS`, `normalizeBankHolidayRegionId`). A company's pickers offer only `bankHolidayRegionsForCountry(countryCode)`; the default is `defaultBankHolidayRegionForCountry` (GB → `GB-ENG-WLS`, `DEFAULT_BANK_HOLIDAY_REGION_ID`; a country with one region → that region; none listed → null). When Company Details changes the country and the saved `bankHolidayRegionId` does not belong to the new country, `companyDetailsRegionPrompt(previous, next)` is `{ required: true, choices, defaultRegionId, message }` and the save is refused (`companyDetailsValidationError`, "Choose the bank holidays for {country}.") until a region from `choices` is picked; the region picker is pre-selected with the default. The same country never asks again. `companyDetailsWriteFields` writes the new `countryCode` and `bankHolidayRegionId` (and `settings.bankHolidayRegionId`) in one partial update; a new country with no listed regions removes the old region. With no saved region, the company's country default applies (`parseCompanyDetails`).

**Countries at launch** (1.13.0, owner decisions round 4, Q6): every country picker — Company details and organisation setup — offers only `LAUNCH_COUNTRY_CODES` (GB, IE), through `launchCountryOptions(stored)`. A company that already stores another country keeps it: the picker lists it as well, so it is shown and saved unchanged. Other countries come later.

### 4.2 Currency
One organisation currency (`resolveOrganizationCurrency`), chosen from `CURRENCY_OPTIONS` (GBP, EUR, USD, CAD, AUD, NZD, SEK, NOK, DKK, PLN, AED). Until one is saved it defaults from the country (`defaultCurrencyForCountry`; GBP when unknown). A save writes `currencyCode`, `currency` and `settings.currencyCode` as one partial update (`organizationCurrencyWriteFields`). Older iOS builds also wrote a top-level field literally named `settings.currencyCode`; `resolveOrganizationCurrency` reads it last, so it is harmless and is left in place (an optional one-off clean-up may delete it with `FieldPath(['settings.currencyCode'])`). Every money figure — timesheets, rates, invoices, weekly report, exports, PDFs — is shown with `formatMoney(amount, currency)`. Subscription prices are billing, not organisation money.

### 4.3 Working hours and overtime
`payrollTimePolicy`: standard day window, break, paid hours, weekday overtime multiplier, Saturday and Sunday rules, paid break. Limits for every platform (`validatePayrollTimePolicy`): paid hours 1–12, break 0–120 minutes, multipliers 1–3. The standard day and its AM/PM halves are `halfDayWindows`; no platform computes a midpoint itself.
Limits also cover weekend "counts as" hours (1–12) — `PAYROLL_POLICY_LIMITS`. **On read** (1.12.0) `parsePayrollPolicy` puts every stored number into those limits: a missing, blank or non-numeric value is the default; paid hours of 0 or less are the default (8); anything else is clamped (paid hours 1–12, break 0–120 minutes, every multiplier 1–3; a weekend "counts as" 0 is kept, §5). A bad stored value can no longer reach pay.

A change is either applied from today or **scheduled** from a chosen date after today (`payrollTimePolicyScheduled { policy, effectiveFrom }`, day keys in the organisation zone). The rules in effect on a day (`effectivePayrollTimePolicy(org, dayKey)`, `payrollTimePolicyTimeline`) are: the scheduled change once its day has arrived (even before any app promotes it); before `payrollTimePolicyEffectiveFrom`, `payrollTimePolicyPrior`; otherwise `payrollTimePolicy`.
- **Apply from today** (`payrollTimePolicyApplyNowWriteFields`) saves the new rules, keeps yesterday's rules as the prior, sets today as the start, removes a scheduled change that is already due and keeps a future one.
- **Schedule** (`payrollTimePolicyScheduleWriteFields`) replaces any pending change; a due change is promoted first so it is not lost.
- **Cancel** (`payrollTimePolicyCancelScheduleWriteFields`) removes a pending change.
No save ever cancels a scheduled change it was not asked to cancel. Every screen that prices or labels a day — timesheets, weekly report, Daily Overview, warnings, booking pickers and invoices — uses the policy in effect on that day in the organisation zone (`effectivePayrollTimePolicy`), never today's rules for another day.

The working week is `WORKING_WEEK` (`isStandardWorkingWeekday`): Monday–Sunday, Monday–Friday working.

**Weekend bookings** (1.13.0, owner decisions round 4, Q2). Saturday and Sunday bookings are **custom hours only** on every platform, whatever the organisation's weekend setup: no FULL DAY, AM or PM. Every booking picker offers `allowedTimeSlotsOnDay(dayKey, policy, timeZone)` — CUSTOM on Saturday and Sunday (`WEEKEND_TIME_SLOTS`), FULL DAY, AM, PM and CUSTOM on weekdays (`timeSlotAllowedOnDay`). When the day's rule is a set window ("standard window + overtime"), the custom-hours editor opens prefilled with that window (`weekendCustomHoursDefault(policy, isoWeekday)` → `{ start, end }`, e.g. 07:30–13:00; Sunday "same as Saturday" uses Saturday's); when the day pays every hour at one rate it is null and the editor opens with its usual times. The prefill is a convenience: the person changes it freely. Under every weekend picker the apps show `weekendBookingNote(policy, weekday)` — "Saturday is paid on the hours you enter: 07:30–13:00 counts as 8h, hours outside it at 2×. Change it in Working hours." or "Sunday is paid on the hours you enter, every hour at 2×. Change it in Working hours." (the day's own values). **A selection of several days** shows `weekendBookingNotes(policy, dayKeys, timeZone)` (1.17.0): with both Saturday and Sunday selected and the same rule on both (same window, counts-as hours and rate outside it, or both every hour at the same rate) one line, "Saturday/Sunday is paid on the hours you enter: …"; with different rules the Saturday line, then the Sunday line; with only one weekend day exactly that day's line; with no weekend day none. `policy` may be the organisation's policy state, so each day is read under the working hours in effect on that day (`effectivePayrollTimePolicy`). Each booked day keeps its own prefill (`weekendCustomHoursDefault` for that day); a picker that holds one time pair for the whole request opens it with the first selected Saturday's — never a computed midpoint. **The custom-hours pair follows the selection** (1.18.0, owner decision): a picker's one start/finish pair for the request is `customHoursPrefillForDays(policyOrState, dayKeys, timeZone)` → `{ start, end, kind }` — `kind` `weekend` (only Saturdays and Sundays: the first selected weekend day that has a set window, Saturdays first — so with Saturday every hour at N× and Sunday on a window, Sunday's window (`weekendCustomHoursDefault`); neither has a window, the editor's usual times, the standard day), `weekday` (only Monday–Friday: the organisation's standard day `halfDayWindows(policy).day` in effect on the first selected day), `none` (a refused weekday and weekend mix; the picker leaves the times alone), or null with no day. The moment the selection changes kind (weekend only ↔ weekday only) the picker sets start and finish to the new result; within the same kind it leaves them, so the person's own edit survives adding another day. A picker that keeps one pair per day uses the same function for that day. Pickers read the weekend rule, prefill and break warning under the working hours in effect on the booking day, not today's. **One request never mixes weekdays and weekend days**: every multi-day booking picker refuses it with `WEEKEND_WEEKDAY_MIX_MESSAGE` ("Weekends cannot be booked alongside Weekdays. Make your weekday booking first then weekend separately.", `bookingDaysMixWeekdayAndWeekend(dayKeys, timeZone)`); quick selections of several days skip Saturday and Sunday. Saturday and Sunday may be booked together whatever their rules. **Per-day hours for a weekend booking** (1.18.0, owner decision): every booking screen shows a Saturday or Sunday booking's hours as one row per selected day, `weekendBookingBreakdown(policyOrState, dayKeys, start, end, isBreakRemoved, timeZone)` → `{ dayKey, weekdayLabel, start, end, workedHours, countsAsHours, standardHours, overtimeHours, multiplier, paidHoursEquivalent, line }[]`, each priced only by the pay rule timesheets use (`payrollHoursResult`) under the working hours in effect on that day — Saturday and Sunday take no unpaid break off, as in pay. Example: Saturday window 07:30–14:00 counts as 8h, Sunday every hour at 2×, booked 07:30–14:00 → "Saturday 07:30–14:00 = 8h (counts as a full day)" and "Sunday 07:30–14:00 = 6.5h × 2 = 13h". Days with identical figures may be shown as one "Saturday/Sunday" row. These rows replace the weekday standard-day summary in every booking confirm step and hours breakdown for a weekend selection; no app computes weekend hours itself. Stored weekend FULL DAY / AM / PM bookings are never rewritten; they are shown as stored and paid as §8 says.

### 4.4 Annual leave settings
`annualLeaveDefaults { daysPerYear, startMonth, endMonth, carriesOver }` (defaults 25, 1, 12, false) and the bank-holiday region, saved together in one write. The region picker offers only the company country's regions (`bankHolidayRegionsForCountry`); the country is changed in Company details (§4.1). Allowance, the leave year and a one-year override are `annualLeaveBalance`. **A leave year is always 12 months** (1.12.0): it ends the month before it starts (`leaveYearEndMonth`: January → December, April → March). A save of the organisation defaults or of a person's leave year whose end month is not `leaveYearEndMonth(start)` is refused (`validateAnnualLeaveDefaults`, `validateLeaveYearMonths`, `LEAVE_YEAR_MONTHS_MESSAGE`); the pickers move the other month with the one chosen. A stored mismatch (saved before 1.12.0) reads as 12 months from its start month (`leaveYearBounds`), so no leave falls outside every year and no year runs 13 months. Changing the region never recounts or rewrites existing leave records: day counting (`leaveRecordDayKeys`, `annualLeaveBalance`) uses the region in effect when it runs. The start month for a chosen end month is `leaveYearStartMonth(endMonth)` (1.13.0; the inverse of `leaveYearEndMonth`) — no app computes it itself.

**Pro rata and carry-over** (1.13.0, owner decisions round 4, Q4). A person's start date is `users/{uid}.employmentStartDate` (a `YYYY-MM-DD` day key, set on Manage Users by whoever manages their leave; never the person, never the account's `createdAt`). The leave year they joined in is pro rata (`proRataLeaveAllowance`): days per year × the calendar days from the start date to the year's last day ÷ the days in that year, rounded up to the next half day; a year that ended before the start date gives 0, and a year that began on or after it gives the full allowance. `annualLeaveBalance` (`employmentStartDayKey`) reports `yearEntitlement` and `proRata`. Carry-over (when `carriesOver`) is the previous year's own allowance (pro rata in the year joined) less the leave taken in it, capped at the optional organisation setting `annualLeaveDefaults.maxCarryOverDays` (`parseMaxCarryOverDays`; null or missing = no cap — every organisation saved before 1.13.0 has none; the settings screen suggests `SUGGESTED_MAX_CARRY_OVER_DAYS` = 5 and saves only what the admin enters). Both apps write `maxCarryOverDays` with the rest of `annualLeaveDefaults` and never drop it.

### 4.5 Payment runs (the invoicing period)
Two modes (`invoicing.paymentRunMode`):
- **Set payment run date ranges** (`date_ranges`): two runs per month on fixed days, e.g. 1st–15th and 16th–last day. "16th–31st" means 16th to the last day of that month in 28, 29, 30 and 31-day months. Run 1 starts on the 1st and must end by the 27th so run 2 exists every month; run 2 starts the day after and ends on the 31st (`validateInvoicingSettings`, `PAYMENT_RUN_1_LAST_END_DAY`). A run is paid on its payment day: the first one on or after the run ends, otherwise that day next month (clamped to short months).
- **Recurring timeframe** (`recurring_timeframe`): a weekly work period (e.g. Monday–Sunday) paid in arrears on the first pay weekday after the period ends (e.g. the following Friday) — `paymentWeekdayAfterPeriodEnd`, shared with timesheet reminders.

The **active payment run** is the work period that contains today in the organisation zone (`invoicingPeriod`); if no date-range run contains today, the run with the latest end day. Its pay date is `paymentRunPayDate`. The summary shown to users is `activePaymentRunSummary(invoicing, now, timeZone)`: `{ start, end, payDate, label }`, e.g. "Mon 26 Oct – Sun 1 Nov · paid Fri 6 Nov", or `{ notConfigured: true }` when the organisation has no payment runs.

### 4.6 Warning settings
`warningDetection { detectClashes, clashLookaheadMode, clashLookaheadDays, includeWeekendsForUnbookedLabour, excludedUserIdsFromUnbookedWarnings }`, parsed by `parseWarningDetection`. See §5.

### 4.7 Material order cut-off
`settings.materialCutOff { materialOrderCutOff, materialCutOffHour, materialCutOffMinute, materialCutOffOnSaturday, materialCutOffOnSunday }` (`parseMaterialCutOff`, `resolveMaterialCutOffClock`). A missing hour defaults to 16:00; a saved 15:30 stays 15:30. A user's notification preferences never hold the clock.

### 4.8 Schedule options
`settings.myScheduleOptions { showOffice, showWorkingFromHome, showSiteSurvey, customItems[], customItemEnabled{name: bool} }`. Missing flags mean on. Every location picker offers exactly `enabledScheduleLocations(options)`. A save writes exactly the list on screen, with names de-duplicated ignoring case (`scheduleOptionsWriteFields`) — it never merges back a deleted item.

## 5. Warnings

Warnings refresh whenever bookings, leave, settings or users change, and when the day changes (midnight in the organisation zone, and when the app or tab returns to the foreground).

**Detection period** (`coverageWindow`):
- **Set number of days:** today through N calendar days including today (2 = today and tomorrow). N is a whole number 1–365; a missing, blank, non-numeric or below-1 value falls back to 7 and both the settings screen and the Warnings screen show the notice `warningLookaheadFallbackNotice(reason)` (`coverageWindow` → `fallbackReason`, `parseWarningDetection` → `clashLookaheadDaysFallback`, never saved) — never a silent failure.
- **Invoicing period:** every past, present and future day of the active payment run. Selecting it shows the **invoicing schedule summary** (`activePaymentRunSummary`); with no payment run configured the screen asks the user to set one up. The summary is hidden for the other two options.
- **Full week:** Monday–Friday of the current week, including days already past. Saturday and Sunday are added for unbooked labour only when "Include weekends in unbooked labour" is on.
- **Unbooked days** (`unbookedScanDays`): the window above; in Full week with include-weekends on it runs to Sunday. Saturday and Sunday are scanned only when include-weekends is on, in every mode. A weekend day whose "counts as" hours are 0 is still skipped by `unbookedLabourRows`.
- **Clash days** (`clashScanDays`): clashes follow the scan window. In Full week, a Saturday or Sunday of the current Monday–Sunday week is also checked when it has a booking. Set number of days and Invoicing period are calendar days, so their weekends are always checked. The include-weekends toggle never affects clashes.

**Warning types and severity:**
- **Booking clashes** — a person double-booked on the same date. Operative clashes are **High** (`operativeClashGroups`); manager/admin overlaps are **Medium** (`managerClashGroups`). Both group a person's bookings per day (the person is `bookingPersonKey` / the roster account, so former ids, same-email ids and catalogue rows are one person) by overlapping clock intervals; touching times do not clash, and A–B plus B–C is one cluster. **Overnight bookings** (1.13.0, owner decisions round 4, Q5): a booking whose finish is before its start crosses midnight, and its interval is the real clock time on its start day (`slotInterval`: 22:00–06:00 is 22:00 to 30:00). It also sits on the next morning (`overnightCarryInterval`), so it clashes with that day's bookings that start before it ends (a 05:00 start clashes with a night shift ending at 06:00; a 06:00 start only touches). Such a clash is listed on the later day; two overnight bookings on one night are one clash on their own day. The same applies to the timesheet overlap flags (`overlappingBookingIds`). Weekend bookings (custom hours only from 1.13.0, §4.3) clash on their clock hours; a stored weekend FULL DAY with no clock times occupies the standard day, an AM / PM its half. An operative cluster lists every booking id and one pair row per overlapping pair, each with its `clashPairKey` and `clashResolutionKey`. A clash can be **approved** and **un-approved** (online, managers and admins only): `clashApprovalWrites` writes `acceptedBookingClashes/{clashPairKey}` and `warningResolutions/{clashResolutionKey}` with status `approved` — the key is the booking-pair key for operative clashes and `mgr-clash-…` for manager clashes; approving an operative cluster writes every pair. Approving writes, and un-approving deletes, both documents (every pair of a cluster) in one batch (1.9.0), so one never exists without the other. A clash is approved when either document exists for it (`isClashApproved`); an operative cluster is approved when every pair is (`isClashGroupApproved`), so a third booking re-opens it. Only approvals count as approved: `approvedWarningKeys` (status `approved`) and `acceptedBookingClashes`; a dismissed clash is hidden but is not approved. Approved clashes are listed separately on the weekly report and no longer count as open. Whether any row still counts is `isWarningActive` over `resolvedWarningKeys` (approved and dismissed). Keys compare without case (§1). Resolutions are read live (a snapshot listener on `warningResolutions`) through `warningResolutionRecords`, which puts older iOS keys in their shared form (`sharedWarningResolutionKey`: `mgr-clash-{user}-{seconds}-{i}` → `mgr-clash-{user}-{YYYY-MM-DD}-{i}`, `materials-{projectId}-{seconds}` → `materials-{projectId}-{YYYY-MM-DD}`, organisation zone). The one-off legacy migration (D3) is `warningResolutionMigrationWrites({ docs, legacyKeyForms, resolvedByUserId, timeZone })`: the `warningResolutions` documents to write under the shared keys (approved beats dismissed; nothing when the shared key is already resolved; old documents are left in place); staff only, idempotent.
- **Unbooked labour (High)** — an operative not booked on a working day in the window (`unbookedLabourRows`). Skipped: excluded users (silently), inactive users, pending users who have not finished sign-up, days on approved annual leave, weekends unless included, anonymised deleted profiles (`listedCurrentLabourPeople`). Every id match in `unbookedLabourRows`, `unbookedLabourRowsOnDay` and `leaveCoverageRows` — leave to person, booking to person, former and same-email ids, exclusions — ignores case (`normalizeDocumentId`, §1); returned rows keep the ids as stored.
- **Low:** materials not ordered by the cut-off (`materialCutOffWarningRows`: once the organisation clock passes the cut-off, each job with an active booking tomorrow warns if tomorrow has no material lines or any line is not ordered — a line counts as ordered when its status is `ordered` or an order send record lists it (`materialLineCountsAsOrdered`); a Saturday or Sunday tomorrow only if that day's flag is on; key `materials-{projectId}-{YYYY-MM-DD}` for tomorrow); qualification expiry including already expired (`qualificationExpiryRows`); unverified accounts (`unverifiedOperativeRows`).

**Scope** (1.10.0, §17). A manager who does not see every job gets only the rows about the jobs they see and the people booked on them: `warningScopeFor(...)` → `WarningScope`, passed as `scope` to `unbookedLabourRows` / `unbookedLabourRowsOnDay`, `qualificationExpiryRows`, `unverifiedOperativeRows` and `materialCutOffWarningRows`. A viewer who cannot read every booking gets no unbooked-labour rows (a person missing from their bookings may be booked on a job they cannot see). Clashes and leave coverage are scoped by the bookings the rules let them read. Admins and managers with both job toggles: everything.

**Annual leave when booking** (1.16.0, owner rule). Every booking flow that lists double bookings before it saves also lists each (person, day) of the booking that falls on that person's annual leave: `bookingLeaveConflicts({ people, dayKeys, holidays, timeZone, timeSlot, workStartTime, workEndTime, day, roster })` → `{ personId, dayKey, kind: 'annual_leave', leaveId, leaveSlot: 'FULL DAY' | 'AM' | 'PM', status, label }`, one row per person-day. Approved leave conflicts when its window overlaps the booking: full-day leave with anything; AM leave with a booking that touches the AM half (`halfDayWindows`), PM likewise — AM leave and a PM booking never conflict; custom hours conflict with half-day leave when they overlap that half. Pending leave is listed too (`status: 'pending'`, `ANNUAL_LEAVE_REQUESTED_LABEL`, shown softer); rejected leave never. People match leave under every id they go by (`personIdSet`, their `userId` and operative ids), without case, from `parseHolidayDocument` / `labourHolidayInput` day keys. Leave rows are purple and read `ANNUAL_LEAVE_BOOKED_LABEL` ("Annual leave booked"); double bookings stay orange; the heading is `BOOKING_CONFLICTS_HEADING` ("Some selected days clash. Tick to confirm, or ✕ to drop that day."). Each row is ticked (book anyway) or ✕ (drop that day for that person), and the save waits until every row is one or the other — the same as a double booking. The warning after saving is still `leaveCoverageRows`.

**Excluded users** are a per-user, all-or-nothing exemption from unbooked-labour warnings, for people who are never bookable (office PAYE staff, directors). Temporarily unavailable operatives use the **inactive** flag instead.

Display order (Oldest/Newest) is a per-device preference (`sortWarningsByDate`).

## 6. Daily Overview

One entry per day listing booked people (with project or small work), unbooked people (`unbookedLabourRowsOnDay`) and people on approved annual leave. It respects the organisation working hours (`effectivePayrollTimePolicy`), the fixed working week, include-weekends, exclusions and active/inactive status. Standard and overtime hours are `workedHoursSplit`. A Saturday or Sunday booking shows the custom hours entered (1.13.0, §4.3); a stored weekend FULL DAY / AM / PM shows as stored. It is identical on every platform for the same day and viewer; a manager who does not see every job sees their jobs' people only, and unbooked people only when they read every booking (`warningScopeFor`, §5, §17).

## 7. Weekly Report

Generated live for any chosen date range from current bookings, Daily Overview, warnings and timesheets. Leave days in the range are `leaveDaysInRange(record, range, timeZone, nonWorkingDayKeys)` (1.9.0, on `leaveRecordDayKeys`; a half day counts 0.5) on every platform. Contents: hours, overtime, warnings including approved clashes, totals. A warning counts as open only while `isWarningActive` over `resolvedWarningKeys` (1.10.0): a dismissed clash is in neither the open warnings nor the approved clashes; approved clashes (`isClashApproved` / `isClashGroupApproved`) are listed separately. Reports are **not stored** and **never write** (1.10.0): a signed sheet with no `weeklyReportOverride` is summarised in memory for the report only — the report never writes anyone's timesheet (`syncWriteAllowed('weeklyReport')` is false). The people in the timesheet feed are `timesheetParticipant(user, day)` (§8). A report is produced and downloaded (PDF/XLSX/HTML or the share sheet) and that is all. Producing a report again for the same range reflects any changes made since.

## 8. Timesheets and employment profile

**Profile fields** on `users/{uid}`: employment status (`employmentType`: PAYE or self-employed), pay basis (`payBasis`: day or hourly), `dayRate`, `hourlyRate`. A rate save writes exactly one basis and removes the other; both apps show `PAY_BASIS_SAVE_NOTE` ("Pay is a day rate or an hourly rate, not both. Saving a day rate removes the hourly rate, and saving an hourly rate removes the day rate.") with `PAY_BASIS_DAY_HELP` / `PAY_BASIS_HOURLY_HELP` under the pay fields (1.11.0; iOS copy that said both rates are kept was wrong). A PAYE person's rate is kept for days they are self-employed and shown with `PAYE_RATE_NOT_USED_NOTE`. The same applies to roster rows: an `operatives` or `managers` row with `payBasis: hourly` is hourly (`parseOperativeDocument`, `parseManagerDocument`). `timesheetsEnabled` is still read and written (`defaultTimesheetsEnabled` when not stored) but, from 1.11.0, no longer decides who has a timesheet: only self-employed days do (below). Annual leave fields not stored on the user (`annualLeaveDaysPerYear`, `annualLeaveYearStartMonth`, `annualLeaveYearEndMonth`, `annualLeaveCarriesOver`) take the organisation `annualLeaveDefaults` (§4.4), never a platform constant (`parseUserDocument` with `annualLeaveDefaults`); a save never writes the default onto the user.

**Effective dating.** Status and rate are both effective-dated; a change asks when it takes effect. Status: `employmentTypeTransitionFrom` / `employmentTypeEffectiveAt` (`applyEmploymentTypeChange`, `employmentTypeOnDay`). Rate: `organizations/{orgId}/operativeDayRateHistory` rows `{ userId, operativeId, dayRate, payBasis, effectiveAt, createdAt }`, built by `payRateHistoryWriteFields`: `effectiveAt` is midnight of the effective day in the organisation zone (never London unless that is the organisation's zone, never the device zone). Clearing a rate writes a row `{ dayRate: null, payBasis: null, effectiveAt }`, meaning "rate not set from that day". History is never rewritten. **A pay change** (1.10.0) writes its rows with `payRateChangeWrites({ previousProfile, nextProfile, history, effectiveDayKey, seedEffective })`: nothing when the amount and basis are unchanged; a seed row of the previous rate from the account's creation only when the person's history loaded and is empty; then the new row. The rows are written in the same batch as the profile (`users/{uid}`), never as a best-effort second write; when the history did not load the save is refused (`history_not_loaded`, `PAY_HISTORY_NOT_LOADED_MESSAGE`) instead of treating it as empty.

**Rate on a day** (`payRateOnDay`; 1.10.0: given `person` and `roster`, history rows match every id of the person — `personIdSet`: own id, former ids, same-email ids — so each app passes the whole history): a PAYE day has rate 0 (the line keeps its hours and is flagged PAYE). Otherwise the rate is the latest history row for the person whose effective day (organisation zone) is on or before the day; an explicit 0 is a real rate. If the live profile is hourly, an hourly row stays in force until a day-rate row falls on a later day. A "rate cleared" row in force means "rate not set" (it ends an hourly row too). With no history row the live profile applies (`users/{uid}`, then the operative row). With nothing set the rate is "rate not set".

**Pay rules.**
- **PAYE has no timesheet** (1.11.0, owner decisions round 3). A PAYE day produces no timesheet line, no pay and no invoice row; it is still a booking for warnings, Daily Overview and Weekly Report hours (where its pay cell reads PAYE, `reportPayCell`). The days that count on a person's sheet for a period are `timesheetDaysForPerson(user, period, timeZone)` — every organisation-zone day of the period on which they are self-employed (`employmentTypeOnDay`, effective-dated); `showsMyTimesheets(user, period, timeZone)` is whether that list is not empty. A person sees **My Timesheets** for a period only then, gets the submission reminder only then, and their owner sheet, its invoice (`timesheetInvoiceRows` with `timesheetDays`: labour lines, price work and expenses dated on another day are left out) and the User Timesheets row for that period exist only then. A PAYE manager or admin still reviews other people's timesheets (User Timesheets is `canReviewUserTimesheets`, not this). A PAYE overtime and expenses submission is a later feature, not part of this rule. `isInvoiceLine` still drops a line flagged PAYE (older data).
- Self-employed days pay the effective day or hourly rate.
- Example: PAYE → self-employed changed on Tuesday, effective Wednesday: the sheet for that period shows Wednesday onwards only; Monday and Tuesday are not on it.
- **Overlapping bookings are each paid** and never merged. An overlap is a warning managers should have caught; on the timesheet each overlapping line is shown in amber for the person and their line manager with "Overlaps another booking — check with your manager" (`overlappingBookingIds`, `OVERLAPPING_BOOKING_NOTE`). Times that only touch do not overlap.

**Who may see pay** (1.13.0, owner decisions round 4, Q1; `canViewPersonPay(viewer, subject, roster)`). A person's pay — day or hourly rate, pay basis, employment type (with its effective-dated transition), rate history, timesheets and invoices — is seen only by: the person (under any of their ids); their active line managers (`lineManagerIds`); admins and super admins of the organisation; a manager with the Operatives toggle, for an operative only; and the platform owner. Every screen showing pay (the people profile, Manage Users, timesheets, User Timesheets, invoices, the weekly report's pay cells) asks `canViewPersonPay` first — from 1.13.0 the people profile on web; the others with the release that reads pay per person (step E of the move). Security rules cannot hide fields, and every member reads the roster's `users` documents, so pay moves to a private document per person per organisation: `organizations/{orgId}/payProfiles/{subjectId}` (`payProfilePath`; `subjectId` = the person's users id, or an `operatives` row id for a catalogue person with no account), fields `PAY_PROFILE_FIELDS` (`payBasis`, `dayRate`, `hourlyRate`, `employmentType`, `employmentTypeTransitionFrom`, `employmentTypeEffectiveAt`) plus `userId` and write metadata, read with `parsePayProfileDocument` and laid over the person with `overlayPayProfile` (the pay profile wins once it exists). A pay save writes the changed pay fields to the pay profile in the same batch as the profile (`payProfileWriteFieldsFromProfileWrite`), by whoever `canChangePersonPay` allows. **The move** (Deploy notes 1.13.0): apps write pay to both places and read the pay profile first; `scripts/backfill-pay-profiles.mjs` copies existing pay (`payProfileBackfillWrites`); a later release reads pay only per person; the platform owner then sets `platformConfig/app.privatePay` true (the rules then limit rate history, the `operativeProfiles` mirror and timesheets to pay viewers and refuse any pay value written back onto `users`, `operatives` or `managers`); the backfill's `--strip` step then removes pay from those documents. Only after the strip can no colleague read another's rate.

**Who may change pay** (`canChangePersonPay`). A person never changes their own pay, line manager or employment type on any path — `users/{uid}`, `operativeProfiles/{uid}`, `operativeDayRateHistory`, or the pay fields of `operatives/{id}` and `managers/{id}`. An admin may (including their own rate). A manager with Operatives access may change an operative's pay in the same company, never their own or another manager's; a manager's pay is changed by admins only. Resending an unchanged value is not a change.

**A self-employed person must have a pay rate** (1.14.0, owner decision). Self-employed people are paid from their rate, so a save that leaves a self-employed person (`normalizeEmploymentType`; a missing type reads as self-employed) without a rate is refused: `payRateRequiredError({ employmentType, payBasis, dayRate, hourlyRate })` returns `PAY_RATE_REQUIRED_MESSAGE` ("Set a day rate or hourly rate — self-employed people are paid from it.") when the rate for the chosen basis (`hourly` → `hourlyRate`, `day` → `dayRate`, no basis → either) is missing, blank, not a number, 0 or below. PAYE never needs a rate. Pass the person as they will be saved — a change to self-employed, immediate or effective-dated, is checked with the new type. Add User refuses the invite and Edit User refuses the save on every platform, with the message on the rate field, whenever the writer may set that person's pay (`canChangePersonPay`). People saved before this rule are listed for admins by `usersMissingPayRate(roster)` (active, not deleted, once per person by `personIdSet`).

**Timesheet review** (`timesheetEntryReviews`). Only the person's line manager or an admin writes `payrollLineReviews` and `extraEntryReviews`. The decision for a price-work or expense entry is `extraEntryReviews[entryId] { decision, revisedAmount, reviewedAmount, reviewedByUserId, reviewedAtMs }` (`timesheetEntryDecision`, written with `timesheetEntryReviewWriteFields` as dotted partial updates); a review stored under the entry id in another letter case is found too. Entries are read with `parseTimesheetEntries(sheetDocId, sheet, { timeZone })`: every entry with a title is kept whatever its id, a stored id keeps its stored case (UUID or not), and an entry stored without an id gets `timesheetEntryId(sheetDocId, kind, index, entry)` — a UUID-shaped id derived from the sheet id, the array, the position and the content, the same on every read and every platform, never random — and the next save writes it onto the entry. A review made against a different amount is stale and the entry is pending again; an entry nobody reviewed counts at its own amount. The inline `managerDecision` / `managerRevisedAmount` on an entry is still written for older builds and counts only when it lowers what is paid, or on a legacy sheet (no map) the line manager already signed. Owner saves go through `timesheetOwnerWriteFields`: it always removes the review maps and the manager sign-off and export fields (`TIMESHEET_MANAGER_SIGN_OFF_FIELDS`); the person writes `weeklyReportOverride` only when they have no line manager (self-signed), cannot change price work or expenses once the line manager has signed, and writes `managerNote` (their own note to the manager). The owner then sends only the fields that changed, as a partial update — never a full merge-set of the sheet. Every timesheet save, owner or reviewer, writes `timesheetChangedFields(base, next)` (1.9.0): the fields that differ from the sheet **as this editor loaded it**, never every difference from the server copy, so a signature, expense or price-work entry saved on the other platform after the load is kept; and whether the line manager has signed is read from the stored sheet, never a local copy. Whether a writer is a reviewer is `timesheetWriterIsReviewer`.

**Pay arithmetic** (1.10.0) is `payForHours({ payBasis, dayRate, hourlyRate, paidHours, standardDayHours, otMultiplier })` — hourly: rate × hours × multiplier; day: day rate × (hours ÷ the organisation's paid day, `orgDayHours`) × multiplier — rounded with `roundPennies`; no app keeps its own. 1.12.0: a day rate with a paid day below 1 hour (`PAY_STANDARD_DAY_MIN_HOURS`), missing or not a number pays 0 (rate not set), never the day rate divided by a 0.01 floor; a multiplier that is not a positive number is 1; a rate that is not a number is 0.

**The unpaid break** (1.12.0, `payrollHoursResult`). On a weekday the break taken off a booking is the part of the break window (`breakWindowStart`–`breakWindowEnd`) the booking's clock time covers, up to `unpaidBreakMinutes`: a booking across the whole window loses the whole break; 11:50–12:20 against a 12:00–12:30 break loses 20 minutes. Nothing comes off when the break is paid (`breakPaid`), removed on the booking (`isBreakRemoved`) or the slot is a named AM / PM. **A booking whose clock time lies entirely within the unpaid break pays 0 hours** (12:00–12:30, 12:05–12:25) — when a booking has clock times it never falls back to a full standard day; only a booking with no clock times at all is paid by its slot (FULL DAY, AM, PM, EVENING, OVERTIME). **Lunch warning** (1.13.0): before a custom-hours booking is saved, every app shows `customHoursBreakWarning(policy, dayKey, booking)` — "You are booking custom hours that cover the unpaid lunch break. Turn off Unpaid break to make sure they are paid for this time." — as a confirm step when the booking is custom hours, the organisation break is unpaid (`breakPaid` not true, an unpaid length above 0), the booking's Unpaid break toggle is on (`isBreakRemoved` not true) and its hours overlap the break window that day (weekdays only; weekends take no break off). The pay rule above is unchanged.

**Weekend pay** (1.13.0, Q2). Weekend bookings are custom hours (§4.3) and are paid by `payrollHoursResult` on that day's rule: with a set window, the hours inside it count as its "counts as" hours (pro rata when only part of it is worked) and the hours outside it are at that day's outside multiplier; with every hour at one rate, each hour × that multiplier. Stored weekend rows keep being paid as before and are never rewritten: an AM / PM pays half the "counts as" hours; a FULL DAY with no clock times pays the set window at its "counts as" hours with nothing outside it (`weekendFullDayWindow`; before 1.13.0 the weekday standard day plus weekend overtime), and on an all-hours day the pre-1.13.0 calculation (the standard day × that day's multiplier, e.g. 07:30–16:00 at 2× = 17).

**Overnight pay** (1.13.0, Q5): a booking that crosses midnight is paid wholly at its start day's rules (`payrollHoursResult`): on a weekday the hours inside that day's standard window count once (less the unpaid break they cover) and every other hour, after midnight too, is at that day's weekday multiplier; on a Saturday or Sunday that day's weekend rule. A weekday night is paid at the weekday overtime multiplier for every hour outside the standard window (owner confirmed). Before 1.13.0 it was paid as plain hours at 1×.

**Who takes part in timesheets** is `timesheetParticipant(user, dayOrPeriod, timeZone)`: never an inactive person or an anonymised profile; given a period, `showsMyTimesheets`; given a day, self-employed that day (1.11.0: `timesheetsEnabled` and operative mode no longer bring a PAYE person in). It decides the Weekly Report timesheet feed (§7, per payment run), the `timesheet_submission_reminder` recipients (§13) and the User Timesheets rows.

**Invoices** (1.10.0). The rows of a generated invoice are `timesheetInvoiceRows({ sheet, payrollLines, extrasMode })` on every platform: a signed sheet's `weeklyReportOverride` first (its signed amounts; declined and zero rows, and PAYE / leave lines, left out); otherwise the live lines (`invoiceLines`) with the line manager's review once signed (`payrollLineReview(sheet, lineId)`, found under the line id in any letter case), then price work and expenses with their decision (`timesheetEntryDecision`) in `decided` mode or at their own amounts in `raw` mode. 1.11.0: given `timesheetDays`, rows dated on a day the person was PAYE are left out (the PAYE-extras path is removed).

**Calculation.** Hours, overtime and pay come from bookings, the working-hours policy in effect that day and payment runs (`payrollHoursResult`, `workedHoursSplit`). Timesheets are grouped by payment run (`timesheetPeriodFromInvoicing`, `selectableTimesheetPaymentRunPeriods`); status Awaiting / Signed off / Exported is `timesheetListBucket`.

**Annual leave on timesheets.** Each approved leave day in the period appears as an information line "Annual leave (full day / AM / PM)" for the person and their line manager, with no edit control and no hours or pay (`timesheetLeaveLines`, `timesheetLeaveLabel`). Leave never appears on a generated invoice.

**Admin and operative mode** (1.11.0). An admin or super admin has no operative mode: a stray `operativeMode` flag on an admin is ignored everywhere — people lists (`parseUserDocument` → `operativeMode`, `accountKind`), permissions (`effectivePermissions`), the approval rules (`isAdminOutsideOperativeMode`, `adminOutsideOperativeMode`) and the security rules (`callerOrgRole`, `hbCallerIsOperative`). Only operative-level users get operative mode, at setup. (Before 1.11.0 such an admin decided only as a line manager.)

**Line manager.** A person's line managers are `assignedManagerUserIds` (else the single `assignedManagerUserId`; `hasNoLineManager` means none) — `lineManagerIds(user, roster)`. Given the roster, only active members count, an old invite id the roster knows as someone's `formerUserIds` / `sameEmailUserIds` is that person, and the person themself never counts under any of their ids (`personIdSet`: id, `formerUserIds`, `sameEmailUserIds`, roster rows with the same email). `hasActiveLineManager` is whether anyone is left. Line managers receive that person's timesheets for signing, annual leave requests and other approval items (`userTimesheetSubjects`, `leaveApproverIds`). With no active line manager (legacy data only), the active admins and super admins outside operative mode receive them — never "any manager". Nobody approves their own items. Routing is read at the time — changing the line manager on any platform re-routes everything, nothing is stored on the request.
- **Every operative and every manager needs an active line manager**, whatever the annual-leave self-book permission and whether annual leave is switched on for them. Only an admin or super admin outside operative mode may have none (`lineManagerRequired`, `isAdminOutsideOperativeMode`); an inactive person is not checked. `lineManagerRequiredError(user, roster)` returns `LINE_MANAGER_REQUIRED_MESSAGE` ("Set a line manager — this person's timesheets and annual leave need approval.") when a required line manager is missing, and Manage Users on every platform refuses that save. People saved before this rule who fail it are listed for admins by `usersMissingLineManager(roster)`; until fixed, their timesheets and requests go to the admins (`leaveApproverIds`), so nothing is stranded.
- **An admin or super admin with no active line manager is self-approved** (`timesheetSelfSigned(user, roster)`). Their timesheet has no "note to manager" and no "pending manager signature" state: their own signature completes the sheet (generate invoice is ready), and their owner save may write `weeklyReportOverride` (`timesheetOwnerWriteFields` with `subjectHasLineManager: !timesheetSelfSigned(...)`). Their annual leave saves approved (§9). An admin who has a line manager goes through normal approval.
- **`hasNoLineManager`** is a line-manager field: it is written only by whoever may change the line manager (admins; operatives managers for operatives), never by the person, together with the line-manager ids in one partial update. It is only valid for an admin or super admin.

## 9. Annual leave

One document per request at `organizations/{orgId}/holidayBookings/{id}`: a run of calendar-consecutive days with the same slot is one record from `startDate` to `endDate` (`holidayRequestRanges`, `holidayRequestWriteFields`), with `timeSlot` (`FULL DAY` / `AM` / `PM`, applying to every day) and `status` (`pending`, `approved`, `rejected`). Cancelling approved leave is a request (`cancellationRequestedAt`, `cancellationRequestedByUserId`) that an approver accepts (the record is removed) or refuses. Either way the requester is notified (`holidayDecisionRecipients`: `holiday_request_approved` when accepted, `holiday_request_declined` when refused, 1.9.0), as its own notice that never reuses the original decision's row. Older one-document-per-day records stay valid. **Reading a record** is `parseHolidayDocument(docId, data, timeZone)` on every platform (no app keeps its own parser): it accepts the keys either app has written (start `startDate`/`start_date`/`start`/`from`/`dateFrom`/`holidayStart`/`date`; end `endDate`/`end_date`/`end`/`to`/`dateTo`/`holidayEnd`, else the start day; person `userId`/`user_id`/`uid`/`userID`/`linkedUserId`/`employeeUserId` or nested `user.id`, and `operativeId`/`operative_id`/`operativeID`; status `status`/`holidayStatus`/`approvalStatus`; slot `timeSlot`/`slot`/`halfDay`; note `decisionNote`/`note`), uses the document id as the record id, keeps ids in their stored case (an `operativeId` that is not a UUID is kept), turns dates into organisation-zone day keys (a calendar-date string is that day) and swaps a reversed range. Status words map through `normalizeHolidayStatus` (`HOLIDAY_STATUS_SYNONYMS`: requested/awaiting/submitted → pending; accepted/confirmed → approved; declined/denied/cancelled → rejected); a missing or unknown status is approved. Warnings, Daily Overview, leave coverage and timesheets take the parsed day keys as they are (`labourHolidayInput`) and never recompute them from the stored dates. A decision writes `status`, `approvedByUserId`, `approvedAt` and an optional trimmed `decisionNote` (blank clears it) shown to the requester (`holidayDecisionWriteFields`, `parseHolidayDecisionNote`). Day counting (`leaveRecordDayKeys`, `annualLeaveBalance`): a single-day record counts its day; a multi-day record counts each day except weekends and bank holidays, each in its own leave year. Submitting a request notifies its approvers (`holiday_request_submitted`, `holidayRequestRecipients`), and the requester is notified of the decision (`holidayDecisionRecipients`); see §13. Approved leave affects Daily Overview, unbooked-labour warnings (`leaveCoverageRows`), timesheets (information lines) and My Schedule. Booking someone onto a day of their approved or pending leave asks first (`bookingLeaveConflicts`, §5, 1.16.0). Editing an existing record is a partial update of the changed fields.

**Self-booking** (`canSelfBookAnnualLeave(user, roster)`): a person's own leave saves approved when they have the `annualLeaveSelfBook` permission outside operative mode, or they are an admin or super admin outside operative mode with no active line manager (self-approved, §8). Having no line manager does not make an operative or manager a self-booker. Everyone else sends a pending request to `leaveApproverIds`. The submit button reads "Submit" when the leave saves approved and "Submit request" otherwise (`leaveSubmitLabel`, `LEAVE_SUBMIT_LABEL`, `LEAVE_SUBMIT_REQUEST_LABEL`). Self-booked leave notifies nobody.

**Who decides** (`canDecideLeave(viewer, requester, roster)`): never the requester under any of their ids, admins included. An admin or super admin not in operative mode may decide any request in the organisation; anyone else only when they are in `leaveApproverIds(requester)` (an admin in operative mode decides only as a line manager). The list a person sees to decide — pending requests and cancellation requests — is `leaveDecisionQueue(viewer, requests, roster)`. Enforced by security rules.

## 10. My Schedule

Every person sees their own bookings and annual leave (approved, and pending marked as pending), matched by account (`bookingIdsForAccount`, with the roster's same-email ids as `aliasIds`; leave with `leaveRecordsForAccount`, 1.9.0, which from 1.10.0 also matches leave whose `userId` is the account's email, as older iOS builds stored it) — never by name. Every My Schedule screen shows it — on web both the read-only screen and the self-booking screen admins and managers get (before 1.12.2 the self-booking screen showed no leave, while Daily Overview did). It updates live when a booking or leave changes on any platform. Hours split as in §6.

## 11. Manage Users

All Manage Users changes — role, line manager, employment status and rates with effective dates, inactive flag, exclusions, invites — are online-only, sync to every platform through live listeners, and are written as partial updates of the changed fields only (`userProfileWriteFields`; a linked `operatives` / `managers` row with `operativeRowWriteFields` / `managerRowWriteFields`). Changing a person's pay from an operative or manager record writes only the pay fields of their `users/{uid}`, never the whole document. People lists use `rosterPeople` / `listedRosterUsers`; Active / Inactive / Pending is `userRosterSegment`. A save that leaves an operative or manager with no active line manager is refused with "Set a line manager — this person's timesheets and annual leave need approval." (`lineManagerRequiredError`, §8) — the self-book permission does not waive it; only admins and super admins outside operative mode may have none. Admins see the people already in that state (`usersMissingLineManager`). A self-employed person needs a day or hourly rate above 0 (`payRateRequiredError`, §8): Add User and Edit User refuse the save with "Set a day rate or hourly rate — self-employed people are paid from it." on the rate field, and admins see an amber list of self-employed people without a rate (`usersMissingPayRate`). The line manager, `hasNoLineManager` and self-book flag are written by admins (operatives managers for operatives) only. The live roster is the `users` query on `organizationId` (§1). A user may not change their own rates, pay basis, employment type, active flag, line manager or permissions — enforced by security rules. **Roles & permissions** opens Manage Users directly.

**Permission toggles by user level** (1.11.0, owner decisions round 3). The toggles in effect are `effectivePermissions(user)`; every permission check on every platform and in the security rules reads them, never the stored flag. The level is `permissionLevelOf(user)` (admin for a super admin, `adminAccess` or the admin role; else operative for operative mode or the operative role; else manager).
- **Admins and super admins:** every `USER_PERMISSION_FIELDS` toggle reads on and is locked (`lockedPermissionFields`) — Admin Access and Operatives included — except **Annual Leave Management** (`annualLeaveSelfBook`), the only toggle an admin can change (`ADMIN_EDITABLE_PERMISSION_FIELDS`). `operativeMode` reads off and is not shown. The level is changed only with "Change user type". The annual leave allowance fields (`annualLeaveEnabled`, days per year, leave year, carry-over) are not permission toggles and stay editable.
- **Managers:** the stored toggles, editable as before, except **Materials** and **Site audit**, always on and locked (`MANAGER_LOCKED_ON_PERMISSION_FIELDS`; both apps already saved them on). **Wholesalers** stays an editable toggle: a manager can have it off. **Operatives** off: they still schedule live active operatives onto the jobs they manage (`canScheduleOperatives`, `canWriteBooking`) but cannot add or manage operatives (`canManageOperatives`).
- **Operatives:** Materials and Site audit, editable.
- Existing user documents are never rewritten for this: locked values are derived when read (`parseUserDocument.permissions` is `effectivePermissions`), and `userProfileWriteFields` never writes a locked toggle (`keepStoredLockedPermissions`: top-level, dotted and `permissions` map entries keep their stored value), except when "Change user type" changes the level.
- **One set of rows** for Add User, its summary and Edit User on both apps: `permissionToggleRows({ level, user?, mode: 'add' | 'edit' | 'summary' })` → ordered `{ field, label, help, visible, editable, value }` (`PERMISSION_TOGGLE_CATALOGUE`). Admin: every row shown on and greyed out except Annual Leave Management. Manager: every row but Admin Access; Materials and Site audit on and greyed out. Operative: Materials and Site audit. Add User starts from `addUserPermissionDefaults(level)` (1.14.0, owner decision): **every toggle the adder can change starts off** and the adder turns them on one by one; locked toggles keep their locked value (admin and super admin: every toggle on and locked except Annual Leave Management, which starts off; manager: Materials and Site audit on and locked; operative: Materials and Site audit both start off). This applies to new users only — changing an existing person's user type keeps every saved toggle (`accountTypePermissions`, 1.15.0) and never applies these defaults.

**Change user type** (1.11.0) is `accountTypeChangeWrites({ person, kind, organizationId, roster, permissions? })`. **A type change keeps every saved toggle** (1.15.0, owner decisions round 6): `accountTypePermissions(kind, previous)` returns the person's stored toggles (top level, else `permissions.{key}`; a toggle never stored keeps the value it reads as) and changes only the level flags (`adminAccess`, `operativeMode`, `manager`); the screen's `permissions` are taken only for the toggles the new level can change (`accountTypeWritePermissions`: an admin only Annual Leave Management). An admin still reads every toggle on and locked except Annual Leave Management (`effectivePermissions`); the stored values stay untouched underneath and read again after a demotion, so manager → admin → manager returns the exact toggles and operative → manager keeps the operative's. (Before 1.15.0 a change kept Projects, Small Works, Weekly Report and Daily Overview and preset the rest.) One batch writes every document that decides the type in this organisation — `users/{uid}` (role, level flags and every toggle, top level and `permissions.{key}`), same-email users documents of this organisation, `organizations/{orgId}.members.{uid}` and `users/{uid}/orgMemberships/{orgId}` (role and nested permissions). When the person's `users/{uid}.organizationId` is another company, that profile is not rewritten: only `members.{uid}` and the membership here are written (their level here is read from them, `organizationLevelFor`) and the screen shows `ACCOUNT_TYPE_OTHER_COMPANY_NOTE`. It is refused with `ACCOUNT_TYPE_SUPER_ADMIN_MESSAGE` for a super admin who would stop being an admin. The security rules allow these writes to an admin or super admin of the organisation only. The plan is written as **one atomic batch** (1.12.2) — never the users document first and the rest after — so a refusal leaves nothing half applied; an admin may read the person's membership (`users/{uid}/orgMemberships/{orgId}` get) to build it. A type that is not the same on the users document of this organisation and `members.{uid}` (or the membership) is **half applied** (`accountTypeSyncState`: an older iOS build wrote only `users/{uid}`, or a save stopped half way); the users document is the source, Manage Users lists those people and Edit User says `ACCOUNT_TYPE_OUT_OF_SYNC_MESSAGE`, and the next Save re-applies `accountTypeChangeWrites` with that type. One save runs at a time (a second press is ignored) and a saved profile returns to the people list. A profile save syncs names to same-email users documents of this organisation only (a users query on email alone is never allowed by the rules).

**Line managers on Manage Users** (1.11.0): the picker lists `lineManagerCandidates(person, roster)` — the active admins, super admins and managers, never the person under any of their ids, never a pending invite or a deleted profile, by name; **one option per person** (1.14.0): roster rows that are the same person by `personIdSet` (two users documents on one email, an id in another letter case, a former invite id) are one option whose value is the person's live users document (active, signed up, not listed as another row's alias), and the level and status are read from that row; the selected values are `lineManagerSelectedIds(person, roster)` — a stored id that names the person's other document (or another letter case) shows that one option as selected; "No line manager" is offered only when `lineManagerOptions(person).allowsNoLineManager` (`lineManagerRequired` false: admins); the row reads `lineManagerSummary(person, roster)` → `{ label, ids: [{ id, name }] }` — each stored id resolved on the roster (an unknown id reads "Unknown person", never dropped), the label the first name with "+N more" only for N ≥ 1, "Not set" when none is stored, "No line manager" when chosen.

**Accepting an invitation** (1.10.0; 1.11.0 below) is `inviteAcceptWrites({ existingProfile, placeholder, invitation })`: the role comes from the invitation (its `role`, else the kind its permissions give), never from another company's profile; with no account yet, `users/{authUid}` is written (from the placeholder when the claim names this invite's) and only then is the placeholder moved and removed and the claim pointed at the account; an account that already exists in another company keeps its profile, the placeholder stays (the in-organisation row with the invited pay) and its role there goes on its membership. Add User cannot tell that an email already has an account in another company (no account lookup by email). **1.11.0 (owner decisions round 3):** accepting applies exactly what the invitation stores, nothing more — the invitation is the only source of the person's access in that organisation. Add User stores the level as `role` on the invitation (`invitationCreateFields`) beside its permissions, pay and line manager, and writes the same on the placeholder. A new account gets `invitationProfileFields(invitation)` (role, permissions, employment type, one pay basis, line manager). An account in another company accepts with one batch, `inviteMembershipWrites({ invitation, invitationId, authUid, now })`: the membership created with the invitation's role (`invitationRole`) and `permissions` exactly as stored plus `invitationId`, `members.{uid}` = that role, and the invitation marked used; the placeholder keeps the invited pay and line manager. The security rules accept it only for a genuine, unused invitation to the signed-in email, marked used in the same batch (§16). **Who may invite** (1.12.0): admins invite any level; a manager with operatives access creates, changes and holds only an operative-only invitation (`invitationIsOperativeOnly`: `invitationRole` operative, operative mode on, no admin, super admin, manager or operatives toggle at the top level or in `permissions`) — the same test as their operative placeholder on `users/{uid}`. The rules refuse any other; an app can call `invitationIsOperativeOnly` before writing to show the reason.

**Deleting a person** (1.10.0). `canDeleteUser(actor, target, { roster, creatorUserId })` (`userDeleteRefusal` gives the reason, `USER_DELETE_REFUSAL_MESSAGES`) is the same test as the security rules: only an admin or super admin outside operative mode deletes; never themselves, the super admin or the organisation creator; an admin who is not super admin deletes only people who are not admins. Both apps check it before any write and show Delete only when it passes. The delete is one ordered plan, `userDeleteWrites({ orgId, user, actorUserId, platform, bookings, managerSiteBookings, operativeRows, managerRows, invitations, nowIso, tz })`: (1) one batch deleting `users/{uid}`, `users/{uid}/private/taxIds`, `users/{uid}/orgMemberships/{orgId}`, `organizations/{orgId}/userEmails/{email}` and `members.{uid}` — a refusal there changes nothing; (2) their labour and manager site bookings from today on, each with its tombstone; (3) their `operatives` / `managers` rows (by id or email); (4) their pending invitations in the organisation. Past bookings and their `bookedBy` names are never rewritten.

**Delete my account** (1.15.0, owner decisions round 6; web now, iOS later) is decided per organisation by `accountDeletionPath(viewer, roster, org)`:
- `handover_required` — the person is the organisation's super admin (`isOrganizationSuperAdmin`: its creator, or a users document of it flagged `isSuperAdmin`) and another active member is listed (`rosterSegment` active, not the person under any of their ids). They first make another admin the super admin with the existing ownership transfer (`creatorUserId`, Change Super Admin): the app offers the active admins (web `superAdminSuccessors`) or makes an active member an admin first (`accountTypeChangeWrites`) and then transfers. The account is not deleted until then (`ACCOUNT_HANDOVER_REQUIRED_MESSAGE`).
- `delete_with_company` — the super admin is the only active member: deleting the account deletes the company. They type the company name and DELETE (`organizationDeleteConfirmationError`, `ACCOUNT_DELETE_WITH_COMPANY_MESSAGE`); the company enters the 60-day scheduled state of §20 with `restoreBy: 'platform_owner'` (nobody is left to restore it; only the platform owner can) and the account is deleted straight away.
- `delete` — everyone else, and an organisation already scheduled for erasure: the account is deleted as before (company records stay; the name becomes "Deleted user").
Web `/api/account/delete` answers 409 `handover_required` or `company_delete_required` instead of the old `sole_admin`.

## 12. My Profile

Matches on every platform and updates live: profile photo (`profilePhotoURL`, with `profilePhotoUpdatedAt` set on every upload so other devices refresh the cached avatar), contact details, day/hourly rate and employment status (read-only), and billing details — VAT number and UTR — stored privately at `users/{uid}/private/taxIds` (`sensitiveProfile`). A photo upload stores a fresh download URL; a stale profile copy never removes or rolls back the photo. **Delete my account** (1.15.0) is on My Profile / Settings; what it does is `accountDeletionPath` (§11): a super admin with other active members hands super admin over first, a super admin alone in the organisation deletes the company with the account (§20), everyone else deletes only their account.

## 13. Notifications

- **My notifications** toggles are personal (`users/{uid}.notificationPreferences`), written as dotted partial updates, and sync across platforms (`parseUserNotificationPreferences`, `userNotificationPreferenceFieldPatch`).
- Which toggles a person sees depends on role and features (`visibleNotificationPreferenceKeys`). People who can see variations (`canSeeVariations`: admins and managers) have a **Variations** toggle (`variations`, on by default) covering all five variation types. Admins and super admins have a **Company activity** toggle (`companyActivity`, on by default: "People, clients, jobs added and warnings removed.") covering the six company activity types; the older per-type toggles for them (`projectCreated`, `smallWorksCreated`, `operativeCreated`, `managerCreated`, `clientCreated`, `warningDismissed`) are retired — still parsed, never shown.
- A toggle turned off stops that notification type's **device push** everywhere (`notificationPreferenceAllowsDelivery`, `devicePushAllowed`; enforced by the push Cloud Function). It **never hides the inbox row**: every notice addressed to the person stays in the notification centre and the unread count, on every platform (`notificationShowsInInbox`, `NOTIFICATION_TOGGLE_HIDES_INBOX_ROW = false`). The app-icon badge counts the same unread rows.
- **Reading inbox rows** is `parseNotificationDocument(docId, data, { role })` on every platform: the type is kept as the stored text (a type the app does not know is still listed, `known: false`), `relatedId` keeps any shape (UUID, day key, uid, job id), title / message / read flag default instead of dropping the row, and `destination` is `notificationDestination` for the role. Every app's type list (the iOS enum) accepts every type in `KNOWN_NOTIFICATION_TYPES` (the table below, the push allow-list and the legacy `material_added`); no row is dropped for its type. Marking read writes `isRead` only (`notificationReadWriteFields`).
- Types that send a device push are `DEVICE_PUSH_NOTIFICATION_TYPES`, including every variation type (`variation`, `variation_renumbered`, `variation_added`, `variation_from_tracker`, `variation_numbers_updated`).
- Organisation settings (material cut-off, schedule options) never appear in My notifications.
- Web never sends browser or OS notifications.

**Who receives each notification** (`lib/canonical/notificationRecipients.ts`). One rule per type, the same on every platform, and **never the person who caused it** (the actor) under any of their ids. Every recipient function is pure over the roster (`id`, `email`, `isActive`, `role`, `formerUserIds`, `sameEmailUserIds`, line-manager fields), drops inactive roster members, and de-duplicates ids without case. `personIdSet(person, roster)` is every id of a person (id, `formerUserIds`, `sameEmailUserIds`, roster rows with the same email); `excludeActor(ids, actor, roster)` removes them.
- Timesheets: `timesheetSubmittedRecipients(subject, roster)` — the subject's active line managers, else the active admins (never the subject); nobody when the sheet is self-signed. `timesheetSignedRecipients(subject, signer, roster)` — the subject, unless they signed. `lineManagerPeerRecipients(subject, actor, roster)` — the subject's other active line managers (no admin fallback).
- Annual leave: `holidayRequestRecipients(requester, roster)` — `leaveApproverIds` without the requester; nobody when the leave is self-booked. `holidayDecisionRecipients(requester, decider, roster)` — the requester, unless they decided.
- `bookingCreatedRecipients`, `deadlineAssignedRecipients`, `toolboxTalkRecipients`, `ideaRecipients` — the given ids without the actor.
- **Company activity** (`operative_created`, `manager_created`, `client_created`, `project_created`, `small_works_created`, `warning_removed`, `COMPANY_ACTIVITY_NOTICE_TYPES`): `companyActivityRecipients(actor, roster)` — the active admins and super admins outside operative mode, without the actor. One row per admin with `userId` and `actorUserId`; a row without `userId` is never written.
- **Push test** (`push_test`, Settings "send a test notification"): `pushTestRecipients(actor)` — the signed-in user only. It is the one type pushed to its actor (`notificationPushesToActor`); no toggle turns it off. On web its only effect is the inbox row.
- Job notices keep `materialOrderRecipients` and `receivesJobNotification`, then `excludeActor`. Neither has an "all admins" fallback: a job with no managers notifies no manager.
- **`relatedId`** (1.9.0) is the stored id of the record the notice is about, chosen per type by `NOTIFICATION_RELATED_ID` and written with `notificationRelatedId(type, ids)`: leave notices the holiday booking id; job, booking, material and project / small-works notices and `variation_renumbered` / `variation_numbers_updated` the job id; `variation` / `variation_added` / `variation_from_tracker` the variation id; `client_created` the client id; `operative_created` / `manager_created` the user id; tasks the task id; deadlines the deadline id; toolbox notices the issue id; `warning_removed` the warning key; `timesheet_submission_reminder` the payment day key; feedback notices the idea id; `line_manager_peer_update` the holiday booking id when it is about leave. Timesheet notices and `push_test` carry none (null) — timesheets are identified by `deepLinkUserId` + `deepLinkWeekStart`. Never a random id. A new row is `notificationCreateFields` (§1). 1.10.0: an app holding the one id the type names writes `notificationRelatedIdFor(type, id)` (null for a type that carries none) — the single source for every web and iOS write. `notificationDestination` opens a variation notice on the variation (`variationDetail`, relatedId the variation id) or the job's variations (`variations`, relatedId the job id); operatives get the inbox.
- **Leave notices other than a decision** (1.10.0). A manager or admin removing someone's approved leave writes `holiday_cancelled_by_manager`; a manager or admin booking approved leave for someone writes `holiday_booked_for_you`; both go to `holidayDecisionRecipients(person, actor)` (never the actor) under the annual-leave-decision toggle, and neither reuses `holiday_request_approved` / `holiday_request_declined`. Switching someone's self-book permission off writes no notice. No leave notice goes to every admin.
- Every inbox row an app writes carries `actorUserId` (the signed-in user who caused it; security rules require it to be that user when present). Scheduled notices nobody caused (`timesheet_submission_reminder`, `deadline_reminder`, `deadline_due`) leave it out. Notice dates shown in leave notices (`annualLeaveDecisionDateText` on web, `AnnualLeaveNoticeText.decisionDateText` on iOS) use the organisation business time zone. The push Cloud Function never pushes a row whose `userId` is its `actorUserId`, except a type whose push is for the actor (`notificationPushesToActor`: `push_test`).
- **The inbox is the rows addressed to the person, from their `createdAt`.** `inboxNotificationVisibleToUser(row, ids, now)` and `unreadNotificationBadgeCount(rows, ids, now)` count only rows whose `userId` is one of the person's ids; a scheduled row (`SCHEDULED_NOTIFICATION_TYPES`: `deadline_reminder`, `deadline_due`, `timesheet_submission_reminder`) only once its `createdAt` is not after now (1.10.0), any other row unless its `createdAt` is more than `INBOX_CREATED_AT_SKEW_MS` (5 minutes) after now (1.16.0); a row whose server time is not back yet is listed; the push function neither pushes nor badges a hidden row. A row with no `userId` is not an inbox row and is never listed, counted or pushed.
- **`createdAt` is server time** (1.16.0). A row due now is written with the app's SDK server timestamp, passed to `notificationCreateFields` as `serverTimestamp` (`notificationCreatedAtIsServerTime`); only a scheduled type written ahead of time keeps its own due instant. A writer's or reader's clock no longer hides a row or drops it out of the newest 150.
- **Recipients are accounts** (1.16.0). Every recipient function returns signed-in account ids only, one per person: each given id — an operatives catalogue id, an invite placeholder or former id, a same-email id, any letter case — goes through `notificationRecipientAccountId(id, roster, catalogue)` (the person's active users document that has signed up, not another row's former id, first in roster order) inside `excludeActor`; an id the roster cannot resolve is dropped. `bookingCreatedRecipients(bookedIds, booker, roster, catalogue)` takes the operatives rows. No app resolves recipients itself. (The inbox reads `userId == auth uid`, so a row addressed to any other id was pushed to whatever device held that document's token and never listed.)
- **Push payload** (1.16.0): `pushPayloadFields(row)` — `notificationId`, `type`, `relatedId`, `dayKey`, `catalogue`, `userId`, `organizationId` (strings, empty left out) — so a tapped push routes like the row in the centre.
- **Rows in another company** (1.16.0, interim until the owner decides on a cross-company inbox): the push carries `organizationId`; tapping a push or row of another organisation switches to it first when the person is a member (`notificationOrganizationSwitch({ rowOrganizationId, openOrganizationId, membershipIds })` with `sessionMembershipIds`), otherwise it routes in the open company. Each inbox still lists only the open organisation's rows. The push Cloud Function's app-icon badge counts the recipient's own unread rows the same way (bounded read).
- **Scheduled push types are not pushed** (1.10.0). The push Cloud Function runs when a row is created and has no schedule, so a row written ahead of time with a future `createdAt` (`timesheet_submission_reminder` written early, `deadline_reminder`, `deadline_due`) is never pushed — it appears in the inbox when its `createdAt` arrives. A row written when it is due is pushed as usual (its type's push flag).
- Timesheet notice document ids are each app's synthetic UUID of `timesheetNotificationDedupeKey` — the period start as unix seconds of midnight in the organisation zone (never the device calendar).
- **Device push tokens belong to exactly one account** (1.16.0): the last account to register it. A token is written to `users/{uid}.pushTokens` of the account signed in on that device (its Firebase Auth uid), never copied to other users documents and never to an invite placeholder users document (a UUID-shaped id, `isPushTokenPlaceholderUserId`, 1.17.0); signing out removes this device's token from every users document it was written to. The server enforces it: when a users document gains a token (`addedPushTokens`), the `pushTokenSingleOwner` Cloud Function removes it from every other users document (`pushTokenOwnerWrites`, an `array-contains` query and `arrayRemove`), so a forced or offline sign-out can no longer leave it behind. `scripts/dedupe-push-tokens.mjs` (dry run by default, `--apply`) cleans existing data once (`pushTokenDedupePlan`, 1.17.0): a placeholder users document always loses its tokens; a token on more than one signed-in account stays on the one with the newest `pushTokenUpdatedAt` (`updatedAt` is compared only when none of them has `pushTokenUpdatedAt`); a token found only on placeholders is removed everywhere and the phone registers it again on its signed-in uid at next launch. A placeholder is never the owner in `pushTokenSingleOwner` either: when a placeholder gains a token, the token is removed from that placeholder (`pushTokenOwnerWrites`) and the signed-in accounts keep it. The push function also skips any recipient token that is on the actor's own users document (`pushTokensExcludingActor`).
- **Recipients are members** (1.12.0). An inbox row is written only for a member of the row's organisation (`organizationMemberActive`: a key of `members`, the creator, a users document of that organisation, or a membership there); the security rules refuse any other `userId` and a row without one. The push Cloud Function pushes a row only to an active member of its organisation (the same function; a person that organisation deactivated gets no push). A stranger's own company can no longer push text to a uid elsewhere.
- `NOTIFICATION_CATALOG` is the table below (`notificationCatalogRow(type)`). Push follows `DEVICE_PUSH_NOTIFICATION_TYPES`. `variation_from_tracker`, `variation_numbers_updated`, `booking_clash`, `booked_onto_job` and `material_order_created` are on the push allow-list but nothing writes them. ## 14. Authentication and organisations

- Sign-in and passwords use Firebase Auth email/password on every platform; a password change applies everywhere. Every password — sign-up, invite set-up, reset, change — must be at least 8 characters; the platform owner's developer account needs 10 (`PASSWORD_MIN_LENGTH`, `passwordMinLength`, `passwordPolicyError` → "Password must be at least N characters."). The platform owner is `isPlatformOwnerEmail(email)` (`PLATFORM_OWNER_EMAIL`, compared without case); `passwordMinLength({ email })` applies the 10 for it. No complexity rule.
- **The platform owner** (1.12.0) is the signed-in Firebase Auth account whose token email is `PLATFORM_OWNER_EMAIL` and is verified (`isVerifiedPlatformOwner`; security rules `isPlatformOwner`, owner API routes `requireOwner`). A users document's `email` never counts.
- **Deactivated** (1.12.0): a person is deactivated in an organisation when their users document is that organisation's and says `isActive: false`, or their membership there says `accountActive` (else `isActive`) false (`organizationMemberActive`). The security rules give them no access to that organisation's data and the push function sends them nothing; they still read their own users document and memberships, so the apps show the deactivated screen and Switch organisation.
- **Changing a sign-in email** (1.12.0): the person's own users document `email` changes only to their signed-in Auth email — after Firebase Auth has changed it (iOS `sendEmailVerification(beforeUpdatingEmail:)` / web `verifyBeforeUpdateEmail`, then the next sign-in). An admin changes a person's email from Manage Users (both apps), or the platform owner from the support tool. **1.13.0:** a person's own profile save decides with `selfEmailChangeAction({ storedEmail, nextEmail })` — `verifyBeforeUpdate` asks Auth to verify the new address (the message is `selfEmailChangeSentMessage`) and the rest of the save goes ahead with the stored email; nothing else is written until Auth has changed it. On the next sign-in with a verified token email that differs from `users/{uid}.email`, `signInEmailSyncWrites` gives the writes: `users/{uid}.email` = the token email, the new `userEmails/{email}` claim for the account, and the old claim deleted when it is the account's. The rules allow exactly these (§16).
- **Switching organisation is per device.** Each platform remembers the last organisation it opened (web `pp.webActiveOrg:{userId}`, iOS `cached_organizationId`) and reopens to it (`chooseSessionOrganization`). Switching on one platform does not change another platform, and does not write `users/{uid}.organizationId`.
- **Membership is shared.** The list of organisations a person belongs to is shared data (`sessionMembershipIds`).
- **One membership shape** (1.10.0). `users/{uid}/orgMemberships/{orgId}` is read with `parseOrgMembershipDocument` (nested `permissions.{key}` first, else the legacy flat key, else its default — `ORG_MEMBERSHIP_DEFAULT_ON`; operative mode turns manager and operatives off; `accountActive`, else `isActive`) and written with `orgMembershipWriteFields({ organizationId, stored, next, writer, now })`: nested permissions only, changed fields only, and an admin update removes the legacy flat keys. Only an admin of that organisation writes role, permissions, super admin or the active flag (`ORG_MEMBERSHIP_ADMIN_FIELDS`); the person writes only acceptance (`status: 'active'`, `acceptedAt`). No app copies its users document onto a membership on a switch.
- **A role belongs to an organisation** (1.10.0). Whether someone is an admin or manager *of an organisation* comes from that organisation: their `users/{uid}` flags only when that document's `organizationId` is this organisation, otherwise this organisation's `members` map entry. A manager in company A who is an operative in company B is an operative in B (security rules `callerOrgRole`).

## 16. Server-side permissions (Firestore security rules)

Deployed only from `project-planner-web/firestore.rules`. Apps hide controls too, but these rules are the guard:
- **Organisation:** only a current admin edits `organizations/{orgId}`; billing is never written by an app; ownership (`creatorUserId`) passes only from the current Super Admin to another admin (or by the platform owner). A demoted creator cannot edit. **1.12.0:** `isSuperAdmin` (on `users/{uid}` and on a membership) changes only by that organisation's Super Admin (its creator, or a users document of it that is already super admin) or the platform owner — never on one's own document by anyone else, and a self-created profile is super admin only for the creator; an admin who is not the Super Admin never changes the role, permissions, active flag or company of the Super Admin or the creator (names and other fields stay editable).
- **Platform owner** (1.12.0): `isPlatformOwner` is the Auth token email `info@projectplanner.us` with `email_verified == true`, never a users document's `email`.
- **Deactivated people** (1.12.0, §14): `canAccessOrganization`, `callerOrgRole`, the admin tests and co-member reads refuse a person deactivated in that organisation (their users document of that organisation `isActive: false`; for a member from another company, their membership `accountActive` false). Their own users document and memberships stay readable. Known limit: an admin from another company deactivated only on their membership here keeps the members-map admin test.
- **Identity links on users** (1.12.0): on their own document a person never changes `formerUserIds` or `sameEmailUserIds`, and changes `email` only to their signed-in Auth email; a self-created profile carries alias ids only from the invite placeholder it copies plus that placeholder's id (`inviteMigrationFormerIdWriteFields`), and none when re-created by a returning member or a founder. Admins write them (Manage Users, the admin backfill). Rules read the caller's alias ids only from a users document of that organisation.
- **Company settings documents** (`settings/{id}` such as job types and trades): admins and managers. Deadlines and health & safety documents stay open to the team.
- **Pay reads** (1.13.0, Q1; rules `canViewPayOf` = `canViewPersonPay`): `payProfiles/{subjectId}` is read by id only by the person (their uid, or a users document on their signed-in email), their line manager (listed on their users document), admins of the organisation, a manager with operatives access for an operative of the company, and for a catalogue row admins, operatives managers and the person on its email; the whole collection only by admins and the platform owner. It is written by those `canChangePayOf` allows, only `PAY_PROFILE_FIELDS`, `userId` (= the document id) and write metadata. While `platformConfig/app.privatePay` is true (`privatePayOn`): `operativeDayRateHistory` rows, `operativeProfiles/{uid}` and `settings/timesheet_*` are read only by those people (a non-admin query of history must name the person), and no write puts a pay value (not null) on `users`, `operatives` or `managers` (`payStaysPrivate`; removing one is allowed). The organisation catch-all read never re-opens `payProfiles`, `operativeDayRateHistory`, `operativeProfiles` or `settings`. A person never changes their own `employmentStartDate` (§4.4).
- **Lapsed subscription** (1.13.0, Q3; §19): while `orgBillingOpen` is false, organisation data is refused to everyone but the platform owner — `canAccessOrganization`, the admin tests (`isOrganizationAdmin`, `isOrgAdminViaMembersMap`), `callerOrgRole` and co-member users reads (`anchoredInCallerCompany`) all refuse. Not closed: the organisation document itself (read, and its admin edits), the caller's own users document and memberships. Billing stays server-only.
- **Email claims** (1.13.0, §14): a person deletes their own `userEmails/{email}` claim only when their verified token email is another address.
- **Profile and pay:** a person cannot change their own pay (`dayRate`, `hourlyRate`, `payBasis`), line manager, active flag, employment type or permissions — on `users/{uid}`, `operativeProfiles/{uid}`, `operativeDayRateHistory`, `operatives/{id}` or `managers/{id}`. Pay changes are admins, or operatives managers for operatives (§8). Resending an unchanged value always passes. The self-employed pay-rate requirement (`payRateRequiredError`, §8) is an app form rule: the security rules do not enforce it, so older app builds can still save a self-employed person without a rate (`usersMissingPayRate` lists them).
- **Annual leave:** a person creates and edits their own pending request and asks to cancel. Nobody decides their own request, admins included (`canDecideLeave`). The person's line manager or an admin (not in operative mode) approves or rejects; a person with no line manager waits for an admin — never any manager. Only a self-booker (`canSelfBookAnnualLeave`: the `annualLeaveSelfBook` permission outside operative mode, or an admin / super admin outside operative mode with no current line manager) saves their own leave approved; having no line manager does not allow it for an operative or manager. The rules cannot read the whole roster: a person's line manager is "current" when one is listed that is not the person and, when exactly one is listed, that users document exists and is not `isActive: false`.
- **Timesheets:** a person never counter-signs or exports their own timesheet (their saves never carry those fields, `timesheetOwnerWriteFields`); only their line manager or an admin writes the sign-off and export fields and the review maps (`payrollLineReviews`, `extraEntryReviews`); after sign-off the person cannot change price work or expenses. The owner writes `weeklyReportOverride` only without a current line manager (same test as annual leave).
- **Notifications:** any member creates inbox rows; `actorUserId`, when present, is the signed-in user. Reads and updates are the addressee's own rows (or an admin's). 1.12.0: the row's `userId` must be a member of that organisation (members key, creator, a users document of it, or a membership there); a row without `userId` is refused.
- **Roster rows** (1.12.0): `operatives/{id}` and `managers/{id}` are created by staff (admins and managers) only. Changing an existing row's `email` — which `jobListsCaller` and `callerOwnsBookingId` trust — is admins only, and on an operatives row also a manager with operatives access for a row that is not their own. Pay keys as before (§8).
- **Catalogues** (1.12.0): `qualifications` and `skills` are written by admins and managers only. A person's own qualification assignments and expiry dates stay on their operatives row (iOS My Qualifications).
- **Account confirmations** (1.12.0): `accountConfirmations` are never listed; a founder creates one only for themselves (`userId` = the signed-in account); marking it used needs the signed-in account whose token email is the one it names (the confirm page asks a signed-out visitor to sign in first).
- **Platform config** (1.12.0, §18): `platformConfig/app` is readable by anyone, signed out included; other `platformConfig` documents by signed-in users; only the platform owner writes.
- **Job and booking reads** (§17) are enforced only while `platformConfig/app.enforcedReads` is true (1.12.1); otherwise every member of the organisation reads them (a deactivated person never does).
- **Warnings:** only admins and managers accept or un-accept a clash (create and delete `acceptedBookingClashes`), dismiss a warning (`dismissedWarnings`, enforced from 1.9.0) and approve, dismiss or undo a warning resolution.
- **Jobs and bookings** (1.10.0, owner decisions; `staffAccess.ts`; reads in §17). Creating a project or small works job and changing a job's manager list (`managerIds`, `managerId`, `assignedManagerUserIds`, `managerUserIds` — `JOB_MANAGER_LIST_FIELDS`) is admins, and managers with that kind's add/edit/manage permission (`permissions.projects` / `permissions.smallWorks`) in that organisation (`canCreateJob`, `canChangeJobManagers`). A manager without it edits the details of a job they manage, never its manager list (`canEditJob`, `jobWriteWithoutManagerList`). Creating, editing, cancelling and deleting labour (`bookings`), manager site (`managerSiteBookings`) and subcontractor (`subcontractorBookings`) bookings, and writing their tombstones, is `canWriteBooking` / `canDeleteBooking`: admins every booking; managers bookings on jobs they manage (a manager site booking with no job: their own) — a toggle does not extend it, and a manager never books themselves onto a job they do not manage; operatives never. The rules read the job document (`projects/{id}` or `smallWorks/{id}`, the stored id, then upper, then lower case) and accept the signed-in account in `managerUserIds`, `managerIds` or `managerId`, or `managerId` naming a managers row with the signed-in email. The toggle in an organisation is that organisation's: `users/{uid}` flags when it is the person's own company, else `users/{uid}/orgMemberships/{orgId}.permissions`. A job save writes `managerUserIds` = `jobManagerUserIds(job, managers, accounts)` beside `managerIds`; jobs saved before 1.10.0 get it from `scripts/backfill-job-manager-user-ids.mjs` (Deploy notes). Tombstones as in §2, carrying only their own fields.
- **Invitations** (1.12.0): admins of the organisation (and the platform owner) list, create, change and delete them; a manager with operatives access lists and deletes their company's, and creates or changes only an invitation that is operative-only before and after the write (`invitationIsOperativeOnly`).
- **Memberships:** only an admin of that organisation writes another person's role, permissions, super admin or active flag on `users/{uid}/orgMemberships/{orgId}`; the person may only accept and set `role` to what the organisation's members map lists. **1.11.0:** the person accepting an invitation may create their membership and add their own `members.{uid}` with exactly the invitation's role (`invitationRole`) and permissions, only for an invitation in `invitations/{id}` to the signed-in email and this organisation that was unused before the batch and is marked used by it (`inviteBeingAccepted`); nothing else on the organisation document changes, and an existing members entry is never replaced.
- **Booking kind** (1.11.0): `jobCollection`, when a booking carries it, is `projects` or `smallWorks` and only on a booking with a job; a manager's write must name the collection the job they manage is in (`callerManagesJobIn`).
- **Deleting a person:** as `canDeleteUser` (§11); the account batch is refused whole when the users delete is refused.
- **Material quotes and orders** (1.15.0, `canSendMaterialOrders`): only admins and super admins outside operative mode and managers send a quote or order and see quote / order history; the per-user Materials toggle does not gate them (it is locked on for managers and admins), and for an operative it only opens the job's material list. `materialSendRecords` are created and read by admins and managers of the organisation only. The `material_request` email (email function) and the web send route refuse anyone else (`MATERIAL_ORDER_SEND_REFUSED_MESSAGE`); recipients are saved wholesaler contacts, the sender's own copy and at most 3 typed addresses not saved on a wholesaler per send (`materialOrderRecipientCheck`, `MATERIAL_ORDER_TYPED_RECIPIENTS_MAX`). The web route sends the copy to the signed-in email only.
- **Company deletion** (1.15.0, §20): while `organizations/{orgId}.deletion.status` is `scheduled`, organisation data is refused to everyone but the platform owner, exactly like a lapsed subscription (`orgBillingOpen` also checks it): not closed are the organisation document (read), the caller's own users document and memberships. No other edit of the organisation document is allowed while scheduled. `deletion` is written by the server only, except the super admin's restore — removing `deletion` (with write metadata only) when `restoreBy` is not `platform_owner` (`canRestoreOrganization`). The platform owner may restore any.
- **Write metadata** (`updatedBy` = the signed-in user, `updatedFrom`, `updatedAt`) is validated when present and never required; tombstones never carry it. A staff material status update (Send: `status`, `lastSentAt`, `lastSentRequestType`) may carry it too (1.9.0; the rule's field list refused `updatedBy` / `updatedFrom` before).

## 17. Job access and reads (1.10.0)

Reads are enforced by the security rules, not only filtered on screen. Firestore rules are not filters: an app may only run a query whose every possible result the viewer may read, so both apps build their queries from one plan.

- **Who sees which job** (`seesEveryJob(role, kind, toggles)`, `canSeeJob(viewer, job, managers, kind)`): admins and super admins outside operative mode see every job; a manager with the Projects (`permissions.projects`) or Small works (`permissions.smallWorks`) add/edit/manage permission sees every job of that kind; any other manager sees only the jobs they manage; operatives see no job list, only the jobs of their own bookings, tasks and deadlines, read one by one.
- **Who reads which bookings** (1.11.0, by kind): admins read every booking (`readsEveryBooking`). Every labour, subcontractor and job-linked manager site booking carries `jobCollection` (`projects` | `smallWorks`, `bookingJobCollectionFields`; the collection decides the kind, `jobKind`), written on create and edit by both apps. A manager with the Projects or Small works toggle reads every booking whose `jobCollection` is that kind (one-toggle managers only that kind). Every manager reads the bookings on the jobs they manage and their own; operatives read only their own labour bookings (their account id, a former or same-email id, or an `operatives` row with their email). A booking without `jobCollection` (saved before 1.11.0, until `scripts/backfill-booking-job-collection.mjs` runs) is read only by admins, its job's managers and the people it books; a manager site booking with no job (office, working from home, site survey, custom) by admins and its own manager.
- **Job queries** — `jobQueryPlan(viewer, { documentIds })` → `{ seesEvery, queries }`: per collection `{ kind: 'all' }`, `{ kind: 'managed', field: 'managerUserIds', op: 'array-contains', value: <uid> }`, or for operatives `{ kind: 'documents', ids }` (single-document reads of each id spelling; a job list is refused to them).
- **Booking queries** — `bookingQueryPlan(viewer, visibleJobIds, { ownBookingIds })` → `{ readsEveryBooking, queries }`: whole collections for `readsEveryBooking`; otherwise, for each kind the manager has the toggle for, one `jobCollection ==` <kind> query per collection (1.11.0), and per job in `visibleJobIds` (the jobs of the kinds they have no toggle for — their managed jobs) one query per collection — `bookings` and `subcontractorBookings` `projectId in`, `managerSiteBookings` `locationId in` — over that job's id spellings (`jobIdQueryValues`: as stored, plus upper case for an all-lower id and lower case for an all-upper id; a mixed-case id only as stored, since the rules could not trace another spelling to it), and their own bookings: `bookings` `operativeId in` (`OWN_BOOKING_IDS_PER_QUERY` = 4 per query) and, for managers, `managerSiteBookings` `userId ==` <uid>. Each query also takes the collection's download bound (`date >= bookingLoadStart`, §1); the composite indexes are in `firestore.indexes.json`.
- **Rules limits.** A query may look up 10 documents (`get` / `exists`) in total across all its `in` values, and a rule evaluation stops at 1000 expressions, so a booking query carries one job (`JOBS_PER_BOOKING_QUERY` = 1) and the rules compute the caller's role once per rule. `FIRESTORE_IN_QUERY_LIMIT` (30) is Firestore's own cap, not the plan's chunk.
- **Daily Overview and warnings** for a viewer who does not see every job cover only their jobs and the people booked on them (`warningScopeFor`, §5, §6).
- A viewer whose role changes, or a manager added to or removed from a job, re-plans on the next snapshot: the job leaves or joins their lists and its bookings' queries are closed or opened.
- **Job kind** (1.11.0): `jobKind(doc, collection)` — a `projects` document is a project and a `smallWorks` document is a small works job, whatever `jobType` says; `jobType` decides only when the collection is unknown. A project and a small works job sharing one id (older iOS builds) are both kept, each in its own list; `jobIdsInBothCollections` lists them for the owner and the booking backfill reports their bookings.
- **Switched by data in the rules** (1.12.1): the security rules apply this section's read scoping only when `platformConfig/app.enforcedReads` is `true` (§18; written by the platform owner only, read by the rules — one document read per rule). While it is missing or false, every member of the organisation reads every job and booking, as before 1.10.0, so the rules deploy does not wait for the backfills. Writes (§16: job create and edit, `canWriteBooking` / `canDeleteBooking`, tombstones, `jobCollection`) and every other rule are never switched by it. The apps' `ENFORCED_READS_ACTIVE` and this field are flipped together, **apps first, then the document**: the field is set true only once a release with `ENFORCED_READS_ACTIVE` true has reached every user; setting it false again is the rollback.
- **Switched off until the backfill** (1.10.1; 1.11.0 kind reads too): `ENFORCED_READS_ACTIVE` is false. While false, `jobQueryPlan` returns whole-collection job queries for staff and `readsEveryBooking` is true for every manager, so reads are as before 1.10.0; each app still shows a manager only the jobs `canSeeJob` allows. It becomes true in the release after the owner has run the backfills (`managerUserIds` and, from 1.11.0, `jobCollection`), and that release ships before the rules deploy. 1.11.0 keeps it false: its by-kind booking queries are planned only once it is true.
- Known limit: an operative can read a job document by id without the rules knowing whether they are booked on it (the rules cannot query their bookings); listing jobs is refused to them.

## 18. Forced app update (1.12.0)

One platform document says the oldest build each platform may run:

`platformConfig/app` `{ minimumIosBuild: number, minimumWebVersion?: string, enforcedReads?: boolean, organizationErasureEnabled?: boolean }` (`organizationErasureEnabled`, 1.15.0: the §20 eraser's kill switch, read only by the server)

- `minimumIosBuild` is an iOS `CFBundleVersion` (whole number). `minimumWebVersion` is dotted numbers (e.g. `1.12.0`). Both optional.
- An app reads that one document (`PLATFORM_CONFIG_APP_PATH`), before and after sign-in, and calls `appUpdateRequired({ platform, runningBuild }, config)`: true only when the running build is older than the minimum for its platform. A missing document, a missing field, a value that is not a number (iOS) or not a dotted version (web), or an unreadable running build is false — the gate never blocks by mistake. When true the app shows only the update screen.
- Anyone may read it (signed out too); only the platform owner writes it (§16). It is not organisation data and is not live: an app reads it on launch and when it returns to the foreground.
- `enforcedReads` (1.12.1) is read by the security rules, not by the apps: `true` turns on the §17 job and booking read scoping; missing or false keeps reads as before 1.10.0. It is set true only after the apps' `ENFORCED_READS_ACTIVE` release (§17, Deploy notes).

## 19. Lapsed subscription (1.13.0)

Owner decisions round 4, Q3. When the organisation's subscription has lapsed (`hasAccess(billing)` false: canceled, unpaid, paused, incomplete, or past_due more than 7 days after the failed payment), both apps are blocked — not read-only — and show only `SUBSCRIPTION_LAPSED_MESSAGE`: "The organisation's Project Planner subscription has lapsed. Please contact your system administrator and ask them to renew." and Sign out (`subscriptionAccess({ billing, viewerIsAdmin, viewerIsPlatformOwner })` → `open` | `adminBillingOnly` | `blocked`). Nothing is ever deleted; access returns as soon as Stripe marks the subscription paid. Admins and super admins (`adminBillingOnly`) also reach the billing screen — on web Settings → Billing, and nothing else (`SUBSCRIPTION_LAPSED_ADMIN_NOTE`, web only). **On iOS everyone, admins and super admins included, sees only `SUBSCRIPTION_LAPSED_MESSAGE` and Sign out** (1.14.0, owner decision, App Store guideline 3.1.3): neither `SUBSCRIPTION_LAPSED_ADMIN_NOTE` ("renew in Settings → Billing") nor `SUBSCRIPTION_LAPSED_ADMIN_WEB_NOTE` is ever shown on iPhone, and the iOS app links to no billing or renewal. Missing billing is open (trials and organisations created before billing). The platform owner is never blocked.

The security rules enforce it (§16) from two fields the Stripe webhook writes into `billing` on every sync (`billingAccessFields`): `accessOpen` (= `hasAccess` at the time) and `accessClosesAt` (the end of the 7-day grace while a payment has failed), so the grace ends on time without another Stripe event. The rules close the organisation when `accessOpen` is false or `accessClosesAt` has passed; missing fields are open, so an organisation whose billing has not synced since 1.13.0 is closed by the apps only until its next Stripe event.

## 20. Company deletion (1.15.0)

Owner decisions round 6. The canonical module is `lib/canonical/organizationDeletion.ts`.
- **Who and where.** Web only: Settings → Billing → **Delete organisation**, shown to the super admin only (`isOrganizationSuperAdmin`). iOS has no delete control (it reaches the company only through "Delete my account", §11, later). The form explains what happens (`ORGANIZATION_DELETE_BODY`) and asks for the company name and DELETE (`organizationDeleteConfirmationError`; the server checks both again). There is no data export in the apps yet; the form says to email info@projectplanner.us for a copy first.
- **What deleting does** (server, admin SDK): cancels the Stripe subscription at the end of the paid period (`cancel_at_period_end`, no refund — refunds are made by hand in Stripe), writes `organizations/{orgId}.deletion = { status: 'scheduled', requestedAt, requestedBy, eraseAfter: requestedAt + DELETION_RESTORE_DAYS (60) days, restoreBy: 'super_admin' | 'platform_owner' }` (`organizationDeletionWriteFields`), and emails the platform owner (info@projectplanner.us) and the person who deleted it through the email function's server mode.
- **Locked for 60 days** (`organizationDeletionState(org, now)` → `active` | `scheduled` (locked, `due` once `eraseAfter` passed) | `erased`). Every member of the organisation, on every platform, sees only `organizationDeletedMessage(eraseAfter, timeZone)` — "This organisation has been deleted and will be erased on {date}." (organisation zone) — and Sign out; the security rules refuse its data (§16). The super admin also sees **Restore** when `canRestoreOrganization` (the deletion was theirs, `restoreBy` `super_admin`): restore removes `deletion` and, when the subscription is still in its period, resumes it (`cancel_at_period_end` false); a subscription that has already ended is started again from Billing. A company deleted with its last member's account (`restoreBy` `platform_owner`) is restored only by the platform owner. The platform owner is never locked out.
- **Erased on day 61** by a daily scheduled Cloud Function (`eraseDeletedOrganizations`, `functions/organizationEraser.js`; `organizationEraseDue`): users whose users document names the organisation and who belong to no other organisation (their tax ids, memberships, users document and Firebase Auth account; never the platform owner), every membership of the organisation, its invitations, its Storage files under `organizations/{orgId}/`, and the organisation document with every subcollection (bookings, timesheets, `userEmails` claims, …). People who also belong to another organisation keep their account and lose only this membership. An audit row `erasedOrganizations/{orgId}` `{ erasedAt, name, status }` is kept (`erasedOrganizationAuditFields`; no personal data). The eraser is idempotent and can run as a dry run. **Kill switch:** the eraser deletes nothing unless `platformConfig/app.organizationErasureEnabled` is `true` (written by the platform owner only, §18). While it is missing, false or unreadable, every daily run is a dry run that only logs each due organisation's id, name and counts (people deleted and kept, memberships, invitations). It is deployed off; the platform owner turns it on after reviewing the first dry-run log. `functions/organizationEraser.emulator.test.js` runs the eraser against the Firestore emulator (not in CI; how to run it is in the file).

## How the rulebook changes

1. A rule change starts in `project-planner-web`: edit the function in `lib/canonical`, add a test in `lib/canonical/canonical.test.ts`, and edit this file.
2. Bump `Version:` (major: a breaking field or behaviour change; minor: a new rule; patch: wording) and add a `### <version> — <date>` entry under Changelog.
3. `npm run build:canonical` packs the script with this file's version stamped in, writes `lib/canonical/dist/canonical-manifest.json`, and mirrors the files into `../project-planner-ios` when it is checked out.
4. `npm run rulebook:handoff` writes the iOS follow-on prompt to `docs/ios-handoff/v<version>.md` and `docs/ios-handoff/LATEST.md`.
5. Enforcement: the pre-commit hook, CI (`.github/workflows/rulebook.yml`) and the Claude Code Stop hook (`.claude/settings.json`) all run `node scripts/rulebook-sync.mjs check` and refuse a change to `lib/canonical`, `firestore.rules`, `storage.rules`, `firestore.indexes.json` or this file without a version bump, a changelog entry, a fresh pack and a hand-off. A daily CI job compares the iOS repo's mirror with this version and fails when iOS is behind.
6. iOS runs `scripts/sync-rulebook-from-web.sh`, and its `RulebookParityTests` fail when its mirror, manifest or packed script differ from what web published.
7. **A write-shape change updates the cross-platform contract** (1.10.0): when an app changes what it writes to a shared collection, or a reader changes what it returns, regenerate `lib/canonical/cross-platform-contract.json` (`npx tsx lib/canonical/crossPlatformContract.samples.ts --write`; web samples come from the web writers, iOS samples are copied from the iOS payload builders named in `iosWriter`) in the same change. `crossPlatformContract.test.ts` fails until it is, and iOS `CrossPlatformContractTests` fails when its builders no longer produce `iosWritten`.
8. A gap found on iOS is reported to the web agent and fixed here first — never by diverging on iOS.

- Status synonyms are shared (`HOLIDAY_STATUS_SYNONYMS`, `normalizeHolidayStatus`): declined, denied and cancelled are rejected and requested / awaiting / submitted are pending (web read them as approved). Slot synonyms morning / afternoon read as AM / PM (`normalizeHolidayTimeSlot`) (§9).
- Unbooked labour and leave coverage match ids without case (`normalizeDocumentId`): an iOS upper-case `userId`, `operativeId` or booking `personId` matches a web lower-case id and the reverse, so leave and bookings are no longer missed by letter case; returned rows keep the stored ids (`unbookedLabourRows`, `unbookedLabourRowsOnDay`, `leaveCoverageRows`) (§5).
- §1 lists the shared document readers; `users/{uid}` documents and `operatives` roster rows are known gaps without one.
