# Project Planner Rulebook

Version: 1.27.0
Updated: 2026-11-04

This is the one rulebook for every Project Planner platform: web, iOS and (later) Android. It is written platform-neutral. Each rule names the shared function in `lib/canonical` that implements it; platforms call that function (web `@/lib/canonical`, iOS `CanonicalBusinessEngine`, Android the same packed script) and never keep a second copy.

**Where it lives.** The canonical copy is `docs/RULEBOOK.md` in `project-planner-web`. iOS keeps a byte-identical mirror at `docs/RULEBOOK.md`; the packed script carries this file's version and sha256 (`rulebookStamp()`), so a platform can prove at test time that its mirror matches the rules it runs. Never edit a mirror by hand. See "How the rulebook changes" at the end.

---

## 1. Data, sync and source of truth

- **Firebase is the single source of truth** for shared data. No shared data is kept only on a device or in a browser. Device storage is a cache or a per-device preference only.
- **Identical field names, types, defaults and enums** on every platform. Where platforms differed, the web schema wins. Shapes are listed in `ORGANIZATION_DOCUMENT_FIELDS`, `USER_DOCUMENT_FIELDS` and `OPERATIONAL_COLLECTION_PATHS`, all three in the packed script.
- **Live screens use real-time listeners.** A screen showing shared data holds a Firestore snapshot listener for it while it is open, so a save on one platform appears on the other without a refresh, a restart or a pull-to-refresh. The list is `LIVE_COLLECTIONS` (`liveCollection(id)`, `screenMustListen(id)`; an id not listed is live). Listeners are scoped to the open organisation, removed when the organisation changes or the user signs out, and never publish another company's rows. A cache may give the first paint; it is never the only read, and a time-to-live cache never stands in for a listener. The roster is `users` where `organizationId` is the open organisation; a member linked only through a membership, `userEmails` or a staff link is not in that listener and refreshes on the next full load (accepted). **Anchored people** (1.11.0, `rosterMembersForOrganization`): every key of `organizations/{orgId}.members`, the creator, and the signed-in user when listed are always on the roster, read by id when their users document names another company (the security rules let a co-member read them, `anchoredInCallerCompany`); their level in this organisation is `organizationLevelFor` — their users flags only when that document's `organizationId` is this organisation, else their membership here, else the `members` role, and the creator is always the super admin. An anchored person leaves the roster only when their users document is confirmed missing or they are removed from `members`; a denied read or a listener snapshot never removes them, and no device permanently hides anyone because a read was denied.

- **Never re-save what you didn't change.** A write happens only because the user changed that record in that action, or because the device replays such a queued action (`syncWriteAllowed(trigger)`: `userAction` and `offlineReplay` only, from `SYNC_WRITE_TRIGGERS`). Launch, return to the foreground, reconnect, a background sync, a pull-to-refresh and a listener snapshot never write records; the only exceptions are writes of a field the device itself owns (the signed-in user's `lastSeenAt`, this device's push token), seeding a starter library that is missing (`starterCollectionShouldSeed`, `missingStarterQualificationCodes`: creates only documents that do not exist) and, from 1.10.0, the idempotent key migrations in `IDEMPOTENT_MIGRATION_WRITES` (`syncWriteAllowed(trigger, migration)`): `warningResolutionMigrationWrites` writes a resolution stored under an older warning key to its shared key only when the shared key is not resolved yet, changes no data and gives the same result however often or wherever it runs, so it may run from a warnings scan or listener. Names recovered for display (job types from live jobs, `mergeJobTypeCatalogues`) are shown, never written — on load or by a later save: a job type save is the stored list plus the user's explicit adds and removes only (`jobTypesChangeWriteFields(stored, { add, remove })`, 1.10.0); a recovered name is saved only when the user adds it. A save writes only the records the user changed (`recordsToSave(records, changedIds)`) — saving one project never saves the others — and each as a partial update of its changed fields. An edit of a document that no longer exists is refused, never re-created (`editOfMissingDocumentIsRefused({ isCreate, exists, code })`): edits use an update that fails on a missing document, never a set or merge-set, and the app drops its local row and shows `EDIT_OF_MISSING_DOCUMENT_MESSAGE` ("This was deleted on another device."). A refused offline replay is final under `replayRefusedIsFinal` (`bookingReplayRefusedIsFinal` is the booking form, §2).
- **Bounded downloads.** Booking listeners start at `bookingLoadStart`: the earlier of this week's Monday and the warning window start, filtered on the booking `date`. A screen showing an older day moves the start earlier (never later); history screens ask for the full archive. The notification inbox loads the newest 150 rows for the signed-in user (`createdAt` descending).

programmes `parseDeadlineDocument` / `parseDeadlineItem` and `settings/deadlineAssignments` `parseDeadlineAssignments` / `deadlineAssignedProjectIds`, the operations collections (job material lines `parseMaterialLineDocument` / `parseMaterialListDocuments`, `materialCatalogue` `parseMaterialCatalogueDocument`, `materialSendRecords` `parseMaterialSendRecordDocument`, `wholesalers` `parseWholesalerDocument`, `siteAudits` `parseSiteAuditDocument`, `tasks` `parseTaskDocument`, `settings/jobTypes` `parseJobTypesDocument` / `coerceJobTypeList` / `canonicalJobTypeName`, `settings/tradeTypeInventory` `parseTradeTypeInventory`, the `operativeProfiles` pay mirror `parseOperativeProfileDocument`, the private pay profile `payProfiles` `parsePayProfileDocument` (1.13.0, §8)), the record collections (health & safety `parseHealthSafetyDocument`, variations `parseVariationDocument` and `variationTrackers` `parseVariationTrackerDocument`, inbox rows `parseNotificationDocument` (§13), `warningResolutions` `parseWarningResolutionDocument` / `warningResolutionRecords` (§5)), the roster fold `rosterPeople`, the people collections (`parseUserDocument` for `users/{uid}`, `parseOperativeDocument` for `operatives`, `parseManagerDocument` for `managers`, `parsePayRateHistoryDocument` / `parsePayRateHistoryDocuments` for `operativeDayRateHistory`, `parseClientDocument`, `parseSubcontractorDocument`, `parseSkillDocument`), and organisation memberships `parseOrgMembershipDocument` (§14, 1.10.0), and the organisation settings parsers (`parseCompanyDetails`, `parseOrganizationName`, `resolveOrganizationCurrency`, `parseWarningDetection`, `parseMaterialCutOff`, `parseUserNotificationPreferences`, `parseAnnualLeaveDefaults`). A reader turns stored dates into organisation-zone day keys (and epoch milliseconds), keeps ids in their stored case and uses the document id as the record id — a stored `id` field never replaces it and an id that is not a UUID is kept. Readers accept a Firestore Timestamp, `{seconds, nanoseconds}`, a Date, epoch ms or an ISO string for an instant, true/false/1/0/"yes"/"no" for a flag, and a numeric string for a number (`documentInstantMs`, `documentBool`, `documentNumber`). An array row stored without an id (a subcontractor or wholesaler contact, a task item, a site-audit item, a variation line, a timesheet entry) gets a derived id — `derivedRowId` of the parent document id, the array, the position and the row's content (`subcontractorContactId`, `wholesalerContactId`, `variationLineId`, `timesheetEntryId`) — the same on every platform and read, never random; the next save writes it. A job naming a client with no client id gets `jobClientId(jobDocId, clientName)`. A stored organisation reference may be an id, a path (`organizations/{id}`) or a DocumentReference; readers return the id (`documentOrganizationId`). `users/{uid}.organizationId` is written on create only (`userProfileWriteFields`); switching organisation never rewrites it (§14). `parseUserDocument` without the organisation's `annualLeaveDefaults` marks `annualLeaveDefaultsPending`: the app re-parses the user when the organisation document arrives and never saves those figures. Status words are one vocabulary per collection: materials `normalizeMaterialWorkflowStatus` (`draft`, `sentForQuote`, `ordered`), tasks `normalizeProjectTaskStatus` (`To Do`, `In Progress`, `Completed`), toolbox issues `normalizeHSIssueStatus` (`awaiting`, `scheduled`, `complete`, stored `completed`), signatures `normalizeHSSignatureStatus`, variations `normalizeVariationStatus`; an unknown word reads as the first value and never drops the row. **Known gaps:** none — every shared collection has a rulebook reader.
- **Cross-platform contract** (1.10.0). `lib/canonical/cross-platform-contract.json` holds, for every shared collection in `LIVE_COLLECTIONS` that has a reader, a document as web writes it, a document as iOS writes it, and what the reader returns for each (`readCrossPlatformSample(reader, docId, data, { timeZone })`; collections without a reader are `CONTRACT_NO_READER` in `crossPlatformContract.samples.ts`). It is packed and mirrored like the parity fixture (iOS `ProjectPlannerTests/CrossPlatformContract.json`; its sha256 is `crossPlatformContractSha256` in the manifest). Web `crossPlatformContract.test.ts` and iOS `CrossPlatformContractTests` read every sample through the packed readers and compare with `expected`, and each checks its own writers still produce its samples. A change to what an app writes changes the contract in the same change.
- **Writes carry metadata.** Every write to a shared document includes `updatedAt` (server timestamp), `updatedBy` (signed-in user id) and `updatedFrom` (`web` | `ios` | `android`) — `writeMetadataFields(uid, platform)`; each app adds its SDK server timestamp. Security rules never reject a write only because these are missing (older app builds). **Exception:** a booking tombstone (§2) carries only its own fields (`BOOKING_TOMBSTONE_FIELDS`) and no write metadata.
- **Partial writes only.** A save writes the fields it changed (dotted partial update) — `documentWriteFields(before, next)` → `{ set, remove }`, and for the people collections `userProfileWriteFields`, `operativeRowWriteFields`, `managerRowWriteFields`, `clientWriteFields` and `subcontractorWriteFields`: a `null` removes a field only when the stored copy has one, line manager ids and `hasNoLineManager`, pay basis and both rates, and employment type and its transition are each written together, and `id` / `createdAt` / `organizationId` are never rewritten. For the work collections: jobs `jobWriteFields` (manager ids, the address lines and the map pin each written together), edits of an existing booking `bookingUpdateWriteFields` of a manager site booking `managerSiteBookingUpdateWriteFields` (1.9.0; the slot with its clock times and break, and the location kind with its id or custom name, each written together) and of a subcontractor booking `subcontractorBookingWriteFields` (the slot with its clock times, and the firm contacts with their names, written together; `bookedBy` is never rewritten; an edit of a booking whose document is gone writes nothing and is refused, never turned into a create), a new subcontractor booking `subcontractorBookingCreateFields` (document id = its `id` field, status Confirmed when not given, `isBreakRemoved`, `bookedContactIds` and `bookedOperativeNames` always written), and one job's deadline assignees `deadlineAssignmentWriteFields` (a field-path partial update of `projects.{KEY}`, the document created only when missing, `deadlineProjectKey` = the job id upper-cased as both apps have always stored it, `deadlinesDocumentId`). For the operations and record collections (1.8.0): material lines `materialLineFields` + `materialLineWriteFields` (`date` is organisation-zone midnight of the materials day and `dayKey` is stored with it; owner fields `addedBy` / `addedByUserId` / `addedAt` are create-only; a send moves status with `materialSendStatusWriteFields`, never ordered → sent for quote), catalogue items `materialCatalogueItemWriteFields`, wholesalers `wholesalerWriteFields` (contacts with the primary contact), site audits `siteAuditWriteFields` (`createdAt` and author never rewritten; items laid over their stored rows with `mergeStoredRows`), tasks `taskFields` + `taskWriteFields` (never a whole-task `setData`), variations `variationWriteFields` and renumbering `variationRenumberWriteFields` (only the sequence and, when the number changes, the number with one appended history entry), the `operativeProfiles` mirror `operativeProfileWriteFields`, `settings/jobTypes` `jobTypesWriteFields` (the `jobTypes` field only; empty only when the user removed every stored name, `options.removed`), `settings/tradeTypeInventory` `tradeTypeInventoryWriteFields` (adds, never removes), send records `materialSendRecordCreateFields` (written once), inbox rows `notificationReadWriteFields` (`isRead` only). 1.9.0: `variationTrackers/{parentId}` `variationTrackerWriteFields(stored, action)` (enable, disable, lock, unlock, mode, renumbered — only that action's fields; enabling an existing tracker keeps its mode, prefix, padding and version), `settings/variationTrades` `parseVariationTrades` / `variationTradesWriteFields` (only the trades added or removed in that action), a variation settings log `settings/variations_{parentId}` `variationLogItems` / `parseVariationLogDocument` / `variationLogWriteFields` (an entry stored without an id gets `variationLogItemId`, a `derivedRowId`, and the next save writes it; one entry is laid over its stored entry, others are never touched). While `annualLeaveDefaultsPending`, a `users/{uid}` save leaves out `annualLeavePendingOmitFields(user, edited)`. Health & safety: whole-list saves go through `healthSafetyDocumentWriteFields` (rows laid over their stored rows by id; 1.16.1: a blank or missing `fileURL` / `fileName` (`HEALTH_SAFETY_FILE_FIELDS`) never overwrites a stored non-blank one, and two copies of the same rows — the job's nested copy and the settings document — are read as one list by `mergeHealthSafetyRowCopies`, keeping the copy that has a `fileURL`; an upload stores a download URL only, never a `gs://` address, an empty list replaces a stored one only when the user removed every stored row in that save, `options.removedIds`; `signatureRecords` never touched); removing a recipient or an issue removes those signatures with `healthSafetySignatureRemovalWrites` (field-path deletes of the matching `signatureRecords` entries and the `signatures` array without them, in the same update); a signature is `healthSafetySignatureWriteFields` — a field-path update of `signatureRecords.{issueId}__{userId}` (`healthSafetySignatureKey`) plus an `arrayUnion` of the row onto `signatures` for older builds — so two people signing at once never lose a signature, and readers fold both sources (`foldHealthSafetySignatures`, a signed copy always wins). The skills catalogue is saved with `skillsCatalogueWrites` and the material catalogue with `materialCatalogueWrites`: never delete-all and rewrite, only changed items are written, and an empty or failed load never deletes an item. **Create shapes** (1.9.0) for the documents written whole once: `invitations/{id}` `invitationCreateFields` (never UTR or VAT; marking used is `invitationUsedWriteFields`), `organizations/{orgId}` `organizationCreateFields` (billing and subscription at create only), `users/{uid}/private/taxIds` `taxIdsDocumentFields` (its only fields, written whole), inbox rows `notificationCreateFields` (created once; a row that already exists — a dedupe hit — is never rewritten, so its read state is never reset). It never rewrites a whole document from a possibly stale copy, and never deletes a field just because the local copy lacks it. A dotted key (`settings.currencyCode`) is only used with a partial update, never with a merge-set, where it would become a literal field name. Edits to an existing document — annual leave (`holidayBookings`) and timesheet drafts included — are partial updates.
- **Document ids keep their stored case.** Ids are written exactly as created (iOS `UUID.uuidString` is upper case; web ids may be lower case) and stored keys are never rewritten. Comparisons ignore case: `normalizeDocumentId` (trimmed, lower case) is used for warning resolution keys, accepted clash pairs and timesheet entry-review lookups (`resolvedWarningKeys`, `approvedWarningKeys`, `isWarningActive`, `isClashApproved`, `isClashAccepted`, `timesheetEntryDecision`).
- **Job keys.** A record that belongs to a job (material lines, send records, site audits, tasks, variations, subcontractor bookings, bookings, offline caches) stores the job's document id exactly as stored in its `projectId` / `parentId` field — never re-formatted through a UUID type, so a non-UUID or lower-case job id works on every platform. Settings documents keyed by a job use the job id upper-cased (`deadlineProjectKey`: `deadlinesDocumentId`, `healthSafetyDocumentId` → `settings/healthSafety_{projects|smallWorks}_{KEY}`; `healthSafetyDocumentIds` also lists the stored-case id older web builds wrote, read and merged). A key read back from a store, a map or a cache is mapped to the job with `storedJobIdForKey(key, jobIds)` (without case); `deadlineAssignedProjectIds(data, personIds, jobIds)` returns stored job ids.
- **Shared calculations run on each device from one packed script.** Warnings, overtime, timesheet figures, Daily Overview and pay are calculated on each device by the same packed rulebook script, not re-implemented per platform. Moving a calculation to the server (Cloud Functions) is a separate decision; until then the function named here is the exact specification (inputs, edge cases, rounding) and is locked by tests in `lib/canonical/canonical.test.ts` and `lib/canonical/parity-fixture.json`.
- **Working-hours history** (1.19.0). `organizations/{orgId}.payrollTimePolicyHistory` is an append-only list of `{ effectiveFrom: 'YYYY-MM-DD', policy }` (organisation-zone day keys; `PAYROLL_POLICY_HISTORY_START` `1970-01-01` for the rules before any recorded change), written by Apply from today, the promotion of a due scheduled change, Schedule and Cancel alongside the flat fields older builds read (`payrollTimePolicy`, `payrollTimePolicyPrior`, `payrollTimePolicyEffectiveFrom`, `payrollTimePolicyScheduled`), and `payrollTimePolicyRevision`, a counter every working-hours write bumps. Entries are never rewritten, reordered or removed; no cap is applied (an entry is about 1 KB, so the 1 MiB document limit is several hundred changes away). Both fields are in `ORGANIZATION_DOCUMENT_FIELDS`. See §4.3.
- **One business time zone per organisation**, from `organizations/{orgId}.countryCode` (`organizationTimeZone`): GB → Europe/London; missing or unknown → Europe/London. Every day key, warning window, payment run, timesheet day, cut-off clock and effective date uses this zone, with BST/GMT handled by the zone rules. Never the phone or browser zone. A day key's instant is the first instant of that calendar day in the zone (`dateFromDayKeyInZone`, `midnightInZone`, `addDaysInZone`), worked out from the zone offset at that local midnight — never from UTC noon, which in a zone at UTC+12 or later (Pacific/Auckland, Pacific/Chatham, Pacific/Kiritimati) is already the next local day (1.12.0: every New Zealand day key was one day out, so a Friday paid at Saturday rules, Mon–Fri leave counted 2 days and rate changes started a day late).
- **The week starts on Monday** and runs Monday–Sunday for every organisation. Monday–Friday are working days; Saturday and Sunday count only where a setting says so (for example "Include weekends in unbooked labour"). This is fixed, not an organisation setting.
- **Security rules enforce permissions on the server.** Firestore rules enforce role permissions, approvals and who may change organisation settings. Hiding a control in an app is never the only guard.

## 2. Offline rules

- **Web:** online only. No offline editing.
- **iOS and Android:** offline mode with restrictions. The logic is kept separate from screens so Android can reuse the same rules.

The table below is `OFFLINE_ACTIONS` (stable action ids, e.g. `booking.create`, `users.pay_rate`, `view.warnings`), read with `offlineAvailability(actionId)` → `allowedOffline` | `onlineOnly` | `readOnlyOffline`; an unknown id is online only. The messages are `OFFLINE_PENDING_SYNC_LABEL`, `OFFLINE_ONLINE_ONLY_MESSAGE` and `offlineLastUpdatedLabel(instant, timeZone)`.

**Allowed offline** (queued on the device, pushed automatically when the connection returns; each queued item shows **"Pending sync"** until the server confirms it):
- Create, edit and cancel bookings (projects and small works). Deleting a booking is online only.
- Annual leave requests.
- The user's own personal profile fields.
- The user's own notification toggles.

**Online only** (controls disabled offline with the message **"Connect to the internet to change this"**):
- All organisation settings: company details, currency, working hours and overtime (including scheduled changes), warning settings (including excluded users), payment runs, material order cut-off and schedule options (including custom items).
- All Manage Users changes: role, line manager, employment status, day/hourly rate and effective dates, exclusions, inactive flag, invites.
- Approvals: annual leave approval, timesheet signing, clash approvals.
- Account actions: sign-in, password changes, switching organisation.
- Deleting a booking (the delete and its tombstone are never queued).

**Read-only offline.** Daily Overview, warnings, weekly reports and My Schedule show the last synced data, labelled "Last updated [date/time]" in the organisation zone (`offlineLastUpdatedLabel`, e.g. "Last updated 24 Oct 2026, 14:05"), and are never recalculated from unsynced local changes.

**Conflicts.**
- Last write wins, by server timestamp.
- A booking cancelled or deleted on another device cannot be brought back by an offline edit. Deleting a booking (`bookings`, `managerSiteBookings` or, from 1.10.0, `subcontractorBookings`) writes a tombstone at `organizations/{orgId}/deletedBookings/{bookingId}` in the same batch (`bookingTombstonePath`, `bookingTombstoneWriteFields`; the app adds the server `deletedAt`). A tombstone carries only `bookingId`, `collection`, `deletedAt`, `deletedBy` and `deletedFrom` — no write metadata. Security rules refuse any later create or update of that booking id. Who may create, edit, cancel or delete a booking — labour, manager site or subcontractor — is `canWriteBooking` / `canDeleteBooking` (1.10.0, owner decision; §16): admins every booking; managers the bookings on a project or small works they manage (and their own office / working-from-home / site-survey bookings); operatives never. Apps show Delete to exactly those people. Only they can move a booking off `Cancelled`. **Deleting a person or a job** removes only their bookings dated today or later in the organisation zone (`bookingsToRemoveOnOperativeDelete` — every id of the person, never a name — and for a job `jobDeleteBookingRemovals` (1.10.0): its labour bookings, its subcontractor bookings and the manager site bookings at the job), each with its tombstone in the same batch; past bookings stay as history with their stored names (a job's show `ORPHAN_BOOKING_LABEL`); deactivating or archiving a person removes nothing. No platform deletes all of a person's bookings or deletes one without its tombstone. A refused replay is final (`bookingReplayRefusedIsFinal({ code, isCreate })`): permission-denied always, and not-found when the queued item edits or cancels a booking (`isCreate` false), so an edit of a booking deleted elsewhere is never turned into a create (the general rule for every collection is `replayRefusedIsFinal` / `editOfMissingDocumentIsRefused`, §1). The device removes the queued item, drops the local row and shows `BOOKING_REPLAY_REFUSED_MESSAGE` ("This booking was cancelled or deleted on another device").
- Double bookings created offline are not blocked; warnings pick them up after sync.
- **A new booking never replaces or hides another** (1.20.2). A create always writes a new document id (never a caller-chosen or derived id, never a merge onto an existing document). A booking request is skipped as "already booked" only when it is the same booking — same person, day, slot, place and, for custom hours, the same start, finish and break toggle (`bookingRequestIdentity`, `isSameBookingRequest`; ids and names without case). Lists show one row per stored document. Before 1.20.2 web My Schedule (self-booking) and Book labour (manager bookings) compared person, day, slot and place only; weekend bookings are all custom hours, so a second Saturday / Sunday booking at the same place with other times was dropped after its double-booking row was ticked ("That time is already booked."), and My Schedule folded two such stored bookings into one row.
- Queued writes to online-only areas are refused by the security rules when they replay.

## 3. The data flow (in order)

1. **Scheduling** (projects and small works) books people onto days.
2. **Daily Overview** is a snapshot of each day: who is booked (and on what), who is unbooked, who is on annual leave. It is driven by bookings, annual leave and organisation settings.
3. **Warnings** consume the same day data plus warning settings and organisation settings.
4. **Weekly Report** is an extraction of Daily Overview and warnings for a chosen date range.
5. **Timesheets** are fed by bookings, annual leave, working hours/overtime rules, payment runs and each person's effective-dated employment profile.
6. **My Schedule** is each person's own view of their bookings and annual leave.

A change upstream flows to everything downstream on every platform.

## 4. Organisation settings

All organisation settings live on `organizations/{orgId}` and are identical on every platform. They are online-only edits, saved only when the user presses **Save**, and a save on one platform appears on the other through the live listener. Settings screens keep an unsaved draft and only refresh it from the server while the draft is unchanged. A value that looks like the factory default on the server is still the server value — no platform re-saves its own cached copy over it.

### 4.1 Company details
Flat fields on the organisation document: `name`, `officeAddressLine1`, `officeAddressLine2`, `officeCity`, `officeCounty`, `officePostcode`, `countryCode` (two letters, GB when missing), `documentAbbreviation` (1–3 characters), `companyLogoURL`, `defaultLatitude`, `defaultLongitude`, `bankHolidayRegionId` (`parseCompanyDetails`, `companyDetailsWriteFields` → `{ set, remove }`, `companyDetailsValidationError`). A legacy nested `officeAddress` map is read only as a fallback and every save deletes it. Blank optional fields are deleted, never saved as empty text; with no office, all address fields are deleted. A missing map pin leaves the saved pin alone. A blank name is never saved (`organizationNameWriteFields`). The country sets the business time zone and the default currency.

**Country change asks for the bank-holiday region.** Regions are one shared list, `BANK_HOLIDAY_REGIONS` (`{ id, title, countryCode, subdivisionCodes? }`; ids are stored and never renamed: `GB-ENG-WLS`, `GB-SCT`, `GB-NIR`, `GB`, `IE`, `US`, …; the older web id `GB-ENG` reads as `GB-ENG-WLS`, `normalizeBankHolidayRegionId`). A company's pickers offer only `bankHolidayRegionsForCountry(countryCode)`; the default is `defaultBankHolidayRegionForCountry` (GB → `GB-ENG-WLS`, `DEFAULT_BANK_HOLIDAY_REGION_ID`; a country with one region → that region; none listed → null). When Company Details changes the country and the saved `bankHolidayRegionId` does not belong to the new country, `companyDetailsRegionPrompt(previous, next)` is `{ required: true, choices, defaultRegionId, message }` and the save is refused (`companyDetailsValidationError`, "Choose the bank holidays for {country}.") until a region from `choices` is picked; the region picker is pre-selected with the default. The same country never asks again. `companyDetailsWriteFields` writes the new `countryCode` and `bankHolidayRegionId` (and `settings.bankHolidayRegionId`) in one partial update; a new country with no listed regions removes the old region. With no saved region, the company's country default applies (`parseCompanyDetails`).

**Countries at launch** (1.13.0, owner decisions round 4, Q6): every country picker — Company details and organisation setup — offers only `LAUNCH_COUNTRY_CODES` (GB, IE), through `launchCountryOptions(stored)`. A company that already stores another country keeps it: the picker lists it as well, so it is shown and saved unchanged. Other countries come later.

### 4.2 Currency
One organisation currency (`resolveOrganizationCurrency`), chosen from `CURRENCY_OPTIONS` (GBP, EUR, USD, CAD, AUD, NZD, SEK, NOK, DKK, PLN, AED). Until one is saved it defaults from the country (`defaultCurrencyForCountry`; GBP when unknown). A save writes `currencyCode`, `currency` and `settings.currencyCode` as one partial update (`organizationCurrencyWriteFields`). Older iOS builds also wrote a top-level field literally named `settings.currencyCode`; `resolveOrganizationCurrency` reads it last, so it is harmless and is left in place (an optional one-off clean-up may delete it with `FieldPath(['settings.currencyCode'])`). Every money figure — timesheets, rates, invoices, weekly report, exports, PDFs — is shown with `formatMoney(amount, currency)`. Subscription prices are billing, not organisation money.

### 4.3 Working hours and overtime
`payrollTimePolicy`: standard day window, break, weekday overtime multiplier, Saturday and Sunday rules, paid break (1.20.0: the Monday–Friday paid hours are derived from these, below). Limits for every platform (`validatePayrollTimePolicy`): paid hours 1–12 (1.20.0: the derived weekday day), break 0–120 minutes inside the working day, multipliers 1–3. The standard day and the AM/PM split of a **stored** AM / PM booking are `halfDayWindows` (the legacy booking split); annual-leave halves are `leaveHalfDayWindows` (§9); no platform computes a midpoint itself.

**The Monday–Friday working day** (1.20.0, owner decisions). The firm sets the start, the finish and the lunch break (Paid / Unpaid, its length and its start–end) — nothing else. There is **no manual "counts as" or paid-hours figure for Monday–Friday** on any platform (web Working hours, the setup wizard, iOS): the paid hours of a weekday full day are finish − start − the unpaid break (a paid break takes nothing off) — `derivedWeekdayPaidHours(policy)`. Under Monday–Friday, Working hours shows the live calculation `weekdayPaidDayPreview(policy).line`, e.g. "06:30–14:30 = 8h − 45 min unpaid break = 7h15m" (paid break: "10:00–18:00 = 8h, 30 min break paid = 8h"). **Compatibility, no re-pricing:** every 1.20.0 working-hours save (Apply from today, Schedule, the setup wizard's first save) marks the saved policy `paidHoursDerived: true` and writes `standardPaidHours` = the derived value, so older builds that read `standardPaidHours` agree (`withDerivedWeekdayPaidHours`, applied inside `payrollTimePolicyApplyNowWriteFields` / `payrollTimePolicyScheduleWriteFields`). A policy without `paidHoursDerived` — the current policy, prior, scheduled change or history entry saved before 1.20.0 — keeps its stored `standardPaidHours` exactly as before. The weekday paid day everywhere it is used — what FULL DAY and a stored AM / PM pay, the day a day rate is divided by, the weekly-report day unit, invoices, Daily Overview, My Schedule, Home — is `weekdayPaidHours(policy)` (derived when `paidHoursDerived`, else the stored figure; `parsePayrollPolicy` also reads a derived policy's `standardPaidHours` as the derived value). Validation: the derived day must be 1–12 hours ("The working day must give between 1 and 12 paid hours (finish − start − unpaid break).") and the break window must fall inside the day. Saturday and Sunday keep their own "counts as" hours (1.19.0), unchanged. Owner example 06:30–14:30, break 10:00–10:45 unpaid 45 min: FULL DAY 7.25h; custom 06:30–12:00 = 4.75h; 11:00–14:30 = 3.5h; 06:30–16:30 = 7.25h + 2h at the weekday overtime rate.
**Time steps** (1.20.2, 1.20.3, owner decisions, final). The working day's clock times — the Monday–Friday start and finish (`standardDayStart`, `standardDayEnd`) and each weekend day's set-window start and finish (`definedWindowStart`, `definedWindowEnd`) — are on a 30-minute step (:00 or :30; `PAYROLL_POLICY_TIME_STEP_MINUTES` = 30, `payrollPolicyTimeOnStep`); one off it is refused with "Working hours use 30-minute steps (e.g. 07:30)." (`PAYROLL_POLICY_TIME_STEP_MESSAGE`). The lunch break's start and end (weekday `breakWindowStart` / `breakWindowEnd` and each weekend day's own) and the break **length** (`unpaidBreakMinutes`, each weekend day's `breakMinutes`: 0, 15, 30, 45 … 120) are on a 15-minute step (1.20.3; `PAYROLL_BREAK_TIME_STEP_MINUTES` = 15, `payrollBreakTimeOnStep`, `payrollBreakMinutesOnStep`) — e.g. 10:00–10:45, 45 min; one off it is refused with "Lunch break times and length use 15-minute steps (e.g. 10:45)." (`PAYROLL_BREAK_TIME_STEP_MESSAGE`). `validatePayrollTimePolicy(policy, previous)` checks the day times first, then the break. A value stored off its step before the step applied is shown as stored and passes until it is changed (`previous` = the saved policy). Pickers offer 30-minute day times and 15-minute break times, and the break-length stepper moves in 15 minutes (web dropdowns and stepper, iOS pickers). The deduction stays the covered part of the break window up to the length (owner: 10:00–10:45 unpaid → 45 min off a booking that covers it). The pay rule already works in minutes, so half hours are priced exactly. Booking custom times keep their own 15-minute step.
Limits also cover weekend "counts as" hours (1–12) — `PAYROLL_POLICY_LIMITS`. **On read** (1.12.0) `parsePayrollPolicy` puts every stored number into those limits: a missing, blank or non-numeric value is the default; paid hours of 0 or less are the default (8); anything else is clamped (paid hours 1–12, break 0–120 minutes, every multiplier 1–3; a weekend "counts as" 0 is kept, §5). A bad stored value can no longer reach pay.

A change is either applied from today or **scheduled** from a chosen date after today (`payrollTimePolicyScheduled { policy, effectiveFrom }`, day keys in the organisation zone). The rules in effect on a day (`effectivePayrollTimePolicy(org, dayKey)`, `payrollTimePolicyForDayFromState`, `payrollTimePolicyTimeline`) are: the scheduled change once its day has arrived (even before any app promotes it); otherwise (1.19.0) the latest `payrollTimePolicyHistory` entry whose `effectiveFrom` is on or before the day (entries on the same day: the later one), with the current policy counting from `payrollTimePolicyEffectiveFrom` so a save by an older build that writes only the flat fields still counts from its day (`payrollTimePolicyHistoryEntries`); a day before the first entry uses the first entry. A company with no history reads as before 1.19.0: before `payrollTimePolicyEffectiveFrom`, `payrollTimePolicyPrior`; otherwise `payrollTimePolicy`. Before 1.19.0 only one prior policy was kept, so a third change re-priced every day before the second-to-last change; the history ends that. **Seed:** the first working-hours write after 1.19.0 backfills the history from the existing fields — `[{ 1970-01-01, prior }, { effectiveFrom, current }]`, or just the current policy — so no rules are lost (`parsePayrollTimePolicyHistory`).
- **Apply from today** (`payrollTimePolicyApplyNowWriteFields`) saves the new rules, keeps yesterday's rules as the prior, sets today as the start, removes a scheduled change that is already due and keeps a future one; 1.19.0: appends the due change (at its day) and today's entry to the history.
- **Schedule** (`payrollTimePolicyScheduleWriteFields`) replaces any pending change; a due change is promoted first (into the current policy and the history) so it is not lost. There is only ever one pending change; it is not history until its day.
- **Cancel** (`payrollTimePolicyCancelScheduleWriteFields`) removes a pending change, never a history entry.
- **Two admins** (1.19.0): every working-hours save runs in a Firestore transaction that reads the organisation document, refuses the save when the working hours changed since the screen loaded them — a different `payrollTimePolicyRevision`, or different stored rules from an older build that does not bump it (`payrollTimePolicySaveConflict(baseOrgDoc, liveOrgDoc)`, `PAYROLL_POLICY_STALE_SAVE_MESSAGE`: "Someone else changed the working hours while you were editing. Your change was not saved — check the latest working hours and try again.") — and computes the write fields from the fresh document. One admin can never silently replace or cancel another's change. Every write is a partial update of the working-hours fields only.
No save ever cancels a scheduled change it was not asked to cancel. Every screen that prices or labels a day — timesheets (lines, totals, reviews, invoices), weekly report (pay rows, the timesheet feed and the day units of each row), Daily Overview, warnings, booking pickers and their hours previews and timelines, schedule summaries and Home "Up next" — uses the policy in effect on that day in the organisation zone (1.19.0: the whole policy state is passed, `effectivePayrollTimePolicy` / `payrollTimePolicyForDayFromState`, never only the current policy and never today's rules for another day; a change scheduled to start inside a pay run prices the days before it on the old rules and the days from it on the new ones). A signed timesheet (`weeklyReportOverride`, the signed snapshot) is never re-priced (§8).

**Weekend lunch breaks** (1.19.0, owner decisions). Each weekend day has its own lunch break: `saturday` / `sunday` `{ breakPaid, breakMinutes, breakWindowStart, breakWindowEnd }`. **`breakPaid` missing means paid**, and a missing length or window is the weekday one (`unpaidBreakMinutes`, `breakWindowStart`–`breakWindowEnd`) — the one fallback is `weekendBreakFor(policy, weekendDay)` — so data saved before 1.19.0 reads unchanged. Limits are the weekday ones (`validatePayrollTimePolicy`: 0–120 minutes; the window must form an interval). Working hours shows, for both weekend modes (set window, every hour at N×), "Lunch break on Saturday: Paid / Unpaid", its length and start–end, prefilled from the weekday break (`weekendLunchBreakCopy`); "Sunday same as Saturday" copies them. Whether a day takes a break off is `unpaidBreakAppliesOnDay(policy, dayKey)` (weekday: `breakPaid` not true; weekend: that day's `breakPaid === false`; both: a length above 0); the day's break is `payrollBreakOnDay`. The deduction is the weekday rule (`breakDeductionMinutes`) with that day's break: the part of the day's break window the booking covers, up to the day's length; the booking's "No unpaid break" (`isBreakRemoved`) cancels it on weekends as on weekdays; a named AM / PM never takes it. Booking pickers offer the toggle and `customHoursBreakWarning` (against the day's own window) on a weekend day only when that day's break is unpaid. **An unpaid break is plain hours, never multiplied** (1.20.3, owner decision, final; before 1.20.3 a break in multiplied hours came off before the multiplier). **Set window:** the deduction comes from whichever hours it falls in — inside the window, off the credited "counts as" hours as plain hours (pro rata for partial cover, as before); outside the window, the outside hours are multiplied first and the break then comes off as plain hours: (outside clock hours × N) − break. **Every hour at N×:** clock hours × N − break. In `payrollHoursResult` a multiplied segment with a break keeps `paidHours` = clock × N − break and `baseHours` = clock − break / N, so `outsideHours × outsideMultiplier` (what timesheets, weekly report and invoices pay) is exactly that; `payrollOutsideClockHours(result)` gives the clock hours at the multiplier and the break taken off them, for display. Monday–Friday is unchanged (the break sits in the standard window, no multiplier). Owner's examples: Saturday window 07:30–14:00 counts as 8h, break 12:00–12:30 paid → 8h, unpaid → 7.5h; Saturday break set to 45 min 11:30–12:15, unpaid → 8 − 0.75 = 7.25h; Saturday unpaid, 07:30–11:00 → 8 × 3.5 / 6.5 = 4.31h, no break; Sunday every hour ×2, 07:30–14:00, 30-minute break paid → 6.5 × 2 = 13h, unpaid → 6.5 × 2 = 13 − 0.5 = 12.5h (1.20.3; 12h before), unpaid with No unpaid break → 13h; Saturday window 07:30–11:00 counts as 4h, outside ×2, booked 07:30–14:00 with the unpaid break in the outside hours → 4 + 3 × 2 − 0.5 = 9.5h (1.20.3; 9h before). Stored weekend FULL DAY / AM / PM keep being paid as stored; the break comes off a FULL DAY only if that day's break was unpaid on the day worked (the policy in effect then). `payrollHoursResult` returns `unpaidBreakHours` (and each segment its own), and the booking breakdown rows show it in the Mon–Fri style (below). **Older app builds do not read the weekend break fields** and pay every weekend hour (and their Working hours save drops them); `minimumIosBuild` (§18) must be raised to a build that does before any company switches a weekend break to Unpaid or sets its own weekend break. No "under-booked hours" warning is added. Under Saturday and under Sunday, Working hours shows the same live calculation Monday–Friday has: that day's window (or every hour at N× over the standard day), its break (paid / unpaid, window, length, and the minutes the pay rule takes off) and the paid hours with the multiplier — `weekendDayPreview(draft, weekday, timeZone)` → `{ start, end, summary, rows }`, priced only by `weekendBookingBreakdown` (`payrollHoursResult`) from the policy being edited, so it changes the moment that day's break is switched Paid / Unpaid or its length or times change (1.20.3; e.g. "07:30–14:00 counts as 8h · Unpaid break 12:00–12:30, 30 min — 30 min taken off · 7.5h paid"). A weekend day is judged on its own break length: `unpaidBreakAppliesOnDay` no longer requires the weekday length to be above 0 on Saturday or Sunday (1.20.3). The timeline in every booking picker draws the day's own window (`payrollDayWindows`: the weekday standard day, a set-window weekend day's window, none on an every-hour day) and that day's unpaid break only when it applies. **Weekdays** (1.20.0): new bookings are FULL DAY or custom hours; a stored AM / PM keeps the standard day's break split (`halfDayWindows`), and every weekday figure follows the organisation's start, finish, break paid / unpaid, length, window and multipliers (`standardDayCoverage`); Saturday and Sunday stay custom hours only. **The setup wizard** (1.23.0) offers the same weekend lunch-break controls as Settings → Working hours for each of Saturday and Sunday — Paid / Unpaid, length, start and end — from the same helpers (`weekendBreakFor`, `weekendLunchBreakCopy`) on the same 15-minute steps (`PAYROLL_BREAK_TIME_STEP_MINUTES`, `payrollBreakTimeOnStep`); its Monday–Friday break length steps by 15 minutes too (it stepped by 5, which the save then refused). The wizard checks the working hours with `validatePayrollTimePolicy` (weekend breaks included) when leaving that step and again before setup completes (1.23.1, web `orgSetupWorkingHoursError`); before 1.23.1 it never ran the check.

The working week is `WORKING_WEEK` (`isStandardWorkingWeekday`): Monday–Sunday, Monday–Friday working.

**Weekend bookings** (1.13.0, owner decisions round 4, Q2). Saturday and Sunday bookings are **custom hours only** on every platform, whatever the organisation's weekend setup: no FULL DAY, AM or PM. Every booking picker offers `allowedTimeSlotsOnDay(dayKey, policy, timeZone)` — CUSTOM on Saturday and Sunday (`WEEKEND_TIME_SLOTS`), FULL DAY and CUSTOM on weekdays (`WEEKDAY_TIME_SLOTS`, 1.20.0: AM and PM are no longer offered Monday–Friday; `timeSlotAllowedOnDay`). Every picker — Book Labour, Quick Add, the project and small-works scheduler, edit booking, My Schedule self-booking, manager site bookings, subcontractor flows and quick-select chips — takes its buttons from this function and hard-codes none. A stored AM / PM booking is never rewritten: it is shown as stored, its edit sheet keeps offering its own slot, and it is paid exactly as before (half the weekday paid day, on the `halfDayWindows` split). When the day's rule is a set window ("standard window + overtime"), the custom-hours editor opens prefilled with that window (`weekendCustomHoursDefault(policy, isoWeekday)` → `{ start, end }`, e.g. 07:30–13:00; Sunday "same as Saturday" uses Saturday's); when the day pays every hour at one rate it is null and the editor opens with its usual times. The prefill is a convenience: the person changes it freely. Under every weekend picker the apps show `weekendBookingNote(policy, weekday)` — "Saturday is paid on the hours you enter: 07:30–13:00 counts as 8h, hours outside it at 2×. Change it in Working hours." or "Sunday is paid on the hours you enter, every hour at 2×. Change it in Working hours." (the day's own values). **A selection of several days** shows `weekendBookingNotes(policy, dayKeys, timeZone)` (1.17.0): with both Saturday and Sunday selected and the same rule on both (same window, counts-as hours and rate outside it, or both every hour at the same rate) one line, "Saturday/Sunday is paid on the hours you enter: …"; with different rules the Saturday line, then the Sunday line; with only one weekend day exactly that day's line; with no weekend day none. `policy` may be the organisation's policy state, so each day is read under the working hours in effect on that day (`effectivePayrollTimePolicy`). Each booked day keeps its own prefill (`weekendCustomHoursDefault` for that day); a picker that holds one time pair for the whole request opens it with the first selected Saturday's — never a computed midpoint. **The custom-hours pair follows the selection** (1.18.0, owner decision): a picker's one start/finish pair for the request is `customHoursPrefillForDays(policyOrState, dayKeys, timeZone)` → `{ start, end, kind }` — `kind` `weekend` (only Saturdays and Sundays: the first selected weekend day that has a set window, Saturdays first — so with Saturday every hour at N× and Sunday on a window, Sunday's window (`weekendCustomHoursDefault`); neither has a window, the editor's usual times, the standard day), `weekday` (only Monday–Friday: the organisation's standard day `halfDayWindows(policy).day` in effect on the first selected day), `none` (a refused weekday and weekend mix; the picker leaves the times alone), or null with no day. The moment the selection changes kind (weekend only ↔ weekday only) the picker sets start and finish to the new result; within the same kind it leaves them, so the person's own edit survives adding another day. A picker that keeps one pair per day uses the same function for that day. Pickers read the weekend rule, prefill and break warning under the working hours in effect on the booking day, not today's. **One request never mixes weekdays and weekend days**: every multi-day booking picker refuses it with `WEEKEND_WEEKDAY_MIX_MESSAGE` ("Weekends cannot be booked alongside Weekdays. Make your weekday booking first then weekend separately.", `bookingDaysMixWeekdayAndWeekend(dayKeys, timeZone)`); quick selections of several days skip Saturday and Sunday. Saturday and Sunday may be booked together whatever their rules. **Per-day hours for a weekend booking** (1.18.0, owner decision): every booking screen shows a Saturday or Sunday booking's hours as one row per selected day, `weekendBookingBreakdown(policyOrState, dayKeys, start, end, isBreakRemoved, timeZone)` → `{ dayKey, weekdayLabel, start, end, workedHours, countsAsHours, standardHours, overtimeHours, multiplier, paidHoursEquivalent, line }[]`, each priced only by the pay rule timesheets use (`payrollHoursResult`) under the working hours in effect on that day — the break exactly as pay takes it (1.19.0: on a weekend day only when that day's break is unpaid), with `unpaidBreakHours` and `lines` (set hours / unpaid break / outside hours × rate / total, the Mon–Fri style), e.g. "Saturday 07:30–14:00 = 8h − 0.5h unpaid break = 7.5h" and (1.20.3) "Sunday 07:30–14:00 = 6.5h × 2 = 13h − 0.5h unpaid break = 12.5h". Example: Saturday window 07:30–14:00 counts as 8h, Sunday every hour at 2×, booked 07:30–14:00 → "Saturday 07:30–14:00 = 8h (counts as a full day)" and "Sunday 07:30–14:00 = 6.5h × 2 = 13h". Days with identical figures may be shown as one "Saturday/Sunday" row. These rows replace the weekday standard-day summary in every booking confirm step and hours breakdown for a weekend selection; no app computes weekend hours itself. Stored weekend FULL DAY / AM / PM bookings are never rewritten; they are shown as stored and paid as §8 says.

### 4.4 Annual leave settings
`annualLeaveDefaults { daysPerYear, startMonth, endMonth, carriesOver }` (defaults 25, 1, 12, false) and the bank-holiday region, saved together in one write. The region picker offers only the company country's regions (`bankHolidayRegionsForCountry`); the country is changed in Company details (§4.1). Allowance, the leave year and a one-year override are `annualLeaveBalance`. **A leave year is always 12 months** (1.12.0): it ends the month before it starts (`leaveYearEndMonth`: January → December, April → March). A save of the organisation defaults or of a person's leave year whose end month is not `leaveYearEndMonth(start)` is refused (`validateAnnualLeaveDefaults`, `validateLeaveYearMonths`, `LEAVE_YEAR_MONTHS_MESSAGE`); the pickers move the other month with the one chosen. A stored mismatch (saved before 1.12.0) reads as 12 months from its start month (`leaveYearBounds`), so no leave falls outside every year and no year runs 13 months. Changing the region never recounts or rewrites existing leave records: day counting (`leaveRecordDayKeys`, `annualLeaveBalance`) uses the region in effect when it runs. The start month for a chosen end month is `leaveYearStartMonth(endMonth)` (1.13.0; the inverse of `leaveYearEndMonth`) — no app computes it itself.

**Pro rata and carry-over** (1.13.0, owner decisions round 4, Q4). A person's start date is `users/{uid}.employmentStartDate` (a `YYYY-MM-DD` day key, set on Manage Users by whoever manages their leave; never the person, never the account's `createdAt`). The leave year they joined in is pro rata (`proRataLeaveAllowance`): days per year × the calendar days from the start date to the year's last day ÷ the days in that year, rounded up to the next half day; a year that ended before the start date gives 0, and a year that began on or after it gives the full allowance. `annualLeaveBalance` (`employmentStartDayKey`) reports `yearEntitlement` and `proRata`. Carry-over (when `carriesOver`) is the previous year's own allowance (pro rata in the year joined) less the leave taken in it, capped at the optional organisation setting `annualLeaveDefaults.maxCarryOverDays` (`parseMaxCarryOverDays`; null or missing = no cap — every organisation saved before 1.13.0 has none; the settings screen suggests `SUGGESTED_MAX_CARRY_OVER_DAYS` = 5 and saves only what the admin enters). Both apps write `maxCarryOverDays` with the rest of `annualLeaveDefaults` and never drop it.

### 4.5 Payment runs (the invoicing period)
Two modes (`invoicing.paymentRunMode`):
- **Set payment run date ranges** (`date_ranges`): two runs per month on fixed days, e.g. 1st–15th and 16th–last day. "16th–31st" means 16th to the last day of that month in 28, 29, 30 and 31-day months. Run 1 starts on the 1st and must end by the 27th so run 2 exists every month; run 2 starts the day after and ends on the 31st (`validateInvoicingSettings`, `PAYMENT_RUN_1_LAST_END_DAY`). A run is paid on its payment day: the first one on or after the run ends, otherwise that day next month (clamped to short months).
- **Recurring timeframe** (`recurring_timeframe`): a weekly work period (e.g. Monday–Sunday) paid in arrears on the first pay weekday after the period ends (e.g. the following Friday) — `paymentWeekdayAfterPeriodEnd`, shared with timesheet reminders.

The **active payment run** is the work period that contains today in the organisation zone (`invoicingPeriod`); if no date-range run contains today, the run with the latest end day. Its pay date is `paymentRunPayDate`. The summary shown to users is `activePaymentRunSummary(invoicing, now, timeZone)`: `{ start, end, payDate, label }`, e.g. "Mon 26 Oct – Sun 1 Nov · paid Fri 6 Nov", or `{ notConfigured: true }` when the organisation has no payment runs.

### 4.6 Warning settings
`warningDetection { detectClashes, clashLookaheadMode, clashLookaheadDays, includeWeekendsForUnbookedLabour, excludedUserIdsFromUnbookedWarnings, weekendCoverage }`, parsed by `parseWarningDetection`. See §5.

**Weekend hours to cover** (1.19.0, owner design). When "Include weekends in unbooked labour" is on, Warning settings shows two more toggles, **Saturday** and **Sunday**; each, when on, shows an "Hours to cover" start–end (e.g. Saturday 07:30–14:00, Sunday 08:00–13:00). Stored as `warningDetection.weekendCoverage = { saturday: { enabled, start, end }, sunday: { enabled, start, end } }` (`parseWeekendCoverage`; `start` / `end` `HH:MM` or null). Defaults when missing: `enabled` = `includeWeekendsForUnbookedLabour`; the window = that day's working-hours set window if it has one, else the standard day (`resolveWeekendCoverageDay(coverage, includeWeekends, policy, day)`, read under the policy in effect that day) — so existing settings behave as today. Turning include-weekends on starts with both days on. Include-weekends off hides the toggles and scans no weekend day. The settings save writes the whole `weekendCoverage` map as one field of the partial update (`warningDetectionFirestoreFields` → `warningDetection.weekendCoverage`).

### 4.7 Material order cut-off
`settings.materialCutOff { materialOrderCutOff, materialCutOffHour, materialCutOffMinute, materialCutOffOnSaturday, materialCutOffOnSunday }` (`parseMaterialCutOff`, `resolveMaterialCutOffClock`). A missing hour defaults to 16:00; a saved 15:30 stays 15:30. A user's notification preferences never hold the clock.

### 4.8 Schedule options
`settings.myScheduleOptions { showOffice, showWorkingFromHome, showSiteSurvey, customItems[], customItemEnabled{name: bool} }`. Missing flags mean on. Every location picker offers exactly `enabledScheduleLocations(options)`. A save writes exactly the list on screen, with names de-duplicated ignoring case (`scheduleOptionsWriteFields`) — it never merges back a deleted item.

## 5. Warnings

Warnings refresh whenever bookings, leave, settings or users change, and when the day changes (midnight in the organisation zone, and when the app or tab returns to the foreground).

**Detection period** (`coverageWindow`):
- **Set number of days:** today through N calendar days including today (2 = today and tomorrow). N is a whole number 1–365; a missing, blank, non-numeric or below-1 value falls back to 7 and both the settings screen and the Warnings screen show the notice `warningLookaheadFallbackNotice(reason)` (`coverageWindow` → `fallbackReason`, `parseWarningDetection` → `clashLookaheadDaysFallback`, never saved) — never a silent failure.
- **Invoicing period:** every past, present and future day of the active payment run. Selecting it shows the **invoicing schedule summary** (`activePaymentRunSummary`); with no payment run configured the screen asks the user to set one up. The summary is hidden for the other two options.
- **Full week:** Monday–Friday of the current week, including days already past. Saturday and Sunday are added for unbooked labour only when "Include weekends in unbooked labour" is on.
- **Unbooked days** (`unbookedScanDays`): the window above; in Full week with include-weekends on it runs to Sunday. Saturday and Sunday are scanned only when include-weekends is on, in every mode. 1.19.0: a Saturday or Sunday whose `weekendCoverage` toggle is off is not scanned (`unbookedScanDays` takes `weekendCoverage`); the weekend "counts as" hours no longer decide anything here.
- **Clash days** (`clashScanDays`): clashes follow the scan window. In Full week, a Saturday or Sunday of the current Monday–Sunday week is also checked when it has a booking. Set number of days and Invoicing period are calendar days, so their weekends are always checked. The include-weekends toggle never affects clashes.

**Warning types and severity:**
- **Booking clashes** — a person double-booked on the same date. Operative clashes are **High** (`operativeClashGroups`); manager/admin overlaps are **Medium** (`managerClashGroups`). Who counts as a manager or admin for that split is one rule (1.23.0, audit finding 20): `clashManagerIds(roster)` — active people at the admin level (super admin, `adminAccess`, the admin role) or with the manager flag (stored top level or in `permissions`; with neither stored, the manager role), the rule both apps already used; a person with no level flag is on the Managers list (§11) but their clashes stay operative clashes. A named slot (Full day, AM, PM) is read under the working hours in effect on the booking's own day (1.23.0: the scans take the organisation's working-hours state, `standardDayOn`), never today's. Both group a person's bookings per day (the person is `bookingPersonKey` / the roster account, so former ids, same-email ids and catalogue rows are one person) by overlapping clock intervals; touching times do not clash, and A–B plus B–C is one cluster. **Overnight bookings** (1.13.0, owner decisions round 4, Q5): a booking whose finish is before its start crosses midnight, and its interval is the real clock time on its start day (`slotInterval`: 22:00–06:00 is 22:00 to 30:00). It also sits on the next morning (`overnightCarryInterval`), so it clashes with that day's bookings that start before it ends (a 05:00 start clashes with a night shift ending at 06:00; a 06:00 start only touches). Such a clash is listed on the later day; two overnight bookings on one night are one clash on their own day. The same applies to the timesheet overlap flags (`overlappingBookingIds`), which also read each booking's named slot under its own day's working hours (1.23.0). Weekend bookings (custom hours only from 1.13.0, §4.3) clash on their clock hours; a stored weekend FULL DAY with no clock times occupies that weekend day's own Full day window (1.23.1, `bookingStandardDayOn`: `weekendFullDayWindow` — the set window, or the standard day when the day pays every hour at the multiplier), an AM / PM its half split at that day's own lunch break; never the Monday–Friday day. The timesheet overlap flag and leave cover read a weekend day the same way. An operative cluster lists every booking id and one pair row per overlapping pair, each with its `clashPairKey` and `clashResolutionKey`. A clash can be **approved** and **un-approved** (online, managers and admins only): `clashApprovalWrites` writes `acceptedBookingClashes/{clashPairKey}` and `warningResolutions/{clashResolutionKey}` with status `approved` — the key is the booking-pair key for operative clashes and `mgr-clash-…` for manager clashes; approving an operative cluster writes every pair. Approving writes, and un-approving deletes, both documents (every pair of a cluster) in one batch (1.9.0), so one never exists without the other. A clash is approved when either document exists for it (`isClashApproved`); an operative cluster is approved when every pair is (`isClashGroupApproved`), so a third booking re-opens it. Only approvals count as approved: `approvedWarningKeys` (status `approved`) and `acceptedBookingClashes`; a dismissed clash is hidden but is not approved. Approved clashes are listed separately on the weekly report and no longer count as open. Whether any row still counts is `isWarningActive` over `resolvedWarningKeys` (approved and dismissed). Keys compare without case (§1). Resolutions are read live (a snapshot listener on `warningResolutions`) through `warningResolutionRecords`, which puts older iOS keys in their shared form (`sharedWarningResolutionKey`: `mgr-clash-{user}-{seconds}-{i}` → `mgr-clash-{user}-{YYYY-MM-DD}-{i}`, `materials-{projectId}-{seconds}` → `materials-{projectId}-{YYYY-MM-DD}`, organisation zone). The one-off legacy migration (D3) is `warningResolutionMigrationWrites({ docs, legacyKeyForms, resolvedByUserId, timeZone })`: the `warningResolutions` documents to write under the shared keys (approved beats dismissed; nothing when the shared key is already resolved; old documents are left in place); staff only, idempotent.
- **Unbooked labour (High)** — an operative not booked on a working day in the window (`unbookedLabourRows`). Skipped: excluded users (silently), inactive users, pending users who have not finished sign-up, days on approved annual leave, weekends unless included, anonymised deleted profiles (`listedCurrentLabourPeople`). 1.19.0: each day of the window is read under the working hours in effect on THAT day — the caller passes the organisation's policy state as `payrollPolicy`. **Weekend requirement** (owner design, replacing the "counts as" hours): with include-weekends on, a Saturday or Sunday is scanned only when its `weekendCoverage` toggle is on, and a person is unbooked there when their bookings that day do not cover every minute of the day's "Hours to cover" window (`resolveWeekendCoverageDay`, `windowCoverage`); missing hours = the uncovered minutes of the window; time inside that day's lunch-break window (its own, else the weekday one; paid or not, `payrollBreakOnDay`) never needs covering, so two bookings either side of lunch cover the day (e.g. Saturday 07:30–14:00 with lunch 12:00–12:30 booked 07:30–11:30 → "… is missing 2h on Saturday …"; 07:30–12:00 plus 12:30–14:00 → covered). A weekday (1.20.0) must be covered for the whole working day, start to finish, and time inside the lunch-break window never needs covering, the same as a weekend day (`standardDayCoverage`; owner example 06:30–14:30, break 10:00–10:45: nothing booked → 7.25h missing; 06:30–10:00 plus 10:45–14:30 → covered). A day with approved half-day leave is not an unbooked-labour row; it is the leave-cover rule (`leaveCoverageRows`, §9; 1.23.0: each day of the window under the working hours in effect on it — the caller passes the policy state as `day`), where the other leave half must be booked minute for minute except the lunch-break window, which never needs covering there either. `unbookedLabourRowsOnDay` (Daily Overview) follows the same rule. Every id match in `unbookedLabourRows`, `unbookedLabourRowsOnDay` and `leaveCoverageRows` — leave to person, booking to person, former and same-email ids, exclusions — ignores case (`normalizeDocumentId`, §1); returned rows keep the ids as stored.
- **Low:** materials not ordered by the cut-off (`materialCutOffWarningRows`: once the organisation clock passes the cut-off, each job with an active booking tomorrow warns if tomorrow has no material lines or any line is not ordered — a line counts as ordered when its status is `ordered` or an order send record lists it (`materialLineCountsAsOrdered`); a Saturday or Sunday tomorrow only if that day's flag is on; key `materials-{projectId}-{YYYY-MM-DD}` for tomorrow); qualification expiry including already expired (`qualificationExpiryRows`; any count of them — a menu subtitle or Home badge — is `qualificationExpiryCount`, 1.23.0: the same rows on the organisation day, expiring on or before today plus one calendar month, split `expired` / `expiringSoon`; never a device-calendar 30-day window); unverified accounts (`unverifiedOperativeRows`).

**Scope** (1.10.0, §17). A manager who does not see every job gets only the rows about the jobs they see and the people booked on them: `warningScopeFor(...)` → `WarningScope`, passed as `scope` to `unbookedLabourRows` / `unbookedLabourRowsOnDay`, `qualificationExpiryRows`, `unverifiedOperativeRows` and `materialCutOffWarningRows`. A viewer who cannot read every booking gets no unbooked-labour rows (a person missing from their bookings may be booked on a job they cannot see). Clashes and leave coverage are scoped by the bookings the rules let them read. Admins and managers with both job toggles: everything.

**Annual leave when booking** (1.16.0, owner rule). Every booking flow that lists double bookings before it saves also lists each (person, day) of the booking that falls on that person's annual leave: `bookingLeaveConflicts({ people, dayKeys, holidays, timeZone, timeSlot, workStartTime, workEndTime, day, roster })` → `{ personId, dayKey, kind: 'annual_leave', leaveId, leaveSlot: 'FULL DAY' | 'AM' | 'PM', status, label }`, one row per person-day. Approved leave conflicts when its window overlaps the booking: full-day leave with anything; AM leave with a booking that touches the AM leave half (1.20.0: `leaveHalfDayWindows`, the exact middle of the day — on 06:30–14:30 AM leave conflicts only with bookings overlapping 06:30–10:30), PM likewise; a stored AM / PM booking is that leave half (`leaveComparableInterval`), so AM leave and a PM booking never conflict; custom hours conflict with half-day leave when they overlap that half. Pending leave is listed too (`status: 'pending'`, `ANNUAL_LEAVE_REQUESTED_LABEL`, shown softer); rejected leave never. People match leave under every id they go by (`personIdSet`, their `userId` and operative ids), without case, from `parseHolidayDocument` / `labourHolidayInput` day keys. Leave rows are purple and read `ANNUAL_LEAVE_BOOKED_LABEL` ("Annual leave booked"); double bookings stay orange; the heading is `BOOKING_CONFLICTS_HEADING` ("Some selected days clash. Tick to confirm, or ✕ to drop that day."). Each row is ticked (book anyway) or ✕ (drop that day for that person), and the save waits until every row is one or the other — the same as a double booking. The warning after saving is still `leaveCoverageRows`.

**Double bookings when booking** (1.19.0, owner decisions). Every booking flow lists a person already booked on a day as an orange row only when the new booking's times actually overlap an existing booking that day (`slotInterval` intervals, `intervalsOverlap`; touching times do not clash) — My Schedule self-booking included (it used to warn for any booking that day). 1.23.0: the check is `bookingRequestClashIds({ request, existing, day })` — the existing bookings (labour or manager schedule) whose `slotInterval` overlaps the booking being made, both read under the working hours in effect on the **booked** day (never today's: pass the policy state), an overnight booking from the day before reaching that morning, cancelled bookings never; every booking flow uses it — the Schedule wizard, Book labour, the Daily Overview booking sheet, Quick Add and booking edit on web (1.23.1), Select Operatives on iOS — and `bookingLeaveConflicts` reads each booked day's working hours the same way; a weekend day's named slot is that day's own window (`bookingStandardDayOn`). A manager or admin who is double-booked may book anyway: the orange row is ticked (keep) or ✕ (drop) like the annual-leave rows, and the overlap is then a Medium manager clash warning (`managerClashGroups`).

**Excluded users** are a per-user, all-or-nothing exemption from unbooked-labour warnings, for people who are never bookable (office PAYE staff, directors). Temporarily unavailable operatives use the **inactive** flag instead.

Display order (Oldest/Newest) is a per-device preference (`sortWarningsByDate`).

## 6. Daily Overview

One entry per day listing booked people (with project or small work), unbooked people (`unbookedLabourRowsOnDay`; on a Saturday or Sunday the "Hours to cover" rule of §4.6 / §5) and people on approved annual leave. It respects the organisation working hours in effect on the day shown (`effectivePayrollTimePolicy`, history first, 1.19.0), including that weekend day's own lunch break, the fixed working week, include-weekends, exclusions and active/inactive status. Hours (1.20.2) are the pay rule's for the day shown (`payrollHoursResult` under the policy in effect that day): each booking row shows its times ("Custom 07:30–14:00") and `bookingHoursLabel(result).label` — the paid hours with the multiplier sum when hours are at a multiplier (Saturday 07:30–14:00 on an 8h set window → "8h"; Sunday 07:30–14:00 every hour × 2 → "13h (6.5h × 2)"; weekday 07:30–18:00 with 2h at 1.5 → "11h (8h + 2h × 1.5)"), never the clock duration; the day's total is the sum of `totalPaidHours`, split into standard hours (`standardHours`) and hours at the multiplier (`outsideHours`). Before 1.20.2 the rows showed clock hours worked (`workedHours`), so a Saturday or Sunday 07:30–14:00 read 6.5h on every list. A Saturday or Sunday booking shows the custom hours entered (1.13.0, §4.3); a stored weekend FULL DAY / AM / PM shows as stored. It is identical on every platform for the same day and viewer; a manager who does not see every job sees their jobs' people only, and unbooked people only when they read every booking (`warningScopeFor`, §5, §17).

**Booked cover for one person on a day** (1.22.0) is `managerCoverageHours({ bookings, dayKey, policy, timeZone })` → `{ paidDayHours, paidHours, blocks, requiredHours, coveredHours, missingHours, covered }`, over all their labour and manager site bookings that day (every id they go by). `covered` is `standardDayCoverage` — the Daily Overview and unbooked-labour rule — and decides who Book labour still offers on both apps. `paidHours` merges the clock intervals (`slotInterval`; overlaps count once) and prices each merged block once with `payrollHoursResult` under the policy in effect that day (hours worked, never multiplied; the unpaid break off only where a block covers the break window); a FULL DAY with no clock times, or a block spanning the standard day, is `weekdayPaidHours`. Before 1.22.0 iOS (`ManagerScheduleInterval.combinedPaidBookedHours`) took the standard break off any partly booked day and Book labour on iOS compared those hours with the paid day, while web used `standardDayCoverage`.

## 7. Weekly Report

Generated live for any chosen date range from current bookings, Daily Overview, warnings and timesheets. Leave days in the range are `leaveDaysInRange(record, range, timeZone, nonWorkingDayKeys)` (1.9.0, on `leaveRecordDayKeys`; a half day counts 0.5) on every platform. Contents: hours, overtime, warnings including approved clashes, totals. 1.19.0: every pay row, the timesheet feed and each row's day units (the standard day and overtime rate) use the working hours in effect on the row's own day (the whole policy state), and rows on days with different rules are separate rows, never averaged; unbooked-labour warnings read each day under its own rules (§5); signed lines keep their signed amounts. The PDF, XLSX and HTML exports show the same rows. A warning counts as open only while `isWarningActive` over `resolvedWarningKeys` (1.10.0): a dismissed clash is in neither the open warnings nor the approved clashes; approved clashes (`isClashApproved` / `isClashGroupApproved`) are listed separately. Reports are **not stored** and **never write** (1.10.0): a signed sheet with no `weeklyReportOverride` is summarised in memory for the report only — the report never writes anyone's timesheet (`syncWriteAllowed('weeklyReport')` is false). The people in the timesheet feed are `timesheetParticipant(user, day)` (§8). **The approved-timesheet feed** (1.22.0) is `weeklyReportTimesheetFeed({ weeks, people, range, timeZone })` on every platform (`mergeTimesheetFeedWeeks`, `timesheetFeedCovers`, `timesheetFeedLabourLines`, `timesheetFeedMoneyLines`): approved weeks of accounts that share an email (roster email, without case; else the user id) and the same week start are one person's week — the first week keeps its fields and its lines are the union by identity (a booking line by `bookingId`, else its day, place, job, hours, days, amount, overtime flag and details; a money line by `id`, else its day, job, title, amount and details; each identity as many times as any one week has it), so a booking both accounts carry counts once and hours on only one account stay; a person's live bookings on a day inside an approved week (organisation-zone days, inclusive) are replaced by that week's lines; labour lines in the range count except declined ones, price work and expenses except declined ones and amounts of 0.0001 or less. Behaviour is unchanged from web 1.21; iOS kept its own copy until 1.22.0. A report is produced and downloaded (PDF/XLSX/HTML or the share sheet) and that is all. Producing a report again for the same range reflects any changes made since.

## 8. Timesheets and employment profile

**Profile fields** on `users/{uid}`: employment status (`employmentType`: PAYE or self-employed), pay basis (`payBasis`: day or hourly), `dayRate`, `hourlyRate`. A rate save writes exactly one basis and removes the other; both apps show `PAY_BASIS_SAVE_NOTE` ("Pay is a day rate or an hourly rate, not both. Saving a day rate removes the hourly rate, and saving an hourly rate removes the day rate.") with `PAY_BASIS_DAY_HELP` / `PAY_BASIS_HOURLY_HELP` under the pay fields (1.11.0; iOS copy that said both rates are kept was wrong). A PAYE person's rate is kept for days they are self-employed and shown with `PAYE_RATE_NOT_USED_NOTE`. The same applies to roster rows: an `operatives` or `managers` row with `payBasis: hourly` is hourly (`parseOperativeDocument`, `parseManagerDocument`). `timesheetsEnabled` is still read and written (`defaultTimesheetsEnabled` when not stored) but, from 1.11.0, no longer decides who has a timesheet: only self-employed days do (below). Annual leave fields not stored on the user (`annualLeaveDaysPerYear`, `annualLeaveYearStartMonth`, `annualLeaveYearEndMonth`, `annualLeaveCarriesOver`) take the organisation `annualLeaveDefaults` (§4.4), never a platform constant (`parseUserDocument` with `annualLeaveDefaults`); a save never writes the default onto the user.

**Effective dating.** Status and rate are both effective-dated; a change asks when it takes effect. Status: `employmentTypeTransitionFrom` / `employmentTypeEffectiveAt` (`applyEmploymentTypeChange`, `employmentTypeOnDay`). Rate: `organizations/{orgId}/operativeDayRateHistory` rows `{ userId, operativeId, dayRate, payBasis, effectiveAt, createdAt }`, built by `payRateHistoryWriteFields`: `effectiveAt` is midnight of the effective day in the organisation zone (never London unless that is the organisation's zone, never the device zone). Clearing a rate writes a row `{ dayRate: null, payBasis: null, effectiveAt }`, meaning "rate not set from that day". History is never rewritten. **A pay change** (1.10.0) writes its rows with `payRateChangeWrites({ previousProfile, nextProfile, history, effectiveDayKey, seedEffective })`: nothing when the amount and basis are unchanged; a seed row of the previous rate from the account's creation only when the person's history loaded and is empty; then the new row. The rows are written in the same batch as the profile (`users/{uid}`), never as a best-effort second write; when the history did not load the save is refused (`history_not_loaded`, `PAY_HISTORY_NOT_LOADED_MESSAGE`) instead of treating it as empty.

**Rate on a day** (`payRateOnDay`; 1.10.0: given `person` and `roster`, history rows match every id of the person — `personIdSet`: own id, former ids, same-email ids — so each app passes the whole history): a PAYE day has rate 0 (the line keeps its hours and is flagged PAYE). Otherwise the rate is the latest history row for the person whose effective day (organisation zone) is on or before the day; an explicit 0 is a real rate. If the live profile is hourly, an hourly row stays in force until a day-rate row falls on a later day. A "rate cleared" row in force means "rate not set" (it ends an hourly row too). With no history row the live profile applies (`users/{uid}`, then the operative row). With nothing set the rate is "rate not set".

**Pay rules.**
- **PAYE has no timesheet** (1.11.0, owner decisions round 3). A PAYE day produces no timesheet line, no pay and no invoice row; it is still a booking for warnings, Daily Overview and Weekly Report hours (where its pay cell reads PAYE, `reportPayCell`). The days that count on a person's sheet for a period are `timesheetDaysForPerson(user, period, timeZone)` — every organisation-zone day of the period on which they are self-employed (`employmentTypeOnDay`, effective-dated); `showsMyTimesheets(user, period, timeZone)` is whether that list is not empty. A person sees **My Timesheets** for a period only then, gets the submission reminder only then, and their owner sheet, its invoice (`timesheetInvoiceRows` with `timesheetDays`: labour lines, price work and expenses dated on another day are left out) and the User Timesheets row for that period exist only then. A PAYE manager or admin still reviews other people's timesheets (User Timesheets is `canReviewUserTimesheets`, not this). A PAYE overtime and expenses submission is a later feature, not part of this rule. `isInvoiceLine` still drops a line flagged PAYE (older data).
- Self-employed days pay the effective day or hourly rate.
- Example: PAYE → self-employed changed on Tuesday, effective Wednesday: the sheet for that period shows Wednesday onwards only; Monday and Tuesday are not on it.
- **An unpaid break is never multiplied** (1.20.3, owner decision, final): on hours at a multiplier (weekend every hour at N×, or a set-window day's outside hours) the hours are multiplied first and the break comes off as plain hours — Sunday 07:30–14:00 every hour × 2 with 30 min unpaid = 13 − 0.5 = 12.5h (§4.3, `payrollHoursResult`). Booking rows show it as "12.5h (6.5h × 2 − 0.5h break)" (`bookingHoursLabel`); (1.20.4) timesheet lines, invoices, the weekly report and Daily Overview show "6.5h × 2 − 0.5h break = 12.5h" (`multipliedHoursText` over `payrollMultipliedHours`; a signed line's stored text is read back with `parseMultipliedHoursText`), never the back-calculated base hours ("6.25h × 2"), and the line's pay is unchanged.
- **Overlapping bookings are each paid** and never merged. An overlap is a warning managers should have caught; on the timesheet each overlapping line is shown in amber for the person and their line manager with "Overlaps another booking — check with your manager" (`overlappingBookingIds`, `OVERLAPPING_BOOKING_NOTE`). Times that only touch do not overlap. A Full day, AM or PM line is the standard day in effect on that line's own day (1.23.0: the collector passes the working-hours state, as pay has since 1.19.0), so a working-hours change inside the pay run moves the overlap flag with it.

**Who may see pay** (1.13.0, owner decisions round 4, Q1; `canViewPersonPay(viewer, subject, roster)`). A person's pay — day or hourly rate, pay basis, employment type (with its effective-dated transition), rate history, timesheets and invoices — is seen only by: the person (under any of their ids); their active line managers (`lineManagerIds`); admins and super admins of the organisation; a manager with the Operatives toggle, for an operative only; and the platform owner. Every screen showing pay (the people profile, Manage Users, timesheets, User Timesheets, invoices, the weekly report's pay cells) asks `canViewPersonPay` first — from 1.13.0 the people profile on web; the others with the release that reads pay per person (step E of the move). Security rules cannot hide fields, and every member reads the roster's `users` documents, so pay moves to a private document per person per organisation: `organizations/{orgId}/payProfiles/{subjectId}` (`payProfilePath`; `subjectId` = the person's users id, or an `operatives` row id for a catalogue person with no account), fields `PAY_PROFILE_FIELDS` (`payBasis`, `dayRate`, `hourlyRate`, `employmentType`, `employmentTypeTransitionFrom`, `employmentTypeEffectiveAt`) plus `userId` and write metadata, read with `parsePayProfileDocument` and laid over the person with `overlayPayProfile` (the pay profile wins once it exists). A pay save writes the changed pay fields to the pay profile in the same batch as the profile (`payProfileWriteFieldsFromProfileWrite`), by whoever `canChangePersonPay` allows. **The move** (Deploy notes 1.13.0): apps write pay to both places and read the pay profile first; `scripts/backfill-pay-profiles.mjs` copies existing pay (`payProfileBackfillWrites`); a later release reads pay only per person; the platform owner then sets `platformConfig/app.privatePay` true (the rules then limit rate history, the `operativeProfiles` mirror and timesheets to pay viewers and refuse any pay value written back onto `users`, `operatives` or `managers`); the backfill's `--strip` step then removes pay from those documents. Only after the strip can no colleague read another's rate. **1.26.0, reading and writing with the switch:** while `privatePay` is on for the organisation (`securitySwitchOn`), a save writes pay only to the pay profile and the rate history — the `users` / `operatives` / `managers` write leaves every `PAY_PROFILE_FIELDS` key out (`sharedDocumentPayWrite`; Add User writes the invited pay to the placeholder's pay profile, and accepting the invitation writes the account without pay); rate history is read whole by admins and otherwise with one `userId ==` query per person whose pay the viewer may see (`rateHistoryQueryPlan`); and pay profiles are read whole by admins and otherwise by id (`payProfileReadPlan`), each laid over the roster person under their id, else a former invite id (`overlayPayProfile`). **1.26.1, one starting value for display and editors** (`payEditorStartingValues(person, profile, { privatePay })`): no single-person pay display or pay editor starting value reads `payProfiles` while `privatePay` is off for the organisation — it is the person's `users` / `operatives` document exactly as stored, because an older build may have left the pay profile stale. While it is on, the display (the people profile) and every pay editor (Manage Users / Edit User, the catalogue operative form, the rate dialogs) start from the same value, the person with their pay profile laid over (`overlayPayProfile`; own id, else a former invite id; the person's document when none is readable), and that same record is the baseline of the save: the changed-fields diff, the "rate changed?" test and the rate history's previous rate (`payRateChangeWrites` `previousProfile`). An editor never starts from, or saves back, an old rate left on a shared document. **1.27.0, catalogue operatives** (owner decision 7): a catalogue operative is an `operatives` row with no app account — no stored `linkedUserId` / `userId` / `uid`, a row id that is no roster member's id and no roster member on its email (`catalogueOperativePaySubjects(operatives, roster)` → `{ id: <row id>, email, catalogueOperative: true }`; the security rules: no users document of that id, no stored link and no `userEmails/{email}` claim of the organisation on its email). Its pay is seen by admins, the person on its email and managers with the Operatives toggle (`canViewPersonPay` with `catalogueOperative: true`; it has no line manager). Both apps pass the catalogue operatives with the roster to `payProfileReadPlan` (so an operatives manager reads `payProfiles/{rowId}` by id and the row is laid over with it, `overlayPayProfile`) and to `rateHistoryQueryPlan`, whose `people` plan now also lists `operativeIds` — one query `operativeId ==` <row id> `and userId == ''` each (`payRateHistoryWriteFields` stores an empty `userId` for a catalogue row; rows saved with no `userId` field at all are read by admins only). An `operatives` row that belongs to an account is that person's and is read through their users id. **1.27.0, the invited rate on accept** (owner decision 6): while `privatePay` is on, accepting an invitation copies the pay fields of the placeholder's pay profile, exactly, to the account's own `payProfiles/{authUid}` (`invitePayProfileCopyWrite`; nothing when the switch is off, there is no placeholder, the account already has a pay profile, or the placeholder's profile holds no pay field). It is written after `users/{authUid}` and before the email claim moves to the account; the security rules allow this one create only then (§16). With the switch off nothing changes. Known limit while it is on: an invitation accepted by an existing account of another company keeps the rate on the placeholder's pay profile (the placeholder stays; admins see it).

**Who may change pay** (`canChangePersonPay`). A person never changes their own pay, line manager or employment type on any path — `users/{uid}`, `operativeProfiles/{uid}`, `operativeDayRateHistory`, or the pay fields of `operatives/{id}` and `managers/{id}`. An admin may (including their own rate). A manager with Operatives access may change an operative's pay in the same company, never their own or another manager's; a manager's pay is changed by admins only. Resending an unchanged value is not a change.

**A self-employed person must have a pay rate** (1.14.0, owner decision). Self-employed people are paid from their rate, so a save that leaves a self-employed person (`normalizeEmploymentType`; a missing type reads as self-employed) without a rate is refused: `payRateRequiredError({ employmentType, payBasis, dayRate, hourlyRate })` returns `PAY_RATE_REQUIRED_MESSAGE` ("Set a day rate or hourly rate — self-employed people are paid from it.") when the rate for the chosen basis (`hourly` → `hourlyRate`, `day` → `dayRate`, no basis → either) is missing, blank, not a number, 0 or below. PAYE never needs a rate. Pass the person as they will be saved — a change to self-employed, immediate or effective-dated, is checked with the new type. Add User refuses the invite and Edit User refuses the save on every platform, with the message on the rate field, whenever the writer may set that person's pay (`canChangePersonPay`). People saved before this rule are listed for admins by `usersMissingPayRate(roster)` (active, not deleted, once per person by `personIdSet`).

**Timesheet review** (`timesheetEntryReviews`). Only the person's line manager or an admin writes `payrollLineReviews` and `extraEntryReviews`. The decision for a price-work or expense entry is `extraEntryReviews[entryId] { decision, revisedAmount, reviewedAmount, reviewedByUserId, reviewedAtMs }` (`timesheetEntryDecision`, written with `timesheetEntryReviewWriteFields` as dotted partial updates); a review stored under the entry id in another letter case is found too. Entries are read with `parseTimesheetEntries(sheetDocId, sheet, { timeZone })`: every entry with a title is kept whatever its id, a stored id keeps its stored case (UUID or not), and an entry stored without an id gets `timesheetEntryId(sheetDocId, kind, index, entry)` — a UUID-shaped id derived from the sheet id, the array, the position and the content, the same on every read and every platform, never random — and the next save writes it onto the entry. A review made against a different amount is stale and the entry is pending again; an entry nobody reviewed counts at its own amount. The inline `managerDecision` / `managerRevisedAmount` on an entry is still written for older builds and counts only when it lowers what is paid, or on a legacy sheet (no map) the line manager already signed. Owner saves go through `timesheetOwnerWriteFields`: it always removes the review maps and the manager sign-off and export fields (`TIMESHEET_MANAGER_SIGN_OFF_FIELDS`); the person writes `weeklyReportOverride` only when they have no line manager (self-signed), cannot change price work or expenses once the line manager has signed, and writes `managerNote` (their own note to the manager). The owner then sends only the fields that changed, as a partial update — never a full merge-set of the sheet. Every timesheet save, owner or reviewer, writes `timesheetChangedFields(base, next)` (1.9.0): the fields that differ from the sheet **as this editor loaded it**, never every difference from the server copy, so a signature, expense or price-work entry saved on the other platform after the load is kept; and whether the line manager has signed is read from the stored sheet, never a local copy. Whether a writer is a reviewer is `timesheetWriterIsReviewer`.

**Pay arithmetic** (1.10.0) is `payForHours({ payBasis, dayRate, hourlyRate, paidHours, standardDayHours, otMultiplier })` — hourly: rate × hours × multiplier; day: day rate × (hours ÷ the organisation's paid day, `orgDayHours`) × multiplier — rounded with `roundPennies`; no app keeps its own. 1.12.0: a day rate with a paid day below 1 hour (`PAY_STANDARD_DAY_MIN_HOURS`), missing or not a number pays 0 (rate not set), never the day rate divided by a 0.01 floor; a multiplier that is not a positive number is 1; a rate that is not a number is 0.

**The unpaid break** (1.12.0, `payrollHoursResult`). On a weekday the break taken off a booking is the part of the break window (`breakWindowStart`–`breakWindowEnd`) the booking's clock time covers, up to `unpaidBreakMinutes`: a booking across the whole window loses the whole break; 11:50–12:20 against a 12:00–12:30 break loses 20 minutes. Nothing comes off when the break is paid (`breakPaid`), removed on the booking (`isBreakRemoved`) or the slot is a named AM / PM. **A booking whose clock time lies entirely within the unpaid break pays 0 hours** (12:00–12:30, 12:05–12:25) — when a booking has clock times it never falls back to a full standard day; only a booking with no clock times at all is paid by its slot (FULL DAY, AM, PM, EVENING, OVERTIME). **Lunch warning** (1.13.0): before a custom-hours booking is saved, every app shows `customHoursBreakWarning(policy, dayKey, booking)` — "You are booking custom hours that cover the unpaid lunch break. Turn off Unpaid break to make sure they are paid for this time." — as a confirm step when the booking is custom hours, the organisation break is unpaid (`breakPaid` not true, an unpaid length above 0), the booking's Unpaid break toggle is on (`isBreakRemoved` not true) and its hours overlap the break window that day (1.19.0: on a Saturday or Sunday only when that day's break is unpaid, `unpaidBreakAppliesOnDay`). The pay rule above is unchanged.

**Weekday pay** (1.20.0, owner decisions). A FULL DAY pays the weekday paid day — the standard day less the covered part of the unpaid break (`payrollHoursResult`; owner example 7.25h). Custom weekday hours pay as before: the hours inside the standard day less the unpaid-break overlap, and the hours outside it at the weekday overtime multiplier (06:30–16:30 → 7.25h + 2h × 1.5). Under a policy saved from 1.20.0 (`paidHoursDerived`) custom hours are never snapped to a half day (11:00–14:30 pays 3.5h, not half the day); a policy saved earlier keeps the 20-minute half-day snap. A stored AM / PM booking pays half `weekdayPaidHours` as before. The day a day rate is divided by is `weekdayPaidHours` of the policy in effect that day (`payForHours`, `reportDayValue`).

**Weekend pay** (1.13.0, Q2). Weekend bookings are custom hours (§4.3) and are paid by `payrollHoursResult` on that day's rule: with a set window, the hours inside it count as its "counts as" hours (pro rata when only part of it is worked) and the hours outside it are at that day's outside multiplier; with every hour at one rate, each hour × that multiplier. 1.19.0: when that day's lunch break is unpaid, that day's own break (length and window, the weekday ones when not set) comes off as §4.3 says (set window: off the credited hours for the part inside the window, off the outside hours for the part outside; every hour: (clock − break) × N). Every day is priced under the policy in effect on it; **a signed timesheet is never re-priced** — its `weeklyReportOverride` lines (and the signed-sheet invoice, `timesheetInvoiceRows`) keep their signed hours and amounts whatever the working hours later become. Stored weekend rows keep being paid as before and are never rewritten: an AM / PM pays half the "counts as" hours; a FULL DAY with no clock times pays the set window at its "counts as" hours with nothing outside it (`weekendFullDayWindow`; before 1.13.0 the weekday standard day plus weekend overtime), and on an all-hours day the pre-1.13.0 calculation (the standard day × that day's multiplier, e.g. 07:30–16:00 at 2× = 17).

**Overnight pay** (1.13.0, Q5): a booking that crosses midnight is paid wholly at its start day's rules (`payrollHoursResult`): on a weekday the hours inside that day's standard window count once (less the unpaid break they cover) and every other hour, after midnight too, is at that day's weekday multiplier; on a Saturday or Sunday that day's weekend rule. A weekday night is paid at the weekday overtime multiplier for every hour outside the standard window (owner confirmed). Before 1.13.0 it was paid as plain hours at 1×.

**Who takes part in timesheets** is `timesheetParticipant(user, dayOrPeriod, timeZone)`: never an inactive person or an anonymised profile; given a period, `showsMyTimesheets`; given a day, self-employed that day (1.11.0: `timesheetsEnabled` and operative mode no longer bring a PAYE person in). It decides the Weekly Report timesheet feed (§7, per payment run), the `timesheet_submission_reminder` recipients (§13) and the User Timesheets rows.

**Invoices** (1.10.0). The rows of a generated invoice are `timesheetInvoiceRows({ sheet, payrollLines, extrasMode })` on every platform: a signed sheet's `weeklyReportOverride` first (its signed amounts; declined and zero rows, and PAYE / leave lines, left out); otherwise the live lines (`invoiceLines`) with the line manager's review once signed (`payrollLineReview(sheet, lineId)`, found under the line id in any letter case), then price work and expenses with their decision (`timesheetEntryDecision`) in `decided` mode or at their own amounts in `raw` mode. 1.11.0: given `timesheetDays`, rows dated on a day the person was PAYE are left out (the PAYE-extras path is removed).

**Timesheet totals** (1.22.0, owner rule: a summary never disagrees with the invoice). Every figure that sums a sheet — the User Timesheets and My Timesheets list rows (hours, overtime, price work, expenses), the detail screen (hours subtotal, overtime, price work, expenses, extras and the total), the sign sheet and the signed-sheet value — is `timesheetTotals(input)`, where `input` is exactly the input of `timesheetInvoiceRows` and the money is the sum of its rows, so the summary total is the invoice total for the same inputs by construction. `{ hours, standardHours, overtimeHours, labour, standardLabour, overtimeLabour, priceWork, expenses, extras, total, submittedPriceWork, submittedExpenses, submittedExtras, pendingEntries, source, invoiceRowCount }`, money rounded to pennies. In `decided` mode a declined entry counts 0, an edited one its revised amount, a stale review (made against another amount) is pending and counts the entry's own amount, an unreviewed entry its own amount (`timesheetEntryDecision`, `timesheetEntryEffectiveAmount`); a signed snapshot (`weeklyReportOverride`) wins; PAYE days and leave lines never count. List rows use `decided` (the export invoice). A detail screen uses `decided` once the line manager has signed or while the viewer is reviewing, else `raw` (the owner's draft at the amounts entered); a reviewer before signing passes `applyLabourReviews: true` (new on `timesheetInvoiceRows`; missing = once the line manager has signed, as before), so their screen shows the invoice their signature will produce. Hours come from the live payroll lines: each booking's standard line carries `bookingPaidHours` (`payrollHoursResult.totalPaidHours`) and `bookingOvertimeHours`; without them a line's `paidHours` (× `otMultiplier` on an overtime line). Before 1.22.0 list rows summed every entry at its own amount (a declined expense still counted) and both apps re-implemented the entry decision on the detail screen.

**Calculation.** Hours, overtime and pay come from bookings, the working-hours policy in effect that day and payment runs (`payrollHoursResult`, `workedHoursSplit`). Timesheets are grouped by payment run (`timesheetPeriodFromInvoicing`, `selectableTimesheetPaymentRunPeriods`); status Awaiting / Signed off / Exported is `timesheetListBucket`.

**Annual leave on timesheets.** Each approved leave day in the period appears as an information line "Annual leave (full day / AM / PM)" for the person and their line manager, with no edit control and no hours or pay (`timesheetLeaveLines`, `timesheetLeaveLabel`); 1.20.0: given the working day in effect on each day, the line carries its clock range from `leaveHalfDayWindows` (`timeRange`, e.g. "Annual leave (AM) · 06:30–10:30"). Leave never appears on a generated invoice.

**Admin and operative mode** (1.11.0). An admin or super admin has no operative mode: a stray `operativeMode` flag on an admin is ignored everywhere — people lists (`parseUserDocument` → `operativeMode`, `accountKind`), permissions (`effectivePermissions`), the approval rules (`isAdminOutsideOperativeMode`, `adminOutsideOperativeMode`) and the security rules (`callerOrgRole`, `hbCallerIsOperative`). Only operative-level users get operative mode, at setup. (Before 1.11.0 such an admin decided only as a line manager.)

**Line manager.** A person's line managers are `assignedManagerUserIds` (else the single `assignedManagerUserId`; `hasNoLineManager` means none) — `lineManagerIds(user, roster)`. Given the roster, only active members count, an old invite id the roster knows as someone's `formerUserIds` / `sameEmailUserIds` is that person, and the person themself never counts under any of their ids (`personIdSet`: id, `formerUserIds`, `sameEmailUserIds`, roster rows with the same email). `hasActiveLineManager` is whether anyone is left. Line managers receive that person's timesheets for signing, annual leave requests and other approval items (`userTimesheetSubjects`, `leaveApproverIds`). With no active line manager (legacy data only), the active admins and super admins outside operative mode receive them — never "any manager". Nobody approves their own items. Routing is read at the time — changing the line manager on any platform re-routes everything, nothing is stored on the request.
- **Every operative and every manager needs an active line manager**, whatever the annual-leave self-book permission and whether annual leave is switched on for them. Only an admin or super admin outside operative mode may have none (`lineManagerRequired`, `isAdminOutsideOperativeMode`); an inactive person is not checked. `lineManagerRequiredError(user, roster)` returns `LINE_MANAGER_REQUIRED_MESSAGE` ("Set a line manager — this person's timesheets and annual leave need approval.") when a required line manager is missing, and Manage Users on every platform refuses that save. People saved before this rule who fail it are listed for admins by `usersMissingLineManager(roster)`; until fixed, their timesheets and requests go to the admins (`leaveApproverIds`), so nothing is stranded.
- **An admin or super admin with no active line manager is self-approved** (`timesheetSelfSigned(user, roster)`). Their timesheet has no "note to manager" and no "pending manager signature" state: their own signature completes the sheet (generate invoice is ready), and their owner save may write `weeklyReportOverride` (`timesheetOwnerWriteFields` with `subjectHasLineManager: !timesheetSelfSigned(...)`). Their annual leave saves approved (§9). An admin who has a line manager goes through normal approval.
- **`hasNoLineManager`** is a line-manager field: it is written only by whoever may change the line manager (admins; operatives managers for operatives), never by the person, together with the line-manager ids in one partial update. It is only valid for an admin or super admin.

## 9. Annual leave

One document per request at `organizations/{orgId}/holidayBookings/{id}`: a run of calendar-consecutive days with the same slot is one record from `startDate` to `endDate` (`holidayRequestRanges`, `holidayRequestWriteFields`), with `timeSlot` (`FULL DAY` / `AM` / `PM`, applying to every day) and `status` (`pending`, `approved`, `rejected`). Cancelling approved leave is a request (`cancellationRequestedAt`, `cancellationRequestedByUserId`) that an approver accepts (the record is removed) or refuses. Either way the requester is notified (`holidayDecisionRecipients`: `holiday_request_approved` when accepted, `holiday_request_declined` when refused, 1.9.0), as its own notice that never reuses the original decision's row. Older one-document-per-day records stay valid. **Reading a record** is `parseHolidayDocument(docId, data, timeZone)` on every platform (no app keeps its own parser): it accepts the keys either app has written (start `startDate`/`start_date`/`start`/`from`/`dateFrom`/`holidayStart`/`date`; end `endDate`/`end_date`/`end`/`to`/`dateTo`/`holidayEnd`, else the start day; person `userId`/`user_id`/`uid`/`userID`/`linkedUserId`/`employeeUserId` or nested `user.id`, and `operativeId`/`operative_id`/`operativeID`; status `status`/`holidayStatus`/`approvalStatus`; slot `timeSlot`/`slot`/`halfDay`; note `decisionNote`/`note`), uses the document id as the record id, keeps ids in their stored case (an `operativeId` that is not a UUID is kept), turns dates into organisation-zone day keys (a calendar-date string is that day) and swaps a reversed range. Status words map through `normalizeHolidayStatus` (`HOLIDAY_STATUS_SYNONYMS`: requested/awaiting/submitted → pending; accepted/confirmed → approved; declined/denied/cancelled → rejected); a missing or unknown status is approved. Warnings, Daily Overview, leave coverage and timesheets take the parsed day keys as they are (`labourHolidayInput`) and never recompute them from the stored dates. A decision writes `status`, `approvedByUserId`, `approvedAt` and an optional trimmed `decisionNote` (blank clears it) shown to the requester (`holidayDecisionWriteFields`, `parseHolidayDecisionNote`). Day counting (`leaveRecordDayKeys`, `annualLeaveBalance`): a single-day record counts its day; a multi-day record counts each day except weekends and bank holidays, each in its own leave year. Submitting a request notifies its approvers (`holiday_request_submitted`, `holidayRequestRecipients`), and the requester is notified of the decision (`holidayDecisionRecipients`); see §13. Approved leave affects Daily Overview, unbooked-labour warnings (`leaveCoverageRows`), timesheets (information lines) and My Schedule. Booking someone onto a day of their approved or pending leave asks first (`bookingLeaveConflicts`, §5, 1.16.0). Editing an existing record is a partial update of the changed fields.

**Leave halves** (1.20.0, owner decision). Annual leave keeps AM / PM / Full day = 0.5 / 0.5 / 1 day (`leaveRecordDayKeys`, `annualLeaveBalance` unchanged). The halves split the Monday–Friday working day at its exact middle, ignoring the break: `leaveHalfDayWindows(policy)` (06:30–14:30 → AM 06:30–10:30, PM 10:30–14:30; 10:00–18:00 → AM 10:00–14:00, PM 14:00–18:00; floored to the minute), read under the working hours in effect that day. They are used only for leave: the Daily Overview, Schedule and My Schedule leave labels (`leaveHalfDayLabel`, e.g. "AM 06:30–10:30"), `bookingLeaveConflicts` (purple rows), `leaveCoverageRows` and timesheet leave lines (`timeRange`). A stored AM / PM booking compared with leave is that leave half (`leaveComparableInterval`); custom hours are their clock times. **Leave cover:** on a half-leave day the other half must be booked minute for minute, except that time inside the lunch-break window never needs covering (owner rule, as for unbooked labour, §5; the break does not move where the halves split): AM leave on 06:30–14:30 with lunch 10:00–10:45 plus a booking 10:30–14:30 → covered; plus 10:45–14:30 → covered; plus 11:00–14:30 → "10:45–11:00 (0.25 hours) is not booked"; on 10:00–18:00 (paid break 13:00–13:30) AM leave plus 14:00–18:00 → covered. Bookings keep `halfDayWindows`; no app splits a leave day itself.

**Self-booking** (`canSelfBookAnnualLeave(user, roster)`): a person's own leave saves approved when they have the `annualLeaveSelfBook` permission outside operative mode, or they are an admin or super admin outside operative mode with no active line manager (self-approved, §8). Having no line manager does not make an operative or manager a self-booker. Everyone else sends a pending request to `leaveApproverIds`. The submit button reads "Submit" when the leave saves approved and "Submit request" otherwise (`leaveSubmitLabel`, `LEAVE_SUBMIT_LABEL`, `LEAVE_SUBMIT_REQUEST_LABEL`). Self-booked leave notifies nobody.

**Who decides** (`canDecideLeave(viewer, requester, roster)`): never the requester under any of their ids, admins included. An admin or super admin not in operative mode may decide any request in the organisation; anyone else only when they are in `leaveApproverIds(requester)` (an admin in operative mode decides only as a line manager). The list a person sees to decide — pending requests and cancellation requests — is `leaveDecisionQueue(viewer, requests, roster)`. Enforced by security rules.

**The leave calendar** (1.23.0, audit finding 19). What a person's annual-leave calendar shows on a day is `leaveDayKind(records, dayKey, timeZone, nonWorkingDayKeys)` → `{ kind, recordId, isLocked }`: a record covers the day only when the day is one of its leave days (`leaveRecordDayKeys` — a multi-day record skips weekends and the bank holidays given, the days the allowance counts); rejected records never show; approved leave with a pending cancellation request still shows as approved (as everywhere in §9); and the order is fixed, never the list order — a full day beats a half day, and at the same length pending beats approved (pendingFull, approvedFull, pendingHalf, approvedHalf, none). A full day is locked (`isLocked`): no more leave is requested on it. Before 1.23.0 web read the whole start–end range on the browser day and iOS hid leave with a pending cancellation.

**Holiday Report** (1.22.0) — one person's leave in one leave year — is `leaveReportRows({ records, personIds, onDayKey, startMonth, timeZone, nonWorkingDayKeys, statuses })` → `{ startDayKey, endDayKey, yearKey, rows: [{ id, startDayKey, endDayKey, timeSlot, status, days }], totalDays }` on every platform, with the year picker from `leaveReportYears({ firstDayKey, todayDayKey, startMonth })` and one record's days from `leaveReportDayCount(record, range, timeZone, nonWorkingDayKeys)` (`leaveDaysInRange`). The year is the organisation leave year (`leaveYearBounds` from `annualLeaveDefaults.startMonth`), never the calendar or device year; a multi-day record counts its working days only (weekends and the region's bank holidays out, `leaveRecordDayKeys`), each inside the year; AM / PM count 0.5; records are `parseHolidayDocument` rows matched under every id the person goes by (`personIdSet` plus their operative ids) without case; approved only unless `statuses` says otherwise. The report's total equals the `taken` figure of `annualLeaveBalance` for the same year. Before 1.22.0 iOS counted every calendar day from start to end, a half day as 1, the device's January–December year and exact ids only. Web has no Holiday Report screen.

## 10. My Schedule

Every person sees their own bookings and annual leave (approved, and pending marked as pending), matched by account (`bookingIdsForAccount`, with the roster's same-email ids as `aliasIds`; leave with `leaveRecordsForAccount`, 1.9.0, which from 1.10.0 also matches leave whose `userId` is the account's email, as older iOS builds stored it) — never by name. Every My Schedule screen shows it — on web both the read-only screen and the self-booking screen admins and managers get (before 1.12.2 the self-booking screen showed no leave, while Daily Overview did). It updates live when a booking or leave changes on any platform. Hours as in §6 (1.20.2: each row shows its times and `bookingHoursLabel`, the pay rule's hours for that day, on every list — My Schedule, Schedule, the project / small works week, Daily Overview).

## 11. Manage Users

All Manage Users changes — role, line manager, employment status and rates with effective dates, inactive flag, exclusions, invites — are online-only, sync to every platform through live listeners, and are written as partial updates of the changed fields only (`userProfileWriteFields`; a linked `operatives` / `managers` row with `operativeRowWriteFields` / `managerRowWriteFields`). Changing a person's pay from an operative or manager record writes only the pay fields of their `users/{uid}`, never the whole document. People lists use `rosterPeople` / `listedRosterUsers`; Active / Inactive / Pending is `userRosterSegment`. **Which list** (1.23.0, audit finding 9): `rosterListFor(kind, roster, claimedEmails)` with `kind` `operatives` | `managers` | `admins` — each person is on exactly one list, their level (`rosterListKind` = `permissionLevelOf`): admins (super admin, `adminAccess`, the admin role) on Admins only, never Managers; the operative level (operative mode, or the operative role) on Operatives; everyone else on Managers — the manager flag, the manager role, and a person with no level flag at all, who already reads as manager level for their toggles, the line-manager picker and Change user type. A `managers` row never moves a person between lists and never sets `manager: true` on a person (1.23.1, owner decision: web's roster no longer does; iOS never did). One document per email (`rosterPeople`), sorted by name. **Every user has a level** (1.23.1, owner decision): every create path writes one — Add User and re-invite (refused without one), accepting an invitation (the invitation's stored level), guided setup and sign-up (admin). A person with none (`userMissingLevel`: no `isSuperAdmin`, `adminAccess`, `manager` or `operativeMode` stored true and not an admin by role) is a data fault: Settings → Data health lists them (`usersMissingLevel`) with `USER_MISSING_LEVEL_MESSAGE` ("Has no user level: open in Manage Users and pick one") and a link to each person, where Change user type sets the level. Until then they read as manager level, are listed on Managers, and their clashes stay operative (High) clashes (owner decisions 1A, 2A). Before 1.23.0 web listed a person with no flag on Operatives and admins by role on Managers; iOS listed a person with no flag nowhere unless a `managers` row placed them on Managers. A save that leaves an operative or manager with no active line manager is refused with "Set a line manager — this person's timesheets and annual leave need approval." (`lineManagerRequiredError`, §8) — the self-book permission does not waive it; only admins and super admins outside operative mode may have none. Admins see the people already in that state (`usersMissingLineManager`). A self-employed person needs a day or hourly rate above 0 (`payRateRequiredError`, §8): Add User and Edit User refuse the save with "Set a day rate or hourly rate — self-employed people are paid from it." on the rate field, and admins see an amber list of self-employed people without a rate (`usersMissingPayRate`). The line manager, `hasNoLineManager` and self-book flag are written by admins (operatives managers for operatives) only. The live roster is the `users` query on `organizationId` (§1). A user may not change their own rates, pay basis, employment type, active flag, line manager or permissions — enforced by security rules. **Roles & permissions** opens Manage Users directly.

**Permission toggles by user level** (1.11.0, owner decisions round 3). The toggles in effect are `effectivePermissions(user)`; every permission check on every platform and in the security rules reads them, never the stored flag. The level is `permissionLevelOf(user)` (admin for a super admin, `adminAccess` or the admin role; else operative for operative mode or the operative role; else manager).
- **Admins and super admins:** every `USER_PERMISSION_FIELDS` toggle reads on and is locked (`lockedPermissionFields`) — Admin Access and Operatives included — except **Annual Leave Management** (`annualLeaveSelfBook`), the only toggle an admin can change (`ADMIN_EDITABLE_PERMISSION_FIELDS`). `operativeMode` reads off and is not shown. The level is changed only with "Change user type". The annual leave allowance fields (`annualLeaveEnabled`, days per year, leave year, carry-over) are not permission toggles and stay editable.
- **Managers:** the stored toggles, editable as before, except **Materials** and **Site audit**, always on and locked (`MANAGER_LOCKED_ON_PERMISSION_FIELDS`; both apps already saved them on). **Wholesalers** stays an editable toggle: a manager can have it off. **Operatives** off: they still schedule live active operatives onto the jobs they manage (`canScheduleOperatives`, `canWriteBooking`) but cannot add or manage operatives (`canManageOperatives`).
- **Operatives:** Materials and Site audit, editable.
- Existing user documents are never rewritten for this: locked values are derived when read (`parseUserDocument.permissions` is `effectivePermissions`), and `userProfileWriteFields` never writes a locked toggle (`keepStoredLockedPermissions`: top-level, dotted and `permissions` map entries keep their stored value), except when "Change user type" changes the level.
- **One set of rows** for Add User, its summary and Edit User on both apps: `permissionToggleRows({ level, user?, mode: 'add' | 'edit' | 'summary' })` → ordered `{ field, label, help, visible, editable, value }` (`PERMISSION_TOGGLE_CATALOGUE`). Admin: every row shown on and greyed out except Annual Leave Management. Manager: every row but Admin Access; Materials and Site audit on and greyed out. Operative: Materials and Site audit. Add User starts from `addUserPermissionDefaults(level)` (1.14.0, owner decision): **every toggle the adder can change starts off** and the adder turns them on one by one; locked toggles keep their locked value (admin and super admin: every toggle on and locked except Annual Leave Management, which starts off; manager: Materials and Site audit on and locked; operative: Materials and Site audit both start off). This applies to new users only — changing an existing person's user type keeps every saved toggle (`accountTypePermissions`, 1.15.0) and never applies these defaults.

**Change user type** (1.11.0) is `accountTypeChangeWrites({ person, kind, organizationId, roster, permissions? })`. **A type change keeps every saved toggle** (1.15.0, owner decisions round 6): `accountTypePermissions(kind, previous)` returns the person's stored toggles (top level, else `permissions.{key}`; a toggle never stored keeps the value it reads as) and changes only the level flags (`adminAccess`, `operativeMode`, `manager`); the screen's `permissions` are taken only for the toggles the new level can change (`accountTypeWritePermissions`: an admin only Annual Leave Management). An admin still reads every toggle on and locked except Annual Leave Management (`effectivePermissions`); the stored values stay untouched underneath and read again after a demotion, so manager → admin → manager returns the exact toggles and operative → manager keeps the operative's. (Before 1.15.0 a change kept Projects, Small Works, Weekly Report and Daily Overview and preset the rest.) One batch writes every document that decides the type in this organisation — `users/{uid}` (role, level flags and every toggle, top level and `permissions.{key}`), same-email users documents of this organisation, `organizations/{orgId}.members.{uid}` and `users/{uid}/orgMemberships/{orgId}` (role and nested permissions). When the person's `users/{uid}.organizationId` is another company, that profile is not rewritten: only `members.{uid}` and the membership here are written (their level here is read from them, `organizationLevelFor`) and the screen shows `ACCOUNT_TYPE_OTHER_COMPANY_NOTE`. It is refused with `ACCOUNT_TYPE_SUPER_ADMIN_MESSAGE` for a super admin who would stop being an admin. The security rules allow these writes to an admin or super admin of the organisation only. The plan is written as **one atomic batch** (1.12.2) — never the users document first and the rest after — so a refusal leaves nothing half applied; an admin may read the person's membership (`users/{uid}/orgMemberships/{orgId}` get) to build it. A type that is not the same on the users document of this organisation and `members.{uid}` (or the membership) is **half applied** (`accountTypeSyncState`: an older iOS build wrote only `users/{uid}`, or a save stopped half way); the users document is the source, Manage Users lists those people and Edit User says `ACCOUNT_TYPE_OUT_OF_SYNC_MESSAGE`, and the next Save re-applies `accountTypeChangeWrites` with that type. One save runs at a time (a second press is ignored) and a saved profile returns to the people list. A profile save syncs names to same-email users documents of this organisation only (a users query on email alone is never allowed by the rules).

**Line managers on Manage Users** (1.11.0): the picker lists `lineManagerCandidates(person, roster)` — the active admins, super admins and managers, never the person under any of their ids, never a pending invite or a deleted profile, by name; **one option per person** (1.14.0): roster rows that are the same person by `personIdSet` (two users documents on one email, an id in another letter case, a former invite id) are one option whose value is the person's live users document (active, signed up, not listed as another row's alias), and the level and status are read from that row; the selected values are `lineManagerSelectedIds(person, roster)` — a stored id that names the person's other document (or another letter case) shows that one option as selected; "No line manager" is offered only when `lineManagerOptions(person).allowsNoLineManager` (`lineManagerRequired` false: admins); the row reads `lineManagerSummary(person, roster)` → `{ label, ids: [{ id, name }] }` — each stored id resolved on the roster (an unknown id reads "Unknown person", never dropped), the label the first name with "+N more" only for N ≥ 1, "Not set" when none is stored, "No line manager" when chosen. **Changing the account type on Add User** (1.24.0): the picks become `lineManagerSelectionAfterLevelChange(picks, newLevel, roster, person?)` → `{ lineManagerIds, hasNoLineManager, dropped }` — each picked id that is still a `lineManagerCandidates` row is kept (as that candidate's id, once per person, in picked order) and the rest are dropped; "No line manager" is kept only when the new level allows it (admins, `lineManagerOptions`). Who may be picked does not depend on the level, so a type change keeps valid picks and drops "No line manager" when leaving admin. Picking the same type again changes nothing. The save is still checked by `lineManagerRequiredError`. **The invitee is never their own line manager** (1.27.0, owner decision 1): Add User passes the invite as it will be saved — `inviteDraftLineManagerSubject({ email, level })` → `{ id: INVITE_DRAFT_PERSON_ID ('invite-draft'), email, role, … }` — as `person` to `lineManagerCandidates`, `lineManagerSelectionAfterLevelChange` and `lineManagerRequiredError`, so the roster rows on the typed email are never offered or counted as the invitee's own line manager. Before 1.27.0 web passed no person (iOS already passed the draft).

**Accepting an invitation** (1.10.0; 1.11.0 below) is `inviteAcceptWrites({ existingProfile, placeholder, invitation })`: the role comes from the invitation (its `role`, else the kind its permissions give), never from another company's profile; with no account yet, `users/{authUid}` is written (from the placeholder when the claim names this invite's) and only then is the placeholder moved and removed and the claim pointed at the account; an account that already exists in another company keeps its profile, the placeholder stays (the in-organisation row with the invited pay) and its role there goes on its membership. Add User cannot tell that an email already has an account in another company (no account lookup by email). **1.11.0 (owner decisions round 3):** accepting applies exactly what the invitation stores, nothing more — the invitation is the only source of the person's access in that organisation. Add User stores the level as `role` on the invitation (`invitationCreateFields`) beside its permissions, pay and line manager, and writes the same on the placeholder. A new account gets `invitationProfileFields(invitation)` (role, permissions, employment type, one pay basis, line manager). An account in another company accepts with one batch, `inviteMembershipWrites({ invitation, invitationId, authUid, now })`: the membership created with the invitation's role (`invitationRole`) and `permissions` exactly as stored plus `invitationId`, `members.{uid}` = that role, and the invitation marked used; the placeholder keeps the invited pay and line manager. The security rules accept it only for a genuine, unused invitation to the signed-in email, marked used in the same batch (§16). **Who may invite** (1.12.0): admins invite any level; a manager with operatives access creates, changes and holds only an operative-only invitation (`invitationIsOperativeOnly`: `invitationRole` operative, operative mode on, no admin, super admin, manager or operatives toggle at the top level or in `permissions`) — the same test as their operative placeholder on `users/{uid}`. The rules refuse any other; an app can call `invitationIsOperativeOnly` before writing to show the reason.

**Deleting a person** (1.10.0). `canDeleteUser(actor, target, { roster, creatorUserId })` (`userDeleteRefusal` gives the reason, `USER_DELETE_REFUSAL_MESSAGES`) is the same test as the security rules: only an admin or super admin outside operative mode deletes; never themselves, the super admin or the organisation creator; an admin who is not super admin deletes only people who are not admins. Both apps check it before any write and show Delete only when it passes. The delete is one ordered plan, `userDeleteWrites({ orgId, user, actorUserId, platform, bookings, managerSiteBookings, operativeRows, managerRows, invitations, nowIso, tz })`: (1) one batch deleting `users/{uid}`, `users/{uid}/private/taxIds`, `users/{uid}/orgMemberships/{orgId}`, `organizations/{orgId}/userEmails/{email}` and `members.{uid}` — a refusal there changes nothing; (2) their labour and manager site bookings from today on, each with its tombstone; (3) their `operatives` / `managers` rows (by id or email); (4) their pending invitations in the organisation. Past bookings and their `bookedBy` names are never rewritten.

**Delete my account** (1.15.0, owner decisions round 6; web now, iOS later) is decided per organisation by `accountDeletionPath(viewer, roster, org)`:
- `handover_required` — the person is the organisation's super admin (`isOrganizationSuperAdmin`: its creator, or a users document of it flagged `isSuperAdmin`) and another active member is listed (`rosterSegment` active, not the person under any of their ids). They first make another admin the super admin with the existing ownership transfer (`creatorUserId`, Change Super Admin): the app offers the active admins (web `superAdminSuccessors`) or makes an active member an admin first (`accountTypeChangeWrites`) and then transfers. The account is not deleted until then (`ACCOUNT_HANDOVER_REQUIRED_MESSAGE`).
- `delete_with_company` — the super admin is the only active member: deleting the account deletes the company. They type the company name and DELETE (`organizationDeleteConfirmationError`, `ACCOUNT_DELETE_WITH_COMPANY_MESSAGE`); the company enters the 30-day scheduled state of §20 with `restoreBy: 'platform_owner'` (nobody is left to restore it; only the platform owner can) and the account is deleted straight away.
- `delete` — everyone else, and an organisation already scheduled for erasure: the account is deleted as before (company records stay; the name becomes "Deleted user").
Web `/api/account/delete` answers 409 `handover_required` or `company_delete_required` instead of the old `sole_admin`.

## 12. My Profile

Matches on every platform and updates live: profile photo (`profilePhotoURL`, with `profilePhotoUpdatedAt` set on every upload so other devices refresh the cached avatar), contact details, day/hourly rate and employment status (read-only), and billing details — VAT number and UTR — stored privately at `users/{uid}/private/taxIds` (`sensitiveProfile`). A photo upload stores a fresh download URL; a stale profile copy never removes or rolls back the photo. **Delete my account** (1.15.0) is on My Profile / Settings; what it does is `accountDeletionPath` (§11): a super admin with other active members hands super admin over first, a super admin alone in the organisation deletes the company with the account (§20), everyone else deletes only their account.

## 13. Notifications

- **My notifications** toggles are personal (`users/{uid}.notificationPreferences`), written as dotted partial updates, and sync across platforms (`parseUserNotificationPreferences`, `userNotificationPreferenceFieldPatch`).
- Which toggles a person sees depends on role and features (`visibleNotificationPreferenceKeys`). People who can see variations (`canSeeVariations`: admins and managers) have a **Variations** toggle (`variations`, on by default) covering all five variation types. Admins and super admins have a **Company activity** toggle (`companyActivity`, on by default: "People, clients, jobs added and warnings removed.") covering the six company activity types; the older per-type toggles for them (`projectCreated`, `smallWorksCreated`, `operativeCreated`, `managerCreated`, `clientCreated`, `warningDismissed`) are retired — still parsed, never shown.
- A toggle turned off stops that notification type's **device push** everywhere (`notificationPreferenceAllowsDelivery`, `devicePushAllowed`; enforced by the push Cloud Function). It **never hides the inbox row**: every notice addressed to the person stays in the notification centre and the unread count, on every platform (`notificationShowsInInbox`, `NOTIFICATION_TOGGLE_HIDES_INBOX_ROW = false`). The app-icon badge counts the same unread rows.
- **Reading inbox rows** is `parseNotificationDocument(docId, data, { role })` on every platform: the type is kept as the stored text (a type the app does not know is still listed, `known: false`), `relatedId` keeps any shape (UUID, day key, uid, job id), title / message / read flag default instead of dropping the row, and `destination` is `notificationDestination` for the role. Every app's type list (the iOS enum) accepts every type in `KNOWN_NOTIFICATION_TYPES` (the table below, the push allow-list and the legacy `material_added`); no row is dropped for its type. Marking read writes `isRead` only (`notificationReadWriteFields`).
- Types that send a device push are `DEVICE_PUSH_NOTIFICATION_TYPES`, including every variation type (`variation`, `variation_renumbered`, `variation_added`, `variation_from_tracker`, `variation_numbers_updated`).
- Organisation settings (material cut-off, schedule options) never appear in My notifications.
- Web never sends browser or OS notifications.

**Who receives each notification** (`lib/canonical/notificationRecipients.ts`). One rule per type, the same on every platform, and **never the person who caused it** (the actor) under any of their ids. Every recipient function is pure over the roster (`id`, `email`, `isActive`, `role`, `formerUserIds`, `sameEmailUserIds`, line-manager fields), drops inactive roster members, and de-duplicates ids without case. `personIdSet(person, roster)` is every id of a person (id, `formerUserIds`, `sameEmailUserIds`, roster rows with the same email); `excludeActor(ids, actor, roster)` removes them.
- Timesheets: `timesheetSubmittedRecipients(subject, roster)` — the subject's active line managers, else the active admins (never the subject); nobody when the sheet is self-signed. `timesheetSignedRecipients(subject, signer, roster)` — the subject, unless they signed. `lineManagerPeerRecipients(subject, actor, roster)` — the subject's other active line managers (no admin fallback).
- Annual leave: `holidayRequestRecipients(requester, roster)` — `leaveApproverIds` without the requester; nobody when the leave is self-booked. `holidayDecisionRecipients(requester, decider, roster)` — the requester, unless they decided.
- `bookingCreatedRecipients`, `deadlineAssignedRecipients`, `toolboxTalkRecipients`, `ideaRecipients` — the given ids without the actor.
- **Company activity** (`operative_created`, `manager_created`, `client_created`, `project_created`, `small_works_created`, `warning_removed`, `COMPANY_ACTIVITY_NOTICE_TYPES`): `companyActivityRecipients(actor, roster)` — the active admins and super admins outside operative mode, without the actor. One row per admin with `userId` and `actorUserId`; a row without `userId` is never written.
- **Push test** (`push_test`, Settings "send a test notification"): `pushTestRecipients(actor)` — the signed-in user only. It is the one type pushed to its actor (`notificationPushesToActor`); no toggle turns it off. On web its only effect is the inbox row.
- Job notices keep `materialOrderRecipients` and `receivesJobNotification`, then `excludeActor`. Neither has an "all admins" fallback: a job with no managers notifies no manager.
- **`relatedId`** (1.9.0) is the stored id of the record the notice is about, chosen per type by `NOTIFICATION_RELATED_ID` and written with `notificationRelatedId(type, ids)`: leave notices the holiday booking id; job, booking, material and project / small-works notices and `variation_renumbered` / `variation_numbers_updated` the job id; `variation` / `variation_added` / `variation_from_tracker` the variation id; `client_created` the client id; `operative_created` / `manager_created` the user id; tasks the task id; deadlines the deadline id; toolbox notices the issue id; `warning_removed` the warning key; `timesheet_submission_reminder` the payment day key; feedback notices the idea id; `line_manager_peer_update` the holiday booking id when it is about leave. Timesheet notices and `push_test` carry none (null) — timesheets are identified by `deepLinkUserId` + `deepLinkWeekStart`. Never a random id. A new row is `notificationCreateFields` (§1). 1.10.0: an app holding the one id the type names writes `notificationRelatedIdFor(type, id)` (null for a type that carries none) — the single source for every web and iOS write. `notificationDestination` opens a variation notice on the variation (`variationDetail`, relatedId the variation id) or the job's variations (`variations`, relatedId the job id); operatives get the inbox.
- **Leave notices other than a decision** (1.10.0). A manager or admin removing someone's approved leave writes `holiday_cancelled_by_manager`; a manager or admin booking approved leave for someone writes `holiday_booked_for_you`; both go to `holidayDecisionRecipients(person, actor)` (never the actor) under the annual-leave-decision toggle, and neither reuses `holiday_request_approved` / `holiday_request_declined`. Switching someone's self-book permission off writes no notice. No leave notice goes to every admin.
- Every inbox row an app writes carries `actorUserId` (the signed-in user who caused it; security rules require it to be that user when present). Scheduled notices nobody caused (`timesheet_submission_reminder`, `deadline_reminder`, `deadline_due`) leave it out. Notice dates shown in leave notices (`annualLeaveDecisionDateText` on web, `AnnualLeaveNoticeText.decisionDateText` on iOS) use the organisation business time zone. The push Cloud Function never pushes a row whose `userId` is its `actorUserId`, except a type whose push is for the actor (`notificationPushesToActor`: `push_test`).
- **The inbox is the rows addressed to the person, from their `createdAt`.** `inboxNotificationVisibleToUser(row, ids, now)` and `unreadNotificationBadgeCount(rows, ids, now)` count only rows whose `userId` is one of the person's ids; a scheduled row (`SCHEDULED_NOTIFICATION_TYPES`: `deadline_reminder`, `deadline_due`, `timesheet_submission_reminder`) only once its `createdAt` is not after now (1.10.0), any other row unless its `createdAt` is more than `INBOX_CREATED_AT_SKEW_MS` (5 minutes) after now (1.16.0); a row whose server time is not back yet is listed; the push function neither pushes nor badges a hidden row. A row with no `userId` is not an inbox row and is never listed, counted or pushed.
- **`createdAt` is server time** (1.16.0). A row due now is written with the app's SDK server timestamp, passed to `notificationCreateFields` as `serverTimestamp` (`notificationCreatedAtIsServerTime`); only a scheduled type written ahead of time keeps its own due instant. A writer's or reader's clock no longer hides a row or drops it out of the newest 150.
- **Recipients are accounts** (1.16.0). Every recipient function returns signed-in account ids only, one per person: each given id — an operatives catalogue id, an invite placeholder or former id, a same-email id, any letter case — goes through `notificationRecipientAccountId(id, roster, catalogue)` (the person's active users document that has signed up, not another row's former id, first in roster order) inside `excludeActor`; an id the roster cannot resolve is dropped. `bookingCreatedRecipients(bookedIds, booker, roster, catalogue)` takes the operatives rows. No app resolves recipients itself. (The inbox reads `userId == auth uid`, so a row addressed to any other id was pushed to whatever device held that document's token and never listed.)
- **Push payload** (1.16.0): `pushPayloadFields(row)` — `notificationId`, `type`, `relatedId`, `dayKey`, `catalogue`, `userId`, `organizationId` (strings, empty left out) — so a tapped push routes like the row in the centre.
- **Rows in another company** (1.16.0, interim until the owner decides on a cross-company inbox): the push carries `organizationId`; tapping a push or row of another organisation switches to it first when the person is a member (`notificationOrganizationSwitch({ rowOrganizationId, openOrganizationId, membershipIds })` with `sessionMembershipIds`), otherwise it routes in the open company. Each inbox still lists only the open organisation's rows. The push Cloud Function's app-icon badge counts the recipient's own unread rows the same way (bounded read).
- **Scheduled push types are not pushed** (1.10.0). The push Cloud Function runs when a row is created and has no schedule, so a row written ahead of time with a future `createdAt` (`timesheet_submission_reminder` written early, `deadline_reminder`, `deadline_due`) is never pushed — it appears in the inbox when its `createdAt` arrives. A row written when it is due is pushed as usual (its type's push flag).
- Timesheet notice document ids are each app's synthetic UUID of `timesheetNotificationDedupeKey` — the period start as unix seconds of midnight in the organisation zone (never the device calendar).
- **Device push tokens belong to exactly one account** (1.16.0): the last account to register it. A token is written to `users/{uid}.pushTokens` of the account signed in on that device (its Firebase Auth uid), never copied to other users documents and never to an invite placeholder users document (a UUID-shaped id, `isPushTokenPlaceholderUserId`, 1.17.0); signing out removes this device's token from every users document it was written to. The server enforces it: when a users document gains a token (`addedPushTokens`), the `pushTokenSingleOwner` Cloud Function removes it from every other users document (`pushTokenOwnerWrites`, an `array-contains` query and `arrayRemove`), so a forced or offline sign-out can no longer leave it behind. **Every iOS sign-out goes through one path** (iOS PR #166, `FirebaseBackend.signOutRemovingPushToken`, a bounded 5-second wait): a forced sign-out (expired session, trial blocked) removes this device's token wherever the app is still signed in to do so; a sign-out Firebase starts itself, when the app can no longer write, relies on the server's single-owner rule (`pushTokenSingleOwner`). `scripts/dedupe-push-tokens.mjs` (dry run by default, `--apply`) cleans existing data once (`pushTokenDedupePlan`, 1.17.0): a placeholder users document always loses its tokens; a token on more than one signed-in account stays on the one with the newest `pushTokenUpdatedAt` (`updatedAt` is compared only when none of them has `pushTokenUpdatedAt`); a token found only on placeholders is removed everywhere and the phone registers it again on its signed-in uid at next launch. A placeholder is never the owner in `pushTokenSingleOwner` either: when a placeholder gains a token, the token is removed from that placeholder (`pushTokenOwnerWrites`) and the signed-in accounts keep it. The push function also skips any recipient token that is on the actor's own users document (`pushTokensExcludingActor`).
- **Recipients are members** (1.12.0). An inbox row is written only for a member of the row's organisation (`organizationMemberActive`: a key of `members`, the creator, a users document of that organisation, or a membership there); the security rules refuse any other `userId` and a row without one. The push Cloud Function pushes a row only to an active member of its organisation (the same function; a person that organisation deactivated gets no push). A stranger's own company can no longer push text to a uid elsewhere.
- `NOTIFICATION_CATALOG` is the table below (`notificationCatalogRow(type)`). Push follows `DEVICE_PUSH_NOTIFICATION_TYPES`. `variation_from_tracker`, `variation_numbers_updated`, `booking_clash`, `booked_onto_job` and `material_order_created` are on the push allow-list but nothing writes them. ## 14. Authentication and organisations

- Sign-in and passwords use Firebase Auth email/password on every platform; a password change applies everywhere. Every password — sign-up, invite set-up, reset, change — must be at least 8 characters; the platform owner's developer account needs 10 (`PASSWORD_MIN_LENGTH`, `passwordMinLength`, `passwordPolicyError` → "Password must be at least N characters."). The platform owner is `isPlatformOwnerEmail(email)` (`PLATFORM_OWNER_EMAIL`, compared without case); `passwordMinLength({ email })` applies the 10 for it. No complexity rule.
- **The platform owner** (1.12.0) is the signed-in Firebase Auth account whose token email is `PLATFORM_OWNER_EMAIL` and is verified (`isVerifiedPlatformOwner`; security rules `isPlatformOwner`, owner API routes `requireOwner`). A users document's `email` never counts.
- **Deactivated** (1.12.0): a person is deactivated in an organisation when their users document is that organisation's and says `isActive: false`, or their membership there says `accountActive` (else `isActive`) false (`organizationMemberActive`). The security rules give them no access to that organisation's data and the push function sends them nothing; they still read their own users document and memberships, so the apps show the deactivated screen and Switch organisation.
- **Changing a sign-in email** (1.12.0): the person's own users document `email` changes only to their signed-in Auth email — after Firebase Auth has changed it (iOS `sendEmailVerification(beforeUpdatingEmail:)` / web `verifyBeforeUpdateEmail`, then the next sign-in). An admin changes a person's email from Manage Users (both apps), or the platform owner from the support tool. **1.13.0:** a person's own profile save decides with `selfEmailChangeAction({ storedEmail, nextEmail })` — `verifyBeforeUpdate` asks Auth to verify the new address (the message is `selfEmailChangeSentMessage`) and the rest of the save goes ahead with the stored email; nothing else is written until Auth has changed it. On the next sign-in with a verified token email that differs from `users/{uid}.email`, `signInEmailSyncWrites` gives the writes: `users/{uid}.email` = the token email, the new `userEmails/{email}` claim for the account, and the old claim deleted when it is the account's. The rules allow exactly these (§16).
- **Switching organisation is per device.** Each platform remembers the last organisation it opened (web `pp.webActiveOrg:{userId}`, iOS `cached_organizationId`) and reopens to it (`chooseSessionOrganization`). Switching on one platform does not change another platform, and does not write `users/{uid}.organizationId`.
- **Membership is shared.** The list of organisations a person belongs to is shared data (`sessionMembershipIds`).
- **One membership shape** (1.10.0). `users/{uid}/orgMemberships/{orgId}` is read with `parseOrgMembershipDocument` (nested `permissions.{key}` first, else the legacy flat key, else its default — `ORG_MEMBERSHIP_DEFAULT_ON`; operative mode turns manager and operatives off; `accountActive`, else `isActive`) and written with `orgMembershipWriteFields({ organizationId, stored, next, writer, now })`: nested permissions only, changed fields only, and an admin update removes the legacy flat keys. Only an admin of that organisation writes role, permissions, super admin or the active flag (`ORG_MEMBERSHIP_ADMIN_FIELDS`); the person writes only acceptance (`status: 'active'`, `acceptedAt`). No app copies its users document onto a membership on a switch.
- **A role belongs to an organisation** (1.10.0). Whether someone is an admin or manager *of an organisation* comes from that organisation: their `users/{uid}` flags only when that document's `organizationId` is this organisation, otherwise this organisation's `members` map entry. A manager in company A who is an operative in company B is an operative in B (security rules `callerOrgRole`).

## 17. Job access and reads (1.10.0)

Reads are enforced by the security rules, not only filtered on screen. Firestore rules are not filters: an app may only run a query whose every possible result the viewer may read, so both apps build their queries from one plan.

- **Who sees which job** (`seesEveryJob(role, kind, toggles)`, `canSeeJob(viewer, job, managers, kind)`): admins and super admins outside operative mode see every job; a manager with the Projects (`permissions.projects`) or Small works (`permissions.smallWorks`) add/edit/manage permission sees every job of that kind; any other manager sees only the jobs they manage; operatives see no job list, only the jobs of their own bookings, tasks and deadlines, read one by one.
- **Who reads which bookings** (1.11.0, by kind): admins read every booking (`readsEveryBooking`). Every labour, subcontractor and job-linked manager site booking carries `jobCollection` (`projects` | `smallWorks`, `bookingJobCollectionFields`; the collection decides the kind, `jobKind`), written on create and edit by both apps. A manager with the Projects or Small works toggle reads every booking whose `jobCollection` is that kind (one-toggle managers only that kind). Every manager reads the bookings on the jobs they manage and their own; operatives read only their own labour bookings (their account id, a former or same-email id, or an `operatives` row with their email). A booking without `jobCollection` (saved before 1.11.0, until `scripts/backfill-booking-job-collection.mjs` runs) is read only by admins, its job's managers and the people it books; a manager site booking with no job (office, working from home, site survey, custom) by admins and its own manager.
- **Job queries** — `jobQueryPlan(viewer, { documentIds })` → `{ seesEvery, queries }`: per collection `{ kind: 'all' }`, `{ kind: 'managed', field: 'managerUserIds', op: 'array-contains', value: <uid> }`, or for operatives `{ kind: 'documents', ids }` (single-document reads of each id spelling; a job list is refused to them).
- **Booking queries** — `bookingQueryPlan(viewer, visibleJobIds, { ownBookingIds })` → `{ readsEveryBooking, queries }`: whole collections for `readsEveryBooking`; otherwise, for each kind the manager has the toggle for, one `jobCollection ==` <kind> query per collection (1.11.0), and per job in `visibleJobIds` (the jobs of the kinds they have no toggle for — their managed jobs) one query per collection — `bookings` and `subcontractorBookings` `projectId in`, `managerSiteBookings` `locationId in` — over that job's id spellings (`jobIdQueryValues`: as stored, plus upper case for an all-lower id and lower case for an all-upper id; a mixed-case id only as stored, since the rules could not trace another spelling to it), and their own bookings: `bookings` `operativeId in` (`OWN_BOOKING_IDS_PER_QUERY` = 4 per query) and, for managers, `managerSiteBookings` `userId ==` <uid>. Each query also takes the collection's download bound (`date >= bookingLoadStart`, §1); the composite indexes are in `firestore.indexes.json`.
- **Rules limits.** A query may look up 10 documents (`get` / `exists`) in total across all its `in` values, and a rule evaluation stops at 1000 expressions, so a booking query carries one job (`JOBS_PER_BOOKING_QUERY` = 1) and the rules compute the caller's role once per rule. `FIRESTORE_IN_QUERY_LIMIT` (30) is Firestore's own cap, not the plan's chunk.
- **Daily Overview and warnings** for a viewer who does not see every job cover only their jobs and the people booked on them (`warningScopeFor`, §5, §6).
- A viewer whose role changes, or a manager added to or removed from a job, re-plans on the next snapshot: the job leaves or joins their lists and its bookings' queries are closed or opened.
- **Job kind** (1.11.0): `jobKind(doc, collection)` — a `projects` document is a project and a `smallWorks` document is a small works job, whatever `jobType` says; `jobType` decides only when the collection is unknown. A project and a small works job sharing one id (older iOS builds) are both kept, each in its own list; `jobIdsInBothCollections` lists them for the owner and the booking backfill reports their bookings.
- **Switched by data in the rules** (1.12.1): the security rules apply this section's read scoping only when `enforcedReads` is on for the organisation (§18; written by the platform owner only, read by the rules — one document read per rule). While it is off, every member of the organisation reads every job and booking, as before 1.10.0, so the rules deploy does not wait for the backfills. Writes (§16: job create and edit, `canWriteBooking` / `canDeleteBooking`, tombstones, `jobCollection`) and every other rule are never switched by it. **1.26.0: the apps follow the same switch.** Each app reads `platformConfig/app` and passes `enforced: securitySwitchOn(config, organizationId, 'enforcedReads')` to `jobQueryPlan`, `bookingQueryPlan`, `readsEveryBooking` and `warningScopeFor`, so it plans whole-collection reads while the switch is off and the scoped queries while it is on — no release has to flip a constant first, and an app that supports 1.26.0 works either way. Web listens to the document and re-plans its job and booking listeners the moment the switch changes; iOS reads it on launch and on return to the foreground (as for `minimumIosBuild`) and re-plans then. Rollback is switching it off. An app build older than its 1.26.0 support still plans whole collections and loses the job and booking lists of managers without a job toggle and of operatives while the switch is on, so `minimumIosBuild` is raised to that build first.
- **Switched off until the backfill** (1.10.1; 1.11.0 kind reads too; from 1.26.0 only the default when no switch value is passed): `ENFORCED_READS_ACTIVE` is false. While false, `jobQueryPlan` returns whole-collection job queries for staff and `readsEveryBooking` is true for every manager, so reads are as before 1.10.0; each app still shows a manager only the jobs `canSeeJob` allows. It becomes true in the release after the owner has run the backfills (`managerUserIds` and, from 1.11.0, `jobCollection`), and that release ships before the rules deploy. 1.11.0 keeps it false: its by-kind booking queries are planned only once it is true.
- Known limit: an operative can read a job document by id without the rules knowing whether they are booked on it (the rules cannot query their bookings); listing jobs is refused to them.

## 18. Forced app update (1.12.0)

One platform document says the oldest build each platform may run:

`platformConfig/app` `{ minimumIosBuild: number, minimumWebVersion?: string, enforcedReads?: boolean, enforcedReadsOrganizationIds?: string[], privatePay?: boolean, privatePayOrganizationIds?: string[], organizationErasureEnabled?: boolean }` (`organizationErasureEnabled`, 1.15.0: the §20 eraser's kill switch, read only by the server)

When true the app shows only the update screen.

- **The security switches** (1.26.0; `SECURITY_SWITCHES`, `securitySwitchOn(config, organizationId, name)`, `securitySwitches(config, organizationId)`). `enforcedReads` (1.12.1) turns on the §17 job and booking read scoping; `privatePay` (1.13.0) limits rate history, the `operativeProfiles` mirror and timesheets to the people who may see that person's pay and keeps pay values off `users`, `operatives` and `managers` (§8, §16). Each is on for every organisation when its field is exactly `true`, or for one organisation when its id (exactly as stored) is in `enforcedReadsOrganizationIds` / `privatePayOrganizationIds` (`SECURITY_SWITCH_ORGANIZATION_FIELDS`), so the owner can switch one company on first; anything else is off. The security rules (`enforcedReadsOn(orgId)`, `privatePayOn(orgId)`) and the apps read the same value: from 1.26.0 the apps plan their reads and pay writes from it (§8, §17), so they work with each switch on or off. Order and rollback: `docs/SECURITY_SWITCHES.md`.

## 19. Lapsed subscription (1.13.0)

Owner decisions round 4, Q3. When the organisation's subscription has lapsed (`hasAccess(billing)` false: canceled, unpaid, paused, incomplete, or past_due more than 7 days after the failed payment), both apps are blocked — not read-only — and show only `SUBSCRIPTION_LAPSED_MESSAGE`: "The organisation's Project Planner subscription has lapsed. Please contact your system administrator and ask them to renew." and Sign out (`subscriptionAccess({ billing, viewerIsAdmin, viewerIsPlatformOwner })` → `open` | `adminBillingOnly` | `blocked`). Nothing is ever deleted; access returns as soon as Stripe marks the subscription paid. Admins and super admins (`adminBillingOnly`) also reach the billing screen — on web Settings → Billing, and nothing else (`SUBSCRIPTION_LAPSED_ADMIN_NOTE`, web only). **On iOS everyone, admins and super admins included, sees only `SUBSCRIPTION_LAPSED_MESSAGE` and Sign out** (1.14.0, owner decision, App Store guideline 3.1.3): neither `SUBSCRIPTION_LAPSED_ADMIN_NOTE` ("renew in Settings → Billing") nor `SUBSCRIPTION_LAPSED_ADMIN_WEB_NOTE` is ever shown on iPhone, and the iOS app links to no billing or renewal. Missing billing is open (trials and organisations created before billing). The platform owner is never blocked.

The security rules enforce it (§16) from two fields the Stripe webhook writes into `billing` on every sync (`billingAccessFields`): `accessOpen` (= `hasAccess` at the time) and `accessClosesAt` (the end of the 7-day grace while a payment has failed), so the grace ends on time without another Stripe event. The rules close the organisation when `accessOpen` is false or `accessClosesAt` has passed; missing fields are open, so an organisation whose billing has not synced since 1.13.0 is closed by the apps only until its next Stripe event.

## 20. Company deletion (1.15.0)

Owner decisions round 6. The canonical module is `lib/canonical/organizationDeletion.ts`.
- **Who and where.** Web only: Settings → Billing → **Delete organisation**, shown to the super admin only (`isOrganizationSuperAdmin`). iOS has no delete control (it reaches the company only through "Delete my account", §11, later). The form explains what happens (`ORGANIZATION_DELETE_BODY`) and asks for the company name and DELETE (`organizationDeleteConfirmationError`; the server checks both again). There is no data export in the apps yet; the form says to email info@projectplanner.us for a copy first.
- **What deleting does** (server, admin SDK): cancels the Stripe subscription at the end of the paid period (`cancel_at_period_end`, no refund — refunds are made by hand in Stripe), writes `organizations/{orgId}.deletion = { status: 'scheduled', requestedAt, requestedBy, eraseAfter: requestedAt + DELETION_RESTORE_DAYS (30; 60 before 1.27.0) days, restoreBy: 'super_admin' | 'platform_owner' }` (`organizationDeletionWriteFields`), and emails the platform owner (info@projectplanner.us) and the person who deleted it through the email function's server mode.
- **Locked for 30 days** (1.27.0, owner decision: the same as file recovery; 60 before — a deletion already scheduled keeps its stored `eraseAfter`, so it is not erased sooner) (`organizationDeletionState(org, now)` → `active` | `scheduled` (locked, `due` once `eraseAfter` passed) | `erased`). Every member of the organisation, on every platform, sees only `organizationDeletedMessage(eraseAfter, timeZone)` — "This organisation has been deleted and will be erased on {date}." (organisation zone) — and Sign out; the security rules refuse its data (§16). The super admin also sees **Restore** when `canRestoreOrganization` (the deletion was theirs, `restoreBy` `super_admin`): restore removes `deletion` and, when the subscription is still in its period, resumes it (`cancel_at_period_end` false); a subscription that has already ended is started again from Billing. A company deleted with its last member's account (`restoreBy` `platform_owner`) is restored only by the platform owner. The platform owner is never locked out.
- **Erased on day 61** by a daily scheduled Cloud Function (`eraseDeletedOrganizations`, `functions/organizationEraser.js`; `organizationEraseDue`): users whose users document names the organisation and who belong to no other organisation (their tax ids, memberships, users document and Firebase Auth account; never the platform owner), every membership of the organisation, its invitations, its Storage files under `organizations/{orgId}/`, and the organisation document with every subcollection (bookings, timesheets, `userEmails` claims, …). People who also belong to another organisation keep their account and lose only this membership. An audit row `erasedOrganizations/{orgId}` `{ erasedAt, name, status }` is kept (`erasedOrganizationAuditFields`; no personal data). The eraser is idempotent and can run as a dry run. **Kill switch:** the eraser deletes nothing unless `platformConfig/app.organizationErasureEnabled` is `true` (written by the platform owner only, §18). While it is missing, false or unreadable, every daily run is a dry run that only logs each due organisation's id, name and counts (people deleted and kept, memberships, invitations). It is deployed off; the platform owner turns it on after reviewing the first dry-run log. `functions/organizationEraser.emulator.test.js` runs the eraser against the Firestore emulator (not in CI; how to run it is in the file).

## 21. Job lists (1.21.0, 1.21.1)

Which jobs appear where — every Projects and Small works list, their tabs and counts, the Home "active projects" figure, Clients, Site Audit, the weekly report's job lookups and every booking picker — is decided by `lib/canonical/worksLists.ts` on every platform, never by a store, listener or screen (owner rule after small works vanished on iOS: an iOS store kept live small works only, and a web store flag dropped inactive projects depending on which screen loaded last). Inputs are plain data (jobs as read by `parseJobDocument`, the viewer as `JobAccessViewer`, arrays of rows), so iOS calls the same functions through `CanonicalBusinessEngine`.

- **Stores keep every job.** A job store or listener keeps every document the reader accepts (`parseJobDocument`, `workDocuments`), live or not. Lookups by id (task job, weekly report rows, timesheet labels) use that full list, never a filtered one.
- **List membership** — `worksListMembership(jobs, kind)`: a Projects (`projects`) or Small works (`smallWorks`) list holds every document of that kind, once by id (two jobs with one job number both stay), inactive ones included. The collection decides the kind (`jobKind`), never `jobType`.
- **Who sees which job** — `visibleJobs(jobs, viewer, context)` (§17, `canSeeJob`): admins and super admins outside operative mode see every job (a per-job hide list never hides a job from them); a manager sees what `canSeeJob` allows for the job's kind, less jobs whose `hiddenManagerUserIds` names them; an operative sees the jobs of their own labour bookings (a status that occupies the day, `bookingOccupiesDay`), of tasks assigned to them and of their deadlines (`operativeJobIds`; also the documents their `jobQueryPlan` reads), less jobs whose `hiddenOperativeUserIds` names them; an account with no staff role sees the jobs it manages or is booked onto. The viewer is matched by every id and by email (`worksListPersonIds`: account ids, `operatives` and `managers` rows on their email), never by name. `context` = `{ managers, operatives, bookings, managerSiteBookings, tasks, deadlineJobIds }`.
- **Tabs and counts** — `jobWorkStatus(job, now, timeZone)` (`workStatusOn` on the organisation-zone day; the zone is required, never London or the device by default), `worksTab(status)` (inactive → Completed), `worksInTab(jobs, tab, now, timeZone)`, `worksTabCounts(jobs, now, timeZone)` → `{ all, active, upcoming, completed }`. All is every job listed, and every job is in exactly one of Active, Upcoming and Completed, so the tiles add up to All. A job's days come from `startDayKey`/`endDayKey`, else `startMs`/`endMs`, else `startDate`/`endDate`.
- **Bookable jobs** (owner decision) — `bookableJobs(jobs, viewer, context)`: the jobs a person may book onto — visible (`visibleJobs`), not inactive (`isLive` not stored false) and writable (`canWriteBooking` for `context.bookingCollection`, default `bookings`; a manager site booking for My Schedule). **The job's start and end dates are never checked**: a job past its end date, and a job with no end date, are bookable on any day. Optional trailing `dayKeys` / `timeZone` arguments are accepted and ignored. Operatives book onto no job. Every booking picker uses it: Book labour, My Schedule self-booking, the Daily Overview booking sheet, the job scheduler (Schedule booking) and Quick Add. A picker's tabs only sort its bookable list.
- **Home "active projects"** — `activeJobsCount(jobs, viewer, context, now, timeZone)`: projects and small works together that `visibleJobs` shows and that are active today — the same jobs the lists show under Active (per-job hide lists applied; an operative's jobs are their bookings, tasks and deadlines; manager site bookings count only for an account with no staff role). Before 1.21.0 iOS also counted an operative's manager site bookings and web ignored hide lists.
- **Job number** — `parseJobDocument` reads a numeric `jobNumber` as its text (4521 → "4521"); it read as blank on both apps.
- **Site map** (1.23.0, audit finding 17) — `siteMapPins({ jobs, bookings, managerSiteBookings, dayKey, timeZone, people })` → `{ jobId, bookingCount, peopleCount }[]`: one pin per job that is not inactive, counting that organisation day's labour bookings whose status occupies the day (`bookingOccupiesDay`; cancelled never) and manager schedule bookings on the job (project or small works, `isSiteLocationType`); `peopleCount` counts each person once (`personIdSet` over users, `operatives` and `managers` rows). The map opens on today in the organisation zone (`dayKeyInOrganizationZone`), never the device day. Before 1.23.0 web counted cancelled bookings.
- **Job tile badges** (1.23.0, audit finding 22) — `jobTileBadges({ jobId, bookings, managerSiteBookings, subcontractorBookings, tasks, people })` → `{ tentativeBookings, openTasks, activeUsers }`: Scheduling = the job's Tentative labour bookings (all time); Tasks = the job's tasks not completed (`normalizeProjectTaskStatus`); Active users = the people booked on the job (labour bookings not cancelled, manager schedule bookings on it), each person once under all their ids, plus subcontractor firms with an open (Confirmed or Tentative) booking. Before 1.23.0 a person under two ids, or with both a labour and a manager booking, counted twice. Job ids compare without case.


## 22. Variation numbers (1.22.0)

Variation (VO) numbers are written by one rule on every platform (audit finding 8: the two apps wrote different numbers for the same job).
- **A label's number is its trailing digits only** (owner decision): `variationNumberValue` — "VO-003" → 3, "V2-003" → 3; a label not ending in digits is 0. Before 1.22.0 iOS joined every digit ("V2-003" → 2003) and wrote "V2-2004" where web wrote "V2-004".
- **The next number** is `nextVariationNumber(existingNumbers, prefix, padding)`: one higher than the highest number among every variation of the job — open, submitted, closed and **deleted** — with the tracker's `prefix` and `padding` (`variationTrackers/{parentId}`; default "VO-", 3; `formatVariationNumber`). Gaps stay empty.
- **Duplicate check** (`variationNumberTaken(existing, voNumber, exceptId)`): a number is taken when another variation of the job has it, trimmed and without case, **deleted variations included** — a number that was ever issued is never reused (decision: before 1.22.0 iOS skipped deleted ones, so it could re-issue a deleted variation's number). The variation being edited is skipped by id without case; a blank number is never taken.
- Renumbering previews (`previewRenumber`) and tracker order use the same trailing-digit value.
- **One list from every source** (1.23.0, audit finding 21): `mergeVariationSources(collectionRows, fallbackRows, itemDocs)` — the `variations` collection, the older iOS settings-log fallback and the one-document fallbacks, one row per id (without case); the newer `updatedAtMs` wins and, on a tie, the collection row, then the item document, then the settings log. The open-variations badge is `openVariationCount(rows)`: rows not deleted whose status is `open` (any case). The rule both apps already used, written once.

## 23. Home, tasks and deadlines (1.23.0)

Audit findings 12 and 18: each app counted these on its own day (web London or the browser, iOS the device) and by raw ids.
- **One day.** Every figure uses the organisation-zone day of now (`organizationTimeZone`); a stored due date is turned into that zone's day with `dueDayKey` (any stored shape `holidayDocumentDayKey` reads).
- **Home overview** — `homeOverviewMetrics({ nowMs, timeZone, viewer, roster, operatives, managers, tasks, bookings, managerSiteBookings, holidays, nonWorkingDayKeys })` → `{ dayKey, tasksDueToday, tasksDueThisWeek, tasksOverdue, outstandingTasksAllUsers, operativesOnSiteToday, managersOnSiteToday, peopleOnSiteToday, operativesOnALToday, managersOnALToday }`. A task is the viewer's when any assignee (operative or manager ids) is one of the viewer's ids (`personIdSet` of their account and email over the users, `operatives` and `managers` rows); due this week is today and the next six days; open tasks counts every task given that is not completed. People on site are the people with a labour booking today that occupies the day, or a manager schedule booking today on a project or small works — each person once (`peopleOnSiteToday` is not the sum of the two when one person has both). People on leave are active people with approved leave covering today (`leaveRecordDayKeys`), on the Operatives list (or with only an `operatives` row) or on the Managers list (§11); admins are not counted. The "active projects" figure stays `activeJobsCount` (§21).
- **Tasks** — `isTaskOverdue(task, nowMs, timeZone)`: not completed (`normalizeProjectTaskStatus`) and due before today; a task due today is not overdue.
- **Deadlines** — `deadlineUrgency(item, nowMs, timeZone)`: complete → overdue (before today, even when blocked) → blocked → today → tomorrow → soon (2–3 days) → this week (4–7 days) → later; `deadlineDaysRemaining` for the days. The rule both apps used, on the organisation day.

## 24. Uploaded files (1.25.0)

Launch checklist 2.2: an uploaded file is never deleted outright or lost by someone who did not upload it. `lib/canonical/storedFiles.ts`; `storage.rules` enforces the same rule on the server.
- **Where files live.** Every upload is under `organizations/{orgId}/…` (`storedFileKind(path)` → `{ kind, organizationId, objectName, ownerUserId }`, `STORED_FILE_KINDS`): profile photos `userProfiles/{userId}/profile.jpg`; the company logo `branding/company_logo/{name}`; timesheet exports `timesheetExports/{seconds}_{name}`; qualification certificates `operatives/{operativeId}/qualifications/{qualificationId}/certificates/{name}`; variation evidence `healthSafety/{jobId}/variations/{name}` (web), `healthSafety/{jobId}/variationEvidence/{name}` and `variations/{variationId}/{name}` (iOS); site audit photos `siteAudits/{auditId}/images/{name}`; task files `tasks/{taskId}/{name}` (web), `tasks/{taskId}/files|images/{name}` (iOS); health & safety files (talks, RAMS, other, deadlines) `healthSafety/{jobId}/{category}/{name}`. Any other prefix is refused for everyone.
- **Every upload is a new object.** Its name is `storedFileObjectName({ uid, unixMs, extension })` → `{uid}_{unixMs}.{ext}` (the uploader's Auth uid; the original file name is never copied in), so a replacement — a new certificate, a new RAMS, a new logo — never overwrites the file it replaces and every stored link keeps working. `storedFileUploader(path)` reads the uploader and upload time back from the name. Two exceptions keep their fixed names because both apps read them: the profile photo (`profile.jpg`, replaced by the person or an admin; the replaced version is kept by the bucket's soft delete) and timesheet exports (`{seconds}_{name}`, no uploader in the name).
- **Who may delete** — (1.27.0, owner decision 3: kept as it is — an admin or super admin outside operative mode may still delete any file of their organisation; a deleted object is recoverable for `FILE_RECOVERY_RETENTION_DAYS`.) `fileDeletePermission({ storagePath, organizationId, viewerUserId, viewerRole, nowMs, uploadedAtMs? })` → `{ allowed, reason, undoEndsAtMs }`: an admin or super admin of that organisation outside operative mode (`reason: 'admin'`); for a profile photo also the person it belongs to (`own_profile_photo`); company logos and timesheet exports admins only (`admin_only`); every other file also its uploader, within `FILE_UNDO_WINDOW_MINUTES` (15) of the upload (`uploader_undo`; after that `undo_expired`) — for a retried upload or a file that uploaded but failed to link. Nobody else, managers included (`not_uploader`); never a file in another organisation (`other_organization`). Uploader ids compare exactly (Auth uids are case-sensitive). The server uses the object's `timeCreated`; an app passes the stored upload time when it has one, else the time in the name. A file whose name does not follow the pattern (uploaded before October 2026) has no provable uploader: admins only.
- **Overwriting an existing object** is allowed only to its uploader inside the same window (a retry of the same path), and for a profile photo to the person or an admin. An admin deletes but never overwrites another person's file.
- **Removing a file from a record** (variation evidence, a health & safety row, a task attachment, a certificate) deletes the Storage object only when `fileDeletePermission` allows it; otherwise the record drops its link and the object is kept, and the app says `FILE_KEPT_ON_REMOVE_COPY` ("Removed from this list. The file itself is kept so an admin can restore it."). Deleting a job, task, audit or H&S row never deletes its files.
- **Removed variation evidence is recorded** (1.27.0, owner decision 4). Unlinking an evidence file from a variation is one partial update (`variationEvidenceRemovalWriteFields(stored, { evidenceId, removedBy, removedAt })` → `{ set: { evidence, evidenceCount, removedEvidence } }`, built from the stored document, on `variations/{id}` and its `settings/variationItem_{id}` copy): the entry leaves `evidence` and `{ path, name, removedBy, removedAt }` is appended to the variation's `removedEvidence` list (`path` the Storage path, else the download URL). Nothing is ever taken off that list and no other save writes it. (Known gap: the apps keep this list append-only and web removes evidence in a transaction; the security rules do not yet refuse a staff write that shortens it.) `parseVariationDocument` returns it as `removedEvidence` (oldest first). Admins and super admins outside operative mode (`canViewRemovedEvidence`) see it in the variation detail under `removedEvidenceHeading(n)` — "Removed evidence (n)" — with the name, path, who removed it and when, to find and restore the file.
- **Server-side deletes.** Only the company eraser (§20, `eraseDeletedOrganizations`, day 61 after a company deletion) deletes Storage objects, with the admin SDK: everything under `organizations/{orgId}/`.
- **Recovery** is the bucket's Google Cloud Storage soft delete (deleted and overwritten objects are kept for the retention period and can be restored), switched on and checked by the platform owner in the Cloud console (Deploy notes 1.25.0). No app or rule changes bucket settings. **Retention is 30 days** (1.27.0, owner decision 5; `FILE_RECOVERY_RETENTION_DAYS`): deleted and replaced files, and the files of a company the §20 eraser has erased, are kept for up to 30 days, then permanently removed. Both apps' privacy policy (Retention) and data processing agreement (Deletion and Return) say so in one sentence, word for word: `DELETED_DATA_RETENTION_NOTICE` ("A deleted company can be restored for 30 days, after which its data is erased. Deleted files, including the files of an erased company, are kept for up to 30 days so they can be recovered, then permanently removed.").

## How the rulebook changes

1. A rule change starts in `project-planner-web`: edit the function in `lib/canonical`, add a test in `lib/canonical/canonical.test.ts`, and edit this file.
2. Bump `Version:` (major: a breaking field or behaviour change; minor: a new rule; patch: wording) and add a `### <version> — <date>` entry under Changelog.
3. `npm run build:canonical` packs the script with this file's version stamped in, writes `lib/canonical/dist/canonical-manifest.json`, and mirrors the files into `../project-planner-ios` when it is checked out.
4. `npm run rulebook:handoff` writes the iOS follow-on prompt to `docs/ios-handoff/v<version>.md` and `docs/ios-handoff/LATEST.md`.
5. Enforcement: the pre-commit hook, CI (`.github/workflows/rulebook.yml`) and the Claude Code Stop hook (`.claude/settings.json`) all run `node scripts/rulebook-sync.mjs check` and refuse a change to `lib/canonical`, `firestore.rules`, `storage.rules`, `firestore.indexes.json` or this file without a version bump, a changelog entry, a fresh pack and a hand-off. A daily CI job compares the iOS repo's mirror with this version and fails when iOS is behind.
6. iOS runs `scripts/sync-rulebook-from-web.sh`, and its `RulebookParityTests` fail when its mirror, manifest or packed script differ from what web published.
7. **A write-shape change updates the cross-platform contract** (1.10.0): when an app changes what it writes to a shared collection, or a reader changes what it returns, regenerate `lib/canonical/cross-platform-contract.json` (`npx tsx lib/canonical/crossPlatformContract.samples.ts --write`; web samples come from the web writers, iOS samples are copied from the iOS payload builders named in `iosWriter`) in the same change. `crossPlatformContract.test.ts` fails until it is, and iOS `CrossPlatformContractTests` fails when its builders no longer produce `iosWritten`.
8. A gap found on iOS is reported to the web agent and fixed here first — never by diverging on iOS.

- Never re-save what you didn't change (§1): only a user action or its offline replay writes (`SYNC_WRITE_TRIGGERS`, `syncWriteAllowed`); a save writes only the changed records (`recordsToSave`); an edit of a missing document is refused, never re-created (`editOfMissingDocumentIsRefused`, `replayRefusedIsFinal`, `EDIT_OF_MISSING_DOCUMENT_MESSAGE`). iOS re-saved every in-memory project, small work and client on each return to the foreground, writing stale values over web edits and re-creating jobs and clients deleted on web.
- Closed 1.8.0 gaps: a deliberate removal of the last health & safety row (`healthSafetyDocumentWriteFields` `removedIds`) or job type (`jobTypesWriteFields` `removed`) can be saved; removing a recipient or issue removes its signatures (`healthSafetySignatureRemovalWrites`); shared writers for `variationTrackers` (`variationTrackerWriteFields`), `settings/variationTrades` (`parseVariationTrades`, `variationTradesWriteFields`) and settings-log entries without an id (`variationLogItems`, `variationLogItemId`, `parseVariationLogDocument`, `variationLogWriteFields`); `annualLeavePendingOmitFields`; notification `relatedId` per type (`NOTIFICATION_RELATED_ID`, `notificationRelatedId`; iOS minted `UUID()`), and create shapes for inbox rows (`notificationCreateFields`, never rewriting an existing row's read state), invitations (`invitationCreateFields`, `invitationUsedWriteFields`), organisations (`organizationCreateFields`) and tax ids (`taxIdsDocumentFields`).
- Security rules (§16): a staff material status write may carry `updatedBy` / `updatedFrom` (validated); `dismissedWarnings` writes are admins and managers only, as §16 already said. Needs a rules deploy.
- Bug hunt fixes: timesheet saves diff the sheet as loaded (`timesheetChangedFields`; a reviewer save on web wiped an owner's signature, expenses or price work saved on iOS, and the owner path read "manager signed" from a stale copy) (§8); Weekly Report leave days are `leaveDaysInRange` on `leaveRecordDayKeys` (§7); a decision on a leave cancellation notifies the requester (§9); manager site booking edits are partial (`managerSiteBookingUpdateWriteFields`; web merge-set the whole booking and re-stamped `createdAt`) and booking creates carry write metadata (§1); My Schedule and annual leave match every id of the person (`aliasIds`, `leaveRecordsForAccount`) (§9, §10); clash approval writes are one batch (§5).
